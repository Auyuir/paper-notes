# Patterns behind Chaos: Forecasting Data Movement for Efficient Large-Scale MoE LLM Inference 通俗讲解

### 0. 整体创新点通俗解读

**痛点直击**

你想想看，现在主流的大模型都在搞 **MoE (Mixture of Experts)**，比如 DeepSeek V3 或者 Llama4。MoE 的好处很明显：参数量巨大，但每次推理只激活一小部分 **Expert**，算力开销小。

但部署到多卡（比如 8×H100）或者未来的 **Wafer-scale GPU** 上时，这就变成了一场灾难。

- 问题出在 **Data Movement** 上。每个 Token 进来，Gating 机制会临时决定激活哪几个 Expert。
- 如果所需的 Expert 权重不在当前 GPU 的显存（**HBM**) 里，就得跨节点或者跨芯片去搬数据。
- 这种 **All-to-All** 通信和权重搬运的开销，在 DeepSeek V3 这种 4K 序列长度的场景下，直接占了总延迟的 **60% 到 90%**。
- 以前的系统优化都在“头痛医头”：要么死磕通信库，要么搞 CPU-GPU 异步流水线。大家都默认 Expert 的选择是“完全随机”的黑盒，只能在系统层面被动应对拥堵。

![](images/a5717c77c8d18fc9c589075293004fa16adbb237ada6d4924f62c001921af639.jpg)

---

**通俗比方**

这就好比一家有 256 个厨师（**Experts**) 的超级餐厅。每个订单（**Token**) 进来，系统会临时随机指派 8 个厨师做菜。

- 如果厨师和食材都在本地，那没问题。
- 但餐厅太大了，厨师分散在不同的楼层（**多 GPU 或 Chiplet**)。服务员拿着订单到处跑着找厨师，电梯（**Interconnect**) 挤爆了，大部分时间都花在“找人”和“运菜”上，而不是“做菜”。
- 之前的做法是：给电梯提速，或者让服务员跑快点。
- 但这篇论文的作者跳出来了，说：“等等，这帮厨师的排班其实**根本不是完全随机的**！”

作者发现：
- **时间维度**：如果第 1 层用了厨师 A，第 2 层大概率用厨师 B（**Layer-level Correlation**)；如果上一个 Token 用了厨师 A，下一个 Token 很可能还是厨师 A（**Token-level Correlation**)；甚至在处理长句子时，Prefill 阶段查的菜谱，在 Decode 阶段照样适用（**Prefill-Decode Correlation**)。
- **空间维度**：某些厨师特别忙（**Skewness**)，而且某些厨师总是一起搭档（**Co-activation**)。甚至做中餐和做西餐激活的厨师群体完全不一样。

既然有规律，我们就不需要被动等系统分配完再去搬数据，而是可以提前预判，把人提前调度好。

---

**关键一招**

作者并没有去改 MoE 模型的结构，也没有重训模型，而是巧妙地把流程里的**“被动等待”替换成了“主动预测”**。

他们通过对 4 个 SOTA 模型（235B-1000B）跑超过 24000 个 Request 进行 Profiling，提炼出了 6 个核心 Insight，并直接指导了两个层面的系统设计：

- **时间维度：跨层级的预取与缓存**
  - 既然相邻 Layer 或相邻 Token 的 Expert 选择高度相关，作者就在硬件架构里插了一个轻量级的 **Data-driven Predictor**。
  - 当 GPU 算当前的 Expert 时，Predictor 根据历史 Heatmap 直接把下一个 Token 极大概率会用到的 Expert 权重，从远程 Die 提前拉到本地的 **HBM** 里缓存好。
  - 这就把高延迟的远程访存，变成了本地的命中。

- **空间维度：Prefill 感知的负载均衡**
  - 在真实的 8×H100 集群上，Decode 阶段刚开始时，系统根本不知道哪些 Expert 会变热，导致负载极度不均。
  - 作者利用 **Prefill 阶段的 Expert 选择轨迹**，去预测 Decode 阶段的热点 Expert。
  - 在 Decode 开始前，就通过 **Remap**（重新分配）或 **Duplication**（复制热点 Expert 到其他 GPU）把负载摊平。

为了让你直观感受这 6 个 Insight 的威力，我给你总结成一张表：

| 维度 | 观察 | 对应 Insight | 系统设计动作 |
| :--- | :--- | :--- | :--- |
| **Temporal** | Prefill 与 Decode 阶段的 Expert 选择高度相似 | **Insight 1** | 用 Prefill 数据预测 Decode 阶段的热点 Expert |
| **Temporal** | 相邻 Layer/Token 的 Expert 选择有强相关性 | **Insight 2** | 利用短重用距离做 LLC 缓存，长重用距离做 DRAM 缓存 |
| **Spatial** | Expert 激活频率极度偏斜，且受任务类型影响 | **Insight 3 & 4** | 动态分配任务，并将热门 Expert 分散或复制到不同计算单元 |
| **Spatial** | 某些 Expert 对总是一起被激活 | **Insight 5** | 将高频共激活的 Expert 对分离到不同单元，最大化并行度 |
| **Spatial** | 不同语言/任务激活不同 Expert 子集 | **Insight 6** | 根据输入任务的元数据，在服务前提前迁移相关 Expert |

最终的结果非常惊艳：
- 在未来的 **Wafer-scale GPU** 架构上，只加了不到 **0.04%** 的面积开销（加了个 Global Command Processor 和 Prediction Unit），就把 MoE 吞吐量提升了平均 **6.6 倍**。
- 在现有的 8×H100 系统上，仅仅通过 Prefill-guided 的 Expert 放置算法，就把 MoE 计算的时间缩短了 **1.25 倍**。

这就是这篇论文最漂亮的地方：**跳出系统层面的内卷，去模型的“混沌”里找“规律”，用极低的成本四两拨千斤。**

### 1. MoE Data Movement Profiling and System-Agnostic Insights

**痛点直击**

在处理千亿参数规模的 MoE 大模型时，系统设计者一直被一个幽灵折磨：**看似完全随机的专家选择**。

- **时间上的灾难**：模型每一层、每一个 Token 激活哪些专家似乎是抛硬币决定的。以 DeepSeek V3 为例，256 个专家中选 8 个，组合数高达 40 亿种。这种不可预测性导致系统根本不敢提前预取或缓存专家权重。在多节点部署时，GPU 只能干等着主机内存把数据慢吞吞地搬过来，**数据搬运时间占据了总延迟的 60%-90%**。
- **空间上的失衡**：如果专家选择是真随机的，多 GPU 并行时就会发生“旱的旱死，涝的涝死”。某些热门专家被大量请求堵塞，而其他 GPU 上的冷门专家无人问津，硬件利用率极低。
- **过去的盲区**：之前的系统优化往往是“头痛医头”。针对特定的多 GPU 拓扑或特定的卸载策略打补丁，缺乏普适性。根本原因在于，**没有人真正去大规模验证过，这种“随机性”背后到底有没有规律**。

---

**通俗比方**

想象一个拥有 256 个炉灶（专家）的超级中央厨房。每个订单（Token）进来，主厨都会随机指定 8 个炉灶同时做菜。

- **过去的做法**：因为订单分配看起来是纯随机的，厨房管理员只能拼命加宽走道（增加通信带宽），或者把所有炉灶的食材都备在门口（显存卸载）。一旦订单来了，小工满厨房乱跑去各个炉灶拿菜，整个厨房乱作一团，小工跑路的时间比炒菜的时间还长。
- **这篇论文的做法**：管理员连续观察了 24,000 个订单，突然发现这根本不是随机，而是**有套路的暗号**。
  - **时间套路**：如果上一道菜用了 1 号炉，下一道菜大概率还用 1 号炉；甚至早上备菜阶段（Prefill）用哪几个炉，就能预测晚上正式出菜（Decode）用哪几个炉。
  - **空间套路**：做川菜的订单总是死磕那几个特定炉灶；而且 3 号炉和 7 号炉总是被同时点亮，属于“捆绑销售”。

一旦看破了这些套路，厨房就不需要盲目加宽走道了。你只需要把 3 号和 7 号炉放近一点，把经常被点亮的炉灶多复制几台，并且根据早上的备菜单提前把食材放到对应的炉灶上。

---

**关键一招**

作者并没有去重新设计 MoE 的门控网络，也没有去写一个极其复杂的调度器，而是巧妙地完成了一次**视角的扭转**：从“以系统为中心”转变为“以模型数据为中心”。

- **抛弃黑盒假设**：不再把专家路由当成不可预测的黑盒，而是将其视为具有时空相关性的时间序列。
- **提取系统无关的洞察**：通过对四个 2025 年的 SOTA 模型进行超过 2000 GPU 小时的 Profiling，作者提炼出了 6 个极其直白的“物理规律”，并直接转化为系统设计的指导方针：

| 洞察维度 | 核心发现 | 系统设计转化 |
| :--- | :--- | :--- |
| **Temporal (时间)** | **Prefill-Decode 强相关**：Prefill 阶段的热门专家，在 Decode 阶段依然热门。 | 利用 Prefill 数据直接预测 Decode 阶段的专家放置，无需冷启动等待。 |
| **Temporal (时间)** | **Layer/Token 级别相关**：相邻层、相邻 Token 倾向于复用专家。 | 短复用距离映射到 LLC 缓存，长复用距离映射到 Local DRAM，实现跨层级内存管理。 |
| **Spatial (空间)** | **激活极度倾斜**：少数专家被激活的频率是平均水平的 16 倍。 | 将热门专家去中心化，跨计算单元复制，打破负载瓶颈。 |
| **Spatial (空间)** | **专家对共激活亲和性**：某些专家对总是被同时选中。 | 将高频共激活的专家对分离到不同计算单元，最大化并行度。 |
| **Spatial (空间)** | **任务感知倾斜**：不同语言/任务激活的专家集差异巨大。 | 根据输入任务的语言/类型，在服务前提前迁移并布置好专家。 |

- **四两拨千斤的验证**：为了证明这些洞察不是纸上谈兵，作者在两个极端场景下做了验证。
  - **未来晶圆级 GPU**：仅通过添加极低开销（<0.04% 面积）的硬件预测单元和两级命令处理器，就实现了 **6.6 倍**的吞吐量提升。
  - **现有 H100 集群**：直接应用“Prefill 预测 Decode”的软件算法进行专家放置，在 8×H100 上获得了 **1.25 倍**的 MoE 计算加速。

这一招的核心在于：**不要对抗混沌，而是寻找混沌背后的秩序**。一旦证明了数据移动是可预测的，所有层级的系统优化（从片上缓存到多机互联）就都能有的放矢地开火。

### 2. Wafer-Scale GPU Architecture with Data-Placement-Aware Command Processor

**痛点直击**

- Wafer-Scale GPU将几十个die塞进一个晶圆，虽然软件层暴露成单一GPU，但物理上die之间的D2D通信依然是瓶颈。
- MoE推理的专家选择具有动态随机性。传统GPU的Command Processor把所有die视为均质计算单元，无视数据存放位置平分任务。
- 这种盲分配导致严重后果：
  - SM为了计算，频繁跨die读取专家权重，D2D带宽瞬间打满。
  - 热门专家所在die被挤爆，冷门专家所在die空转，负载极度不均。

**通俗比方**

- 把Wafer-Scale GPU想象成一个拥有25个车间的大型工厂。
- 每个车间有本地仓库，车间之间靠传送带连接。
- 传统厂长分配订单不看图纸在哪，直接平均分摊。
- 结果1号车间接单后发现图纸在25号仓库，只能靠传送带去借。大家抢传送带，机器全停工等图纸。
- 聪明的做法是看图下菜：图纸在哪个车间，订单就派给哪个车间。如果某图纸特别抢手，提前复印分发到各车间本地仓库。

**关键一招**

- 作者没有重造轮子，而是在硬件架构里插入了**两级Data-Placement-Aware Command Processor**，配合**硬件管理的HBM**机制。
- **两级智能调度**：
  - **Global CP**：掌握全局专家分布表。打破平均分配，根据专家位置和请求热度，将计算任务精准派发给持有对应专家权重的本地die。
  - **Local CP**：接收指令分发给SM，并管理本地HBM。
- **硬件级预测与缓存**：
  - 利用MoE在Token层面的时间相关性。
  - 在D2D控制器中加入**Prediction Unit (PDU)**。当SM读取远程专家时，PDU根据历史热力图预测该专家未来热度。
  - 若预测热门，通过**Address Translation Unit (ATU)**将远程数据复制到本地HBM。
  - 后续SM请求该专家时，ATU直接重定向至本地HBM，彻底消除跨die通信。

**性能收益对比**

| 策略 | 吞吐量提升 | Hop Count降低比 | 核心瓶颈解决情况 |
| :--- | :--- | :--- | :--- |
| Baseline | 1.0x | 1.0x | D2D通信严重拥堵 |

### 3. Prefill-Guided Expert Placement Algorithms

**痛点直击**

- 在大规模MoE模型推理中，**Decode**阶段的专家选择看似随机，导致严重的**Workload Imbalance**。
- 现有的动态负载均衡方案（如**EPLB**）存在严重的滞后性，需要累积**3000+ steps**的profiling数据才能触发调整。
- 这种“慢半拍”的策略在面对短输出请求时彻底失效：**EPLB**还没收集够数据，请求就已经结束了。
- 结果就是，部分GPU忙死，部分GPU闲死，硬件利用率极差。

**通俗比方**

- 这就像一家刚开业的大型餐厅，有多个后厨（GPU），厨师（专家）分散在各处。
- 客人点单（**Decode**阶段）时，如果发现某几道菜突然爆单，导致一号后厨忙不过来，而二号后厨闲得发慌，这时候再去调厨师就晚了。
- **Prefill**阶段就像是客人落座后看菜单、讨论口味的过程。虽然还没正式点单，但已经透露了强烈的偏好信号。
- 与其等正式上菜时手忙脚乱，不如在看菜单阶段就预测出哪些菜会火，提前把对应的厨师调配均匀。

**关键一招**

- 作者并没有引入复杂的时序预测模型，而是巧妙地利用了**Prefill**和**Decode**阶段专家选择的高度相关性。
- 将**Prefill**阶段收集到的专家激活频率作为先验知识，直接指导**Decode**阶段的初始专家布局。
- 具体设计了两种轻量级算法：
  - **Remap-based**：保持每个GPU上的专家总数不变，根据Prefill频率将热门专家重新分配到负载较轻的GPU上。
  - **Duplication-based**：在每个GPU上预留额外空间，根据Prefill频率直接复制热门专家，分流计算压力。
- 通过这种“时间换空间”的逻辑转换，在**Decode**阶段开始前就抹平了负载差异。

| 算法 | 核心机制 | 性能提升 |
| --- | --- | --- |
| **Remap** | 保持每GPU专家数不变，按Prefill频率重分配 | **15.5%** Speedup |
| **Duplication** | 预留Extra Slots，按Prefill频率复制热门专家 | **12.5%** Speedup |
