# {Comet}{}: Fine-grained Computation-communication Overlapping for Mixture-of-Experts 通俗讲解

### 0. 整体创新点通俗解读

**痛点直击**

MoE 模型在分布式执行时，最大的瓶颈是跨 GPU 的 All-to-All 通信，这能吃掉将近一半的执行时间。之前的做法为了掩盖通信延迟，采用“粗粒度流水线”：把数据切分成几个大块，一边收数据一边算。

这种做法在 MoE 场景下非常难受：
- 切得太碎，GPU 的 GEMM 核心吃不饱，计算效率断崖式下跌。
- 切得太粗，通信和计算的首尾根本对不齐，GPU 空闲（气泡）依然严重。
- MoE 的 Token 路由是动态的，每个 Expert 收到的数据量随时在变。把通信和计算封装在两个独立的 Kernel 里，GPU 调度器根本无法根据实时负载精准分配硬件资源，导致“你发你的，我算我的”，经常互相干等。

---

**通俗比方**

想象一家汽车组装厂（GPU），零件（Token）由不同供应商送货（通信），组装机器（GEMM）负责拼装（计算）。

旧方法：设立独立的收货部和组装部。你要么等一整车零件到了才开始组装（无重叠），要么每次只收 1/4 车就开始组装（粗粒度重叠）。但组装机器喜欢大批量作业，零碎组装效率极低。而且供应商送货量忽大忽小，收货部和组装部经常互相闲置。

Comet 的方法：不再设立独立部门，而是把收货和组装融合在同一个车间（Fused Kernel）。它改变了组装流水线的顺序——不再按整车组装，而是只要 128 个方向盘到了，立刻让对应的组装机器开工（Shared Tensor 分解与重排）。同时，车间里的工人（Thread Block）被分成两组：专职搬货的和专职组装的。如果今天送货慢，就多派工人去搬货；如果送货快，就多派工人去组装（自适应工作负载分配）。

---

**关键一招**

作者并没有重写通信库或重造 GEMM 算子，而是巧妙地在**数据依赖**和**Kernel 调度**上做了“扭转”：

- **Shared Tensor 分解与重排**：作者发现通信和计算之间共享的缓冲区（Shared Tensor）是可以被精细拆分的。在 Layer 0，沿 Token 维度拆分，并按数据来源排序，让本地 Token 先算，远程 Token 边收边算；在 Layer 1，沿 Hidden 维度拆分，把按 Expert 顺序计算改成按列计算，让通信能提前介入。
- **Thread Block 隔离与动态分配**：作者没有把通信 I/O 塞进计算 Kernel 的缝隙里（这会拖慢 Tensor Core），而是把通信和计算分配给不同的 Thread Block。在同一个 Fused Kernel 内部，通过预编译多个版本，在运行时根据负载动态挑选“通信/计算 Thread Block 数量比例”最合适的那个 Kernel，实现无缝贴合。

![](figures/overview_v3.pdf)

**性能对比**

相比现有的 SOTA 系统，Comet 在单层 MoE 和端到端执行上都取得了显著加速：

| 评估维度 | 平均加速比 | 隐藏通信延迟比例 |
| :--- | :--- | :--- |
| 单层 MoE Layer | **1.96x** | **86.5%** |
| 端到端模型执行 | **1.71x** | - |

这种做法彻底打破了“粗粒度切分必然导致计算效率下降”的魔咒，让 MoE 的动态通信延迟被近乎完美地隐藏在计算背后。

### 1. Shared Tensor Decomposition and Rescheduling

**痛点直击**

在 MoE 的执行中，通信（搬移 Token）和计算（GEMM）天生就是“门不当户不对”的。
- 通信的粒度是 **Token 级别**的，一个一个搬。
- GPU 的 GEMM 计算为了吃满算力，必须按 **Tile 级别**（比如 128x128 的矩阵块）来组织数据。

这就导致了严重的“ granularity mismatch（粒度不匹配） ”：
- 如果等所有 Token 都搬完再算，GPU 在通信期间干瞪眼，产生巨大的空闲气泡。
- 如果强行把计算粒度切小去迁就通信，GPU 的 Tensor Core 根本吃不饱，计算效率断崖式下跌。
- 更要命的是，MoE 的动态路由导致一个计算 Tile 需要的 Token 随机散落在不同 GPU 上。你必须等最慢的那个 Token 到齐了才能开算，这种复杂的数据依赖让传统的粗粒度流水线根本无法无缝重叠。

---

**通俗比方**

这就好比开了一家“饺子流水线工厂”。
- **通信**：是外卖小哥（跨 GPU 通信），一趟一趟往店里送饺子皮和馅儿（Token）。
- **计算**：是包饺子机（GEMM），这台机器一旦开机，必须一次性倒进去整整 128 斤的料（Tile）才能高效运转，你一次只给它 1 两皮，它根本转不动。

以前的办法是：等外卖小哥把 128 斤料全凑齐了，机器才开机。结果机器闲死，小哥忙死。
你现在的痛点是：料分散在不同的小哥手里，有的小哥堵车了（网络延迟），你得干等。

Comet 的办法不是让机器变小，而是**重组上菜顺序**。把已经在厨房里的料（本地 Token）先下锅，同时让还在路上的小哥（远程通信）继续送。机器始终满载运转，小哥的延迟被完全隐藏。

---

**关键一招**

作者并没有去重写底层的 NCCL 或者造新硬件，而是巧妙地在中间插了一个**Shared Tensor 分解与重排**的逻辑转换层。

![](figures/overview_v3.pdf)

**Shared Tensor** 就是通信和计算之间共用的那个数据缓冲区。作者对它做了两步“扭转”：

- **第一步：Decomposition（分解）**
  找到数据之间相互独立的维度，把大块 Shared Tensor 切开。
  - 在 Layer 0（通信 -> 计算）：Token 之间是独立的，所以沿着 **M（Token）维度**切。
  - 在 Layer 1（计算 -> 通信）：因为要做 top-K reduction，Token 之间有依赖，不能按 Token 切了。于是沿着 **N（Hidden/Feature）维度**切。

- **第二步：Rescheduling（重排）**
  切完之后，不按原来的死板顺序执行，而是重新排布计算序列。
  - 在 Layer 0：把 Token 按来源 GPU 排序。让 GEMM 先算本地就绪的 Token，把远程 Token 的计算往后排，这就给远程通信留出了时间窗口。
  - 在 Layer 1：打破“算完一个 Expert 再算下一个”的传统。让所有 Expert 沿着 N 维度**列优先**计算。这样只要第一列算完，top-K reduction 就可以提前启动把数据发出去，不用等所有 Expert 全算完。

| 机制 | 传统执行逻辑 | Comet 的重排逻辑 | 解决的痛点 |
| :--- | :--- | :--- | :--- |
| **Layer 0 (Comm -> Comp)** | 按固定顺序等待所有 Token 到齐 | 按 Token 来源排序，本地优先计算 | 隐藏远程 Token 传输延迟 |
| **Layer 1 (Comp -> Comm)** | 逐个 Expert 串行计算完毕后再 Combine | 跨 Expert 按列交错计算 | 提前触发 top-K reduction 通信 |

通过这一招，Comet 让 Token 级的细粒度通信和 Tile 级的高效计算完美咬合，既没牺牲 GPU 的计算效率，又把通信延迟藏得干干净净。

### 2. Thread Block Specialized Fused Kernel

**痛点直击**

之前的 MoE 系统在尝试重叠通信和计算时，面临一个进退两难的困境：
- **独立 Kernel 方案**：把通信和计算封装成不同 Kernel 放在不同 Stream 上。这会导致 GPU 硬件资源分配失控，由于 MoE 动态路由导致负载不均，通信和计算时间经常错位，无法无缝重叠。
- **垂直融合方案**：为了解决上述问题，前人尝试把通信 I/O 塞进计算 Kernel 的 prologue 或 epilogue 中，让同一个 Thread Block 既做通信又做计算。但这在 Hopper 等新架构上简直是灾难。计算 Kernel 依赖 **TMA** 硬件指令建立异步流水线，而细粒度的远程通信 I/O 延迟极高。把高延迟的远程读写塞进计算流水线，会严重阻塞后续计算任务，导致 **GEMM** 计算效率断崖式下跌。
- **核心矛盾**：你试图让它们重叠，但通信的“慢”拖垮了计算的“快”，顾头不顾尾。

---

**通俗比方**

把 GPU 执行任务想象成一家高档餐厅的厨房运作：
- **独立 Kernel**：服务员（通信）和厨师（计算）在不同的房间。服务员把食材放门口，厨师得自己跑出去拿。两人节奏经常对不上，厨师要么等食材，要么停下来去拿食材。
- **垂直融合**：让厨师兼任服务员。厨师炒菜炒到一半，得停下去门口接货。这导致高端炉灶（**Tensor Core**）大量闲置，且厨师来回跑腿效率极低。
- **Thread Block Specialization**：Comet 的做法是，厨师和服务员都在同一个厨房（**Fused Kernel**）里，但职责完全分离。设立专职的“传菜员”（通信 Thread Block）和“专职厨师”（计算 Thread Block）。传菜员不断把远程食材搬进来放在备餐台（共享内存），厨师从不离开炉灶，只管从备餐台拿食材猛炒。两者互不干扰，又高度并行。

---

**关键一招**

作者并没有重写底层的计算逻辑，而是巧妙地在同一个 Kernel 内部进行了**职责隔离**与**资源自适应分配**：

- **职责物理隔离**：在同一个 **Fused Kernel** 内部，不再让单个 Thread Block 承担所有任务，而是划分出专门的计算 Thread Block 和通信 Thread Block。
- **保护计算纯净性**：计算 Thread Block 直接复用标准的 **CUTLASS** 高性能 **GEMM** 实现。由于没有掺杂高延迟的通信 I/O，计算流水线（如 **TMA** 加载与 **MMA** 计算）能够满血运行，维持了极高的计算效率。
- **通信专职化**：通信 Thread Block 专门负责通过 **NVSHMEM** 进行细粒度的远程数据读写，以及 top-K reduction，不参与计算，避免了对计算资源的争抢。
- **自适应负载均衡**：这是最精妙的一招。厨房里厨师和传菜员的比例不是固定的。Comet 会根据当前输入 Token 长度、并行策略等动态指标，在运行时动态调整分配给通信和计算的 Thread Block 数量（例如 $n_c$ 和 $n_p$ 的比例），确保两者的耗时完美对齐，最大化掩盖延迟。

| 方案类型 | 资源控制 | 计算效率 | 重叠效果 |
| :--- | :--- | :--- | :--- |
| 独立 Kernel | 不可控，易错位 | 高 | 差，存在调度开销 |
| 垂直融合 | 可控但互相干扰 | 极低（受 I/O 阻塞） | 表面重叠，实际拖累 |
| **Thread Block Specialization** | **精准且自适应** | **高（复用标准 GEMM）** | **无缝重叠，延迟掩盖最大化** |

### 3. Adaptive Thread Block Assignment

**痛点直击**

- 在 MoE 的执行中，通信和计算必须重叠才能省时间。
- 之前的做法是把通信和计算拆成**独立的 Kernel**，靠 CPU 去调度。这导致两个致命问题：
  - CPU 调度开销大，尤其在输入 Token 少的时候，调度时间比计算时间还长。
  - 两个 Kernel 在 GPU 上抢资源，谁也不知道对方什么时候完，导致**非确定性延迟**，Pipeline 里全是 **Bubbles**（即空闲等待）。
- 如果硬把它们塞进同一个 Kernel（垂直融合），细粒度的远程 I/O 会把计算 Warp 拖死，尤其是在 Hopper 架构上，长延迟的远程访问会直接破坏异步计算流水线。

---

**通俗比方**

![](figures/overview_v3.pdf)

- 把 GPU 的 SM 想象成一家餐厅里的**固定数量的厨师**。
- MoE 的执行就像是做菜：有的厨师负责去隔壁分店拿食材（**通信**），有的厨师负责炒菜（**计算**）。
- 痛点在于：每天客人的点单（**Token 路由**）是随机的。今天点素菜多，炒菜快但拿食材慢；明天点荤菜多，炒菜慢但拿食材快。
- 如果你固定“3个人拿菜，5个人炒菜”，一旦遇到拿菜慢的日子，炒菜的厨师就得干等（**计算 Bubbles**）；遇到炒菜慢的日子，拿菜的厨师就闲着（**通信 Bubbles**）。
- 真正聪明的餐厅经理会根据当天的订单情况，**动态调配**厨师的任务分配。

---

**关键一招**

- 作者没有重头造轮子，而是巧妙地在**同一个 Fused Kernel 内部**做了**物理隔离**与**动态配比**。
- **Thread Block Specialization**：在同一个 Kernel 里，明确划分出“通信 Thread Block”和“计算 Thread Block”。计算 Block 依然跑原生的 CUTLASS GEMM，互不干扰，保住了计算效率。
- **Adaptive Assignment**：作者发现，最优的 Block 分配比例（$n_p / n_c$）是受输入长度 $M$ 和并行策略 $TP$ 影响的。具体数据如下：

| 输入长度 (M) | 并行策略 (TP) | 最优计算 Block 数 ($n_c$) |
| :--- | :--- | :--- |
| 4096 | 8 | 18 |
| 16384 | 8 | 26 |
| 16384 | 4 | 46 |

- 具体操作逻辑：
  - 提前 Profile 各种配置下的最优分配点，存成元数据。
  - 运行时，根据当前的动态负载，直接选择已经预编译好的、带有特定分配比例的 Kernel 来执行。
- 这一招直接把“动态平衡硬件资源”变成了“查表选 Kernel”，既实现了无缝的重叠，又没有引入运行时的动态调度开销。
