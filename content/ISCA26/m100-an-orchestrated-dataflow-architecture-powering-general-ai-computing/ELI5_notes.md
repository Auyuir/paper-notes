# M100: An Orchestrated Dataflow Architecture Powering General AI Computing 通俗讲解

### 0. 整体创新点通俗解读

**痛点直击**

在自动驾驶（AD）和大语言模型（LLM）推理场景下，现有的硬件架构让人非常“难受”：
- **GPGPU太贵且效率低**：像NVIDIA Orin/Thor这类基于SIMT架构的芯片，严重依赖多级Cache系统。但AI推理本质上是海量的Tensor数据流，Cache未命中会导致流水线停顿，硬件利用率低。为了通用性，你付出了高昂的BOM成本和功耗代价。
- **DSA太死板**：像Tesla FSD这种硬连线Domain-Specific Architecture，跑特定的CNN确实快，但现在的算法演进太快（比如端到端VLA模型、Transformer架构）。硬件流水线一旦固化，算法一变，芯片就直接成了废铁。
- **核心矛盾**：既想要GPGPU的灵活性以适应算法演进，又想要DSA的极致效率与低功耗，这中间存在巨大的真空地带。

---

**通俗比方**

把计算单元想象成**厨房里的厨师**，数据就是**食材**，做AI推理就是出餐。

- **GPGPU的做法**：像是一个有着复杂冷藏柜（多级Cache）的厨房。每个厨师做完一道菜，要把半成品放回冷藏柜，下个厨师再去冷藏柜里翻找。厨师花大量时间在开门、找食材、排队上，而且经常拿错（Cache冲突）。
- **M100的做法**：一条**高度编排的流水线**。编译器就像**总厨**，提前把所有步骤规划得明明白白。传送带（DMA）直接把切好的菜（Tensor）精准送到下一个厨师手里。厨师不需要去冷库找东西，只管炒菜。炒完了按一下桌上的**计数器铃铛**（Synchronization Counter），下一个人听到铃响就知道菜来了，直接拿过来继续做。

![](images/dd339399be078c47916aeb503075edde33ae4d3d4d9eeb675abca063d885f689.jpg) *Fig. 2. Architecture of the M100 NPU memory system without multi-level caches.*

---

**关键一招**

作者并没有在传统的指令流架构里死磕，而是巧妙地把**硬件Cache管理**替换成了**编译器编排的显式数据流**，这就是所谓的 **Orchestrated Dataflow Architecture**。

- **干掉多级Cache**：M100 NPU内部直接抛弃了多级Cache。所有的数据搬运由可编程的DMA单元显式控制，在片上SRAM和计算单元的本地内存（HBSM）之间流转。编译器全权负责规划数据在什么时间、出现在什么地点。
- **硬件同步计数器（SC）**：这是最巧妙的逻辑转换。传统架构靠原子操作或锁来同步线程，开销极大。M100直接在硬件里放了一堆极简的计数器。生产者写完数据，计数器+1；消费者盯着计数器，到了预期值就开始算。用极低的硬件开销，实现了大规模并行的生产者-消费者流水线。

![](images/8d040780487db0aa5c9be62b3eb60f0c32a6ad265ad9bfc2ce44caa8d16a3760.jpg) *Fig. 3. Two-way producer/consumer synchronization scheme for concurrent processing engines.*

- **张量级指令分发**：指令不再是细碎的标量Load/Store，而是直接描述整个Tensor的形状和操作。一条指令长达几千比特，虽然传输要花几百个周期，但执行要花几万个周期，完全掩盖了分发开销。

这种“软硬协同”的编排带来了极其恐怖的效率提升。在相同的功耗和带宽预算下，面对UniAD这类自动驾驶网络，M100的帧率达到了Thor的3.8倍以上。

| Benchmark | M100 (8 clusters) | Thor-U | M100 Speedup |
| :--- | :--- | :--- | :--- |
| RegNet | 13.1 ms | 57.4 ms | **4.4x** |
| BEVFormer | 7.92 ms | 32.83 ms | **4.1x** |
| **Frame rate** | **30 FPS** | **7.9 FPS** | **3.8x** |

而在LLM推理中，面对Prefill这种计算密集型任务，M100凭借高效的Tensor Computing Unit和Dataflow同步，实现了对Thor-U的1.95倍加速。

| Benchmark (LLaMA2-7B) | M100 (12 clusters) | Thor-U | M100 Speedup |
| :--- | :--- | :--- | :--- |
| Decode (W4A16) | 21.34 ms | 20 ms | 0.94x |
| **Prefill (W8A8)** | **79 ms** | **154 ms** | **1.95x** |

从执行轨迹图可以直观看出，M100的DMA、TCU、CVU等单元在时间轴上高度重叠，几乎没有空隙，这才是把硬件压榨到极致的表现。

### 1. Orchestrated Dataflow Architecture (编排式数据流架构)

**痛点直击**

- 传统 GPGPU 依赖多级 Cache 和硬件一致性协议，在处理 AI 推理这种规则且庞大的 Tensor 流时，不仅功耗高，且容易遇到 Memory Wall，延迟不可控。
- 传统 Dataflow 架构虽然省去了 Cache，但把数据路由和同步的压力全压在硬件上。硬件需要在运行时动态决定极细粒度数据的流向，导致片上网络极其复杂，面积和开销巨大，难以扩展。
- 自动驾驶（AD）和 LLM 推理既要求极低延迟，又受限于车端功耗和 BOM 成本，上述两种架构都显得“顾头不顾尾”。

**通俗比方**

- 把芯片计算想象成一个大型后厨做宴席。
- **GPGPU 做法**：每个厨师（计算单元）做完一道菜，都要跑去中央冷库（多级 Cache）找食材，大家挤在一起抢食材，效率低下且经常撞车。
- **传统 Dataflow 做法**：食材被切成极小的碎块在传送带上流动，硬件需要一套极其复杂的动态轨道系统，实时决定每一块土豆丝该去哪个锅，轨道系统（片上网络）的建造成本极高。
- **M100 编排式 Dataflow 做法**：行政主厨（Compiler）提前把菜谱研究透，直接规划好整袋土豆（Tensor）的传送路线。传送带（硬件）不需要自己思考，只需按照主厨写好的剧本，把整袋食材按顺序传给指定的厨师。厨师之间通过简单的响铃（同步计数器）确认食材到位。

**关键一招**

- 作者没有在硬件上死磕复杂的动态路由，而是把控制权“上交”给了 Compiler，并在**张量粒度**上进行编排。
- **逻辑转换**：将传统硬件运行时的细粒度数据依赖解析，替换为 Compiler 编译期的粗粒度时空映射。
- 具体操作上，M100 直接砍掉了多级 Cache，采用显式管理的 SRAM 和 DMA。
![](images/dd339399be078c47916aeb503075edde33ae4d3d4d9eeb675abca063d885f689.jpg) *Fig. 2. Architecture of the M100 NPU memory system without multi-level caches.*
- Compiler 将计算图切分为多个子图，在空间上映射到不同的 TPB 集群，在时间上编排 Tensor 的流动阶段。
![](images/871fe25f00279863cfc45fb585cc91eb34d87e445126eea4b436c376dda147c1.jpg) *Fig. 14. Space-time scheduler subgraph mapping and tensor streaming on M100.*
- 硬件层面只保留最简单的生产者-消费者模型，通过硬件计数器（SC）实现极低开销的同步。指令虽然长达数千比特，但执行时间长达数万周期，指令分发不再是瓶颈。

| 架构维度 | 传统 GPGPU | 传统 Dataflow | M100 编排式 Dataflow |
| :--- | :--- | :--- | :--- |
| **控制中心** | 硬件指令调度器 | 硬件动态路由网络 | **Compiler 时空编排** |
| **数据粒度** | 标量/向量指令 | 极细粒度数据包 | **Tensor 级别** |
| **存储层级** | 多级 Cache + 一致性协议 | 分布式寄存器/小缓冲 | **无 Cache，显式 SRAM + DMA** |
| **同步机制** | 原子操作/内存屏障 | 复杂的硬件令牌传递 | **简单的硬件计数器 (SC)** |

### 2. 基于硬件同步计数器的无缓存流式内存系统

**痛点直击**

在传统的 GPGPU 架构中，大规模并行计算面临一个极其“难受”的困境：**Cache Coherence（缓存一致性）开销**。
- 当成百上千个计算核心同时处理张量数据时，硬件需要花费大量资源去保证各级 Cache 的数据一致性。
- AI 推理任务具有强烈的**流式特征**，数据通常是“一次性”的，刚加载到 Cache 就会被消费掉，传统 Cache 基于时间/空间局部性的预取机制不仅无效，反而会导致严重的**缓存抖动**。
- 为了维持一致性，硬件设计极其复杂，不仅占用了大量芯片面积，还带来了不可预测的延迟，这在自动驾驶等对延迟极度敏感的场景中是致命的。

![](images/dd339399be078c47916aeb503075edde33ae4d3d4d9eeb675abca063d885f689.jpg) *Fig. 2. Architecture of the M100 NPU memory system without multi-level caches.*

**通俗比方**

想象一个大型后厨（NPU）在流水线作业。
- **传统 Cache 架构**：每个厨师（计算单元）旁边都有一个小冰箱。厨师 A 切完肉放进去，还得拿大喇叭全厨房广播：“我改了 3 号食材的状态，大家赶紧更新各自的冰箱！” 厨师 B 要用肉之前，还得反复确认 A 有没有偷偷改过状态。人一多，全在喊话和核对，根本没空做菜。
- **M100 的无 Cache 流式系统**：直接把小冰箱全砸了，换成一条**流水线传送带**（HBSM）。洗菜工（生产者）洗完一把菜放上去，按一下旁边的**计数器**（SU）；切菜工（消费者）死盯着计数器，看到数字跳变，就知道传送带上有新菜了，直接拿走开切。切完再按另一个计数器通知炒菜工。
- 没有人需要大喇叭广播，大家只看**信号灯**（硬件计数器），数据像水流一样顺畅传递，完全消除了互相等待和核对的开销。

**关键一招**

作者并没有沿用“硬件自动维护一致性”的老路，而是**把控制权交给了编译器，并用极简的硬件计数器兜底**。
具体逻辑转换如下：
- **砍掉多级 Cache**：用显式管理的 SRAM（HBSM）替代隐式 Cache，数据搬运完全由编译器调度的 DMA 控制。
- **植入硬件同步计数器**：在 TPB 内部设置 Synchronization Unit (SU)。生产者写完数据，计数器 +1；消费者监听计数器，达到预期值才开工。
- **统一数据与同步**：同步动作与内存访问绑定。只要仲裁赢得内存访问权，同步动作即刻生效，无需额外的数据通路。

![](images/8d040780487db0aa5c9be62b3eb60f0c32a6ad265ad9bfc2ce44caa8d16a3760.jpg) *Fig. 3. Two-way producer/consumer synchronization scheme for concurrent processing engines.*

这一招把传统架构中极其复杂的“隐式硬件一致性管理”，降维打击成了“显式的生产者-消费者计数器流水线”。

| 特性 | 传统 GPGPU (Cache-based) | M100 NPU (Cacheless Dataflow) |
|---|---|---|
| **数据共享** | 隐式，依赖多级 Cache | 显式，依赖 HBSM 与 DMA |
| **同步机制** | 原子操作，Cache Coherence | 硬件同步计数器 |
| **硬件复杂度** | 极高 | 显著降低 |
| **流式执行效率** | 易受缓存抖动影响 | 极高，计算与传输完美重叠 |

通过这种设计，M100 用极低的硬件复杂度，换取了极致的流式执行效率，让计算单元真正做到了“数据一来就算，算完就走”。

### 3. Configurable Vector Unit (CVU) 的多阶段流水线重构

**痛点直击**

- 传统向量处理单元在执行复杂算子（如 Softmax、Layer Normalization）时，面临**中间数据反复读写**的困境。
- 每一步基础运算（求 Max、做 Exp、求 Sum）完成后，结果通常要写回 SRAM，下一步运算再重新发起读取。
- 这种模式导致**内存带宽被严重浪费**，且流水线频繁因等待数据而停顿。
- 若为了加速直接将特定算子**硬连线**，又会丧失灵活性。一旦 AI 算法迭代（例如更换激活函数或归一化公式），固定硬件电路就直接作废，无法适应快速演进的模型生态。

**通俗比方**

- 这就像在厨房做一道工序复杂的**佛跳墙**。
- 传统做法是：切菜（放冰箱） -> 炒制（放冰箱） -> 加汤（放冰箱） -> 慢炖。每次换工序都要把半成品存入冰箱再拿出来，费时费力。
- CVU 的做法是：提供一套**积木式的模块化厨具**（切菜机、炒锅、炖锅）。
- 根据当天的菜谱，你直接用传送带把这些厨具连成一条流水线。切好的菜直接掉进炒锅，炒完直接滑进炖锅，全程**不落地（不经过冰箱/SRAM）**。
- 如果明天要做别的菜，拆开传送带重新拼接即可。

**关键一招**

![](images/cf32a7aefeff11c79f048188938ed3a8a00b229c2237c298a802583e9b98ef89.jpg)

- 作者并没有为每个复杂的向量算子单独造一个固定的硬件电路，而是巧妙地插了一个**“可编程的内部路由网络”**。
- CVU 内部包含多个基础的**单功能向量算术单元**（如加法器、乘法器、指数运算器）。
- 编译器通过下发 TPB instructions，动态配置数据的流向：
  - 简单运算：让输入数据只穿过单个算术单元。
  - 复杂运算：把多个算术单元用**中间缓存**串联起来，搭建成一条**定制化的多阶段流水线**。
- 以 Softmax 为例，数据流进去后，自动依次经过求 Max、做减法、求 Exp、累加 Sum、做除法，一气呵成。
- 这种设计把原本需要软件循环调度的多步操作，**压缩成了硬件级别的单次流过**，彻底绕开了 SRAM 的读写瓶颈。

| 特性对比 | 传统向量处理单元 | M100 CVU |
| :--- | :--- | :--- |
| **复杂算子处理** | 软件拆分，多次执行与访存 | 硬件流水线，单次流过 |
| **中间数据存储** | 频繁读写 SRAM | 片上中间缓存直接传递 |
| **灵活性** | 依赖软件指令，灵活但慢 | 硬件可重构，既灵活又快 |
| **适用场景** | 通用向量计算 | 规则可预测的 AI 常见算子 |
