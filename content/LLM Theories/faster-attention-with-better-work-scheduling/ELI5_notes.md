# : Faster Attention with Better Work Scheduling 通俗讲解

### 0. 整体创新点通俗解读

**痛点直击**

之前的 Standard Attention 实现在处理长序列时极其难受，根本原因在于它是典型的 **Memory-bound**（访存密集型）操作。
- GPU 的计算能力极强，但显存带宽有限。计算单元经常处于“饿肚子”等数据的状态。
- 在标准流程中，计算 $\mathbf{S} = \mathbf{Q}\mathbf{K}^\top$ 和 $\mathbf{P} = \mathrm{softmax}(\mathbf{S})$ 时，必须把这两个大小为 $N \times N$ 的巨大中间矩阵反复写入 **HBM**（高带宽显存）再读回。
- 当序列长度 $N$ 很大（如 1k-8k）时，这种 $O(N^2)$ 的显存读写不仅极其缓慢，而且为了反向传播，这些中间结果必须常驻显存，导致显存直接爆炸。
- 传统的 **Kernel fusion** 只能融合简单的逐元素操作，面对 Attention 这种包含矩阵乘法和 softmax 的复杂计算，由于反向传播需要中间状态，传统融合方法直接失效。

现代 GPU 的内存层级存在巨大的剪刀差：

| 内存类型 | 容量 (A100) | 带宽 | 特点 |
| :--- | :--- | :--- | :--- |
| **HBM** | 40-80GB | 1.5-2.0TB/s | 容量大，速度相对慢 |
| **SRAM** | 192KB (per SM) | ~19TB/s | 容量极小，速度快一个数量级 |

---

**通俗比方**

把 GPU 想象成一家工厂，**HBM** 是容量大但进出缓慢的大仓库，**SRAM** 是容量极小但速度极快的工作台。
- **传统做法**：为了组装最终产品 $\mathbf{O}$，你把原材料 $\mathbf{Q}, \mathbf{K}, \mathbf{V}$ 搬到工作台上，拼出一个巨大的半成品 $\mathbf{S}$。因为工作台放不下，你只能把它搬回大仓库。下一步算 softmax 时，又得把这个庞然大物从仓库搬回工作台，算完 $\mathbf{P}$ 再搬回仓库。大部分时间都浪费在搬运上。
- **FlashAttention 的做法**：既然工作台（**SRAM**）快，那就不要一次性生成巨大的半成品。把原材料切成小块，搬一小块 $\mathbf{Q}, \mathbf{K}, \mathbf{V}$ 到工作台上，一口气在桌面上完成所有加工（乘法、softmax、输出），直接把最终成品 $\mathbf{O}$ 的一部分送回仓库。中间的半成品 $\mathbf{S}$ 和 $\mathbf{P}$ 自始至终没有落地到仓库里。

---

**关键一招**

作者并没有修改 Attention 的数学公式，而是巧妙地通过 **Tiling**（分块计算）和 **Recomputation**（重计算）扭转了数据流向。
- **前向传播的“乾坤大挪移”**：作者不再调用标准的 GEMM 子程序去生成完整的 $\mathbf{S}$ 和 $\mathbf{P}$。他们将 $\mathbf{Q}, \mathbf{K}, \mathbf{V}$ 分块加载到 **SRAM** 中，在 SRAM 内部完成 $\mathbf{S}$ 的计算和 softmax，直接得到分块的输出 $\mathbf{O}$ 并累加写回 **HBM**。中间矩阵 $\mathbf{S}$ 和 $\mathbf{P}$ 自始至终没有离开过工作台，彻底消除了 $O(N^2)$ 的 HBM 读写。
- **反向传播的“空间换时间”**：为了反向传播，传统做法必须存储巨大的 $\mathbf{P}$ 矩阵。作者直接抛弃了 $\mathbf{P}$，在反向传播时，利用保存的极小量归一化统计量，在 **SRAM** 中快速重新计算一遍 softmax。这看似多算了，但由于省去了从 **HBM** 读取 $\mathbf{P}$ 的时间，整体速度反而大幅提升。
- 这一招直接将 Attention 从 **Memory-bound** 变成了 **Compute-bound**，让 GPU 的算力终于得以满载运行。

### 1. 标准注意力的内存瓶颈

**痛点直击**

- 之前的做法在处理长序列（大 N）时极其难受，核心痛点是**太慢且太占显存**。
- 慢并不是因为算力不够，而是因为**搬运数据的时间远超计算时间**。
- 现代 GPU 的计算能力呈指数级增长，但 HBM 的带宽增长相对缓慢。标准 Attention 将中间结果 $\mathbf{S}$ 和 $\mathbf{P}$（大小为 $N \times N$）老老实实地写进 HBM，再读出来进行下一步。这导致操作变成了 **Memory-bound**，GPU 强大的计算单元大部分时间都在干等数据搬运。
- 占用显存方面，由于必须存储 $N \times N$ 的矩阵，内存消耗呈 $O(N^2)$ 爆炸式增长，直接卡死了长文本训练的可能性。

---

**通俗比方**

- 把 GPU 想象成一个极速加工厂。
- **计算单元**是极速加工机器，**SRAM** 是紧挨着机器的小工作台（极快但极小），**HBM** 是远处的大仓库（大但搬运慢）。
- 标准 Attention 的做法就像：机器加工出一个巨大的中间零件（$N \times N$ 矩阵），必须先搬到大仓库存起来；下一步要用时，再从大仓库搬回小工作台。
- 零件太大、太重，搬运工（带宽）累死，极速机器只能停工干等。这就是典型的“顾头不顾尾”——只管算出来，不管存取的代价。

| 存储类型 | 容量 (A100) | 带宽 | 角色定位 |
| :--- | :--- | :--- | :--- |
| **HBM** | 40-80GB | 1.5-2.0 TB/s | 大仓库，慢速搬运 |
| **SRAM** | 192KB/SM | ~19 TB/s | 小工作台，极速访问 |

---

**关键一招**

- 瓶颈的根源在于**中间矩阵的实例化**，即把 $\mathbf{S}$ 和 $\mathbf{P}$ 物化到 HBM 中。
- 为了解决这个痛点，作者并没有修改 Attention 的数学公式，而是扭转了**数据流向与计算调度**。
- 具体操作是：**分块计算**。将 $\mathbf{Q}, \mathbf{K}, \mathbf{V}$ 切分成小块，加载到极快的 SRAM 中。
- 在 SRAM 内部直接完成 $\mathbf{Q}\mathbf{K}^\top$、softmax 以及与 $\mathbf{V}$ 的乘法，**中间矩阵 $\mathbf{S}$ 和 $\mathbf{P}$ 根本不落地**，全程留在 SRAM 里。
- 最终只把计算好的最终结果 $\mathbf{O}$ 写回 HBM。这直接将 HBM 的访问量从 $O(N^2)$ 降到了 $O(N)$，彻底打破了内存瓶颈。

### 2. 算子融合

**痛点直击**

现代GPU的算力极强，但显存（**HBM**）的读写带宽相对拖后腿。以A100 GPU为例，其硬件参数差异显著：

| 存储类型     | 容量             | 带宽          |
| -------- | -------------- | ----------- |
| **HBM**  | 40-80GB        | 1.5-2.0TB/s |
| **SRAM** | 192KB (per SM) | ~19TB/s     |
|          |                |             |

- 很多深度学习操作（如激活函数、**softmax**、**dropout**）属于 **memory-bound**，即计算量极小，但需要频繁搬运数据。
- 标准实现中，每执行一个操作，就要从 **HBM** 读数据，算完再写回 **HBM**。
- 如果连续有多个操作作用于同一数据，这种“读-算-写”的循环就会重复多次，导致GPU大部分时间都在等数据搬运，而不是在做计算。
- 更难受的是，在模型训练时，为了保存反向传播所需的梯度，中间结果还必须老老实实写回 **HBM**，进一步加剧了访存瓶颈。

---

**通俗比方**

- 假设你是个大厨（**GPU**），厨房案板（**SRAM**）很小但就在手边，外面的冷库（**HBM**）很大但来回跑极其费时间。
- 你要做一道菜，需要切菜、腌制、下锅三道工序。
- **传统做法**：
  - 去冷库拿食材到案板，切完，端回冷库放着。
  - 再去冷库把切好的拿回来，腌制完，又端回冷库。
  - 最后去冷库拿出来下锅。
- 你大部分时间都耗在跑冷库的路上，案板反而闲置了。
- **算子融合**的做法：你一次性把食材拿到案板上，切完直接腌制，腌制完直接下锅，中间一步都不回冷库。

---

**关键一招**

- 作者并没有修改任何数学公式，而是巧妙地在**底层执行流程**上做了替换。
- 将原本独立的多个 **kernel**（如矩阵乘法 **GEMM**、**softmax**、**dropout**）合并为一个大的 **kernel**。
- 数据一旦从 **HBM** 加载到快速的 **SRAM** 中，就在原地连续完成所有计算。
- 只有最终的输出结果才会被写回 **HBM**。
- 通过这种逻辑转换，将多次昂贵的 **HBM** 访问压缩为一次，直接把 **memory-bound** 的操作变成了接近 **compute-bound**，极大提升了墙钟时间。
