## 1. 摘要

**目的**

- 论文提出**ORCA**，目标是为**Transformer-based generative models**，尤其是类似**GPT-3**的大规模自回归生成模型，提供高效的分布式在线推理服务。
- 核心问题：
  - 现有推理服务系统如**Triton Inference Server**、**TensorFlow Serving**通常采用**request-level scheduling**。
  - 对于自回归生成模型，一个请求需要多次运行模型，每次生成一个**Token**。
  - 同一批次中的请求生成长度不同，导致：
    - **early-finished requests**无法提前返回，只能等待整个 batch 完成。
    - **late-joining requests**无法及时加入，只能等待当前 batch 全部结束。
    - GPU 会对已完成请求继续执行无效计算，降低吞吐并增加延迟。
- 论文目标：
  - 降低生成式模型服务中的**端到端延迟**。
  - 提升高负载下的**吞吐量**。
  - 支持数百亿到数千亿参数级别模型的**distributed serving**。

---

**方法**

- 论文提出两个核心机制：
  - **Iteration-level scheduling**
  - **Selective batching**

- **Iteration-level scheduling**
  - 调度粒度从完整请求改为单次生成迭代。
  - 每次调度只让执行引擎运行模型的一次 iteration。
  - 每次 iteration 结束后，scheduler 可以：
    - 检查请求是否已经完成。
    - 立即返回已完成请求。
    - 将新到达请求加入下一轮调度。
    - 动态调整 batch 中的请求集合。
  - 该机制解决：
    - **early-finished requests**的等待问题。
    - **late-joining requests**的排队问题。
    - 固定 batch 带来的无效计算问题。

- **Selective batching**
  - 问题背景：
    - 在 iteration-level scheduling 下，同一 batch 中的请求可能处于不同状态：
      - 输入长度不同。
      - 已生成 Token 数不同。
      - 有的处于 initiation phase，有的处于 increment phase。
    - 传统 batching 要求张量形状一致，因此无法直接对任意请求集合进行完整 batch 执行。
  - ORCA 的处理方式：
    - 对**非 Attention 操作**继续 batching。
    - 对**Attention 操作**按请求拆分单独执行。
    - Attention 执行后再将结果 merge，继续后续 batched operations。
  - 关键观察：
    - **Attention**本身不包含模型参数。
    - 不对 Attention batching 不会显著减少参数复用机会。
    - 大量计算和参数读取仍集中在 Linear、MLP、LayerNorm 等可 batch 的部分。
  - 支持的操作策略：
    - **QKV Linear**、**Attention Out Linear**、**MLP**等参数密集操作使用 batching。
    - **Attention**针对每个 request 分开处理。
    - **Split/Merge**用于在 batched tensor 与 per-request Attention 之间切换。

![](ad0b0963b5ec1aad7ea60ce20ebc70b0a2d0741ed61c64f672c493bec1ab8f6f.jpg) *Figure 5: An illustration of ORCA execution engine running a Transformer layer on a batch of requests with selective batching. We only depict the QKV Linear, Attention, and Attention Out Linear operations for simplicity.*

- **分布式执行架构**
  - ORCA 支持大模型分布式推理，组合使用：
    - **Intra-layer parallelism**
    - **Inter-layer parallelism**
  - **Intra-layer parallelism**
    - 将单层中的矩阵乘法和参数切分到多个 GPU。
  - **Inter-layer parallelism**
    - 将 Transformer layers 划分到不同 worker 或 GPU 组。
  - ORCA 将控制流与数据流分离：
    - 控制消息使用**gRPC**。
    - GPU tensor 数据通信使用**NCCL**。
  - 该设计减少 CPU-GPU synchronization，提升跨 worker pipeline 效率。

![](e26cdf4e4361d4662eebb26fffdbb4b80c7a96cb3d8be2a0302a733054b7f7b4.jpg) *Figure 7: An illustration of the distributed architecture of ORCA’s execution engine using the parallelization configuration shown in Figure 6. For example, the first inter-layer partition (Layer1 and Layer2) in Figure 6 is assigned to Worker1, while the second partition is assigned to Worker2.*

- **调度算法**
  - ORCA scheduler 采用**iteration-level FCFS**策略。
  - 早到请求应运行不少于晚到请求的 iteration 数。
  - 调度时考虑：
    - **max batch size**
    - **Attention K/V cache memory constraint**
    - 请求的**max_tokens**
  - 对新请求预留 K/V cache slots，避免执行过程中因缓存不足产生 deadlock。
  - 通过持续注入 batch，使 inter-layer partitions 形成 pipeline，提高 GPU 利用率。

| 设计点 | ORCA 方案 | 解决的问题 |
|---|---|---|
| 调度粒度 | **Iteration-level scheduling** | 动态加入新请求，提前返回完成请求 |
| Batch 机制 | **Selective batching** | 支持不同长度、不同阶段请求共同调度 |
| Attention 处理 | Per-request execution | 避免不规则 K/V shape 阻碍 batching |
| 非 Attention 处理 | Batched execution | 保持参数密集操作的高吞吐 |
| 分布式执行 | Intra-layer + Inter-layer parallelism | 支持超大规模 GPT 模型 |
| 通信设计 | gRPC 控制流 + NCCL 数据流 | 减少 CPU-GPU synchronization |

**结果**

- 实验环境：
  - 使用**Azure ND96asr A100 v4 VM**。
  - 每台机器配备**8×NVIDIA A100 40GB GPU**。
  - 多机之间使用**200Gbps HDR InfiniBand**。
- 评估模型：
  - 使用不同规模的**GPT**模型。
  - 最大评估到**341B parameters**。

- **Engine microbenchmark**
  - 在没有调度器影响的情况下比较 ORCA engine 与**FasterTransformer**。

    - ORCA 与 FasterTransformer 性能接近。
    - ORCA 因不 batch Attention，部分配置略慢。
    - 性能差距较小，验证 selective batching 的效率损失有限。
  - 对于**175B**模型：
    - ORCA engine 最多比 FasterTransformer 快**47%**。
    - 主要收益来自控制流与数据流分离，减少同步开销。

- **Batch size 影响**
  - ORCA 增大**max batch size**通常能提高吞吐，且对延迟影响较小。
  - FasterTransformer 增大 batch size 不一定提升吞吐：
    - 固定 batch 会放大请求间长度差异。
    - early-finished requests 仍无法提前返回。
    - microbatch-based pipeline 存在 batching efficiency 与 pipeline efficiency 的权衡。

---

**结论**

- ORCA 证明，传统**request-level scheduling**不适合自回归生成模型服务。
- **Iteration-level scheduling**是服务生成式 Transformer 的关键抽象：
  - 将调度器和执行引擎交互粒度细化到每个 Token 生成 iteration。
  - 显著降低排队延迟和无效计算。
- **Selective batching**解决了 iteration-level scheduling 下请求状态不一致导致的 batching 难题：
  - 对 Attention 拆分执行。
  - 对参数密集的非 Attention 操作保持 batching。
  - 在灵活调度与 GPU 高利用率之间取得平衡。
- ORCA 的分布式架构支持百亿到数千亿参数级别模型推理：
  - 结合**intra-layer parallelism**与**inter-layer parallelism**。
  - 通过控制流和数据流分离减少同步开销。
- 实验表明：
  - ORCA 在大规模 GPT 推理服务中同时提升**latency**与**throughput**。
  - 对**GPT-3 175B**，在相同延迟水平下实现**36.9×吞吐提升**。
- 论文的核心贡献在于：
  - 将生成式模型推理服务的调度单位从 request 重新定义为 iteration。
  - 给出适配 Transformer Attention 特性的 selective batching 机制。
  - 构建了可扩展到数百亿至数千亿参数模型的实际分布式 serving system。

## 2. 背景知识与核心贡献

**研究背景**

- **Transformer-based generative models**，尤其是 **GPT-3** 这类大规模自回归生成模型，已成为语言生成任务的核心基础设施。
  - 应用场景包括：
    - **Chatbot**
    - **Summarization**
    - **Code generation**
    - **Caption generation**
    - **Question answering**
    - **Translation**
    - **Classification as generation**
  - 生成式建模趋势也扩展到其他模态：
    - **Text-to-image generation**
    - **Video-to-text generation**
    - **Speech generation**
    - **Multimodal generation**

- 这类模型的推理过程与传统 DNN 推理不同。
  - 传统模型如 **ResNet**、**BERT** 通常一次运行即可完成一个请求。
  - **GPT** 等自回归模型需要逐 Token 生成：
    - 每次运行模型只生成一个 **output token**
    - 新生成的 token 会作为下一轮输入
    - 一个请求通常需要执行多次 **iteration**
  - 推理流程包含：
    - **Initiation phase**：处理用户输入的多个 input tokens，并生成第一个 output token
    - **Increment phase**：每轮处理一个新生成 token，并继续生成下一个 token

![](29af86d2cac3229be2028a4c5e39953ebc1273f54f3a92b385f30916c5abab2c.jpg) *Figure 1: Illustrations for GPT’s inference procedure, Transformer layer, and internal state usage.*

- 当前主流推理服务系统包括：
  - **NVIDIA Triton Inference Server**
  - **TensorFlow Serving**
  - **FasterTransformer**
  - **TensorRT**
  - **TVM**
- 这些系统通常采用 **request-level scheduling**。
  - Serving system 将多个请求组成一个 batch
  - Execution engine 接收 batch 后持续运行，直到 batch 内所有请求完成
  - Serving system 与 execution engine 只在请求级别交互

![](d6fabf0757f910f5740f07d6a24617d223c4ee028a6fe3f79eaa579d2a4fbd50.jpg) *Figure 2: Overall workflow of serving a generative language model with existing systems.*

---

**研究动机**

- 现有推理服务系统不适合 **multi-iteration autoregressive generation workload**。
  - 根本原因是 **request-level scheduling** 过于粗粒度。
  - 一个 batch 被提交后，请求集合在整个执行期间固定不变。
  - Scheduler 无法在每个 token generation iteration 后重新决策。

- **Early-finished requests** 导致延迟和计算浪费。
  - 同一个 batch 中，不同请求可能需要生成不同数量的 tokens。
  - 较早完成的请求不能立即返回给客户端。
  - Execution engine 仍可能为已完成请求执行无效计算。
  - 结果：
    - **End-to-end latency 增加**
    - **GPU compute 被浪费**
    - **Batch efficiency 下降**

![](b3265c6d41183072bb80fc0b68bca2d365929f9140ea282d5e57c2e0b51679fc.jpg) *Figure 3: An illustration for a case where the requests have the same input length but some requests finish earlier than others. Shaded tokens represent input tokens. “-” denotes inputs and outputs of extra computation imposed by the scheduling.*

- **Late-joining requests** 导致排队时间过长。
  - 新请求如果在当前 batch 执行中到达，必须等待整个 batch 完成。
  - 对长输出请求尤其严重。
  - 请求等待时间不再由单次模型执行决定，而可能被长序列生成拖累。

- 直接改用更细粒度调度会遇到 batching 难题。
  - 如果 scheduler 每个 iteration 都重新选择请求，batch 内请求可能处于不同状态：
    - 不同 input length
    - 不同 generated token index
    - 有的处于 **initiation phase**
    - 有的处于 **increment phase**
  - Transformer 的 **Attention** 依赖历史 **key/value states**。
    - 不同请求的历史长度不同
    - Attention K/V tensor shape 不一致
    - 传统 batching 要求输入 tensor shape 一致
  - 这使得任意请求集合难以直接组成标准 batch。

- 大模型服务还面临分布式执行问题。
  - GPT-3 级别模型参数量可达数千亿。
  - 单 GPU 无法容纳模型参数和 Attention K/V cache。
  - 系统必须支持：
    - **Intra-layer parallelism**
    - **Inter-layer parallelism**
    - **Pipeline parallelism**
    - 高效跨 GPU / 跨机器通信

---

**核心贡献**

- 提出 **iteration-level scheduling**。
  - 将调度粒度从 **request** 降低到 **iteration**。
  - Scheduler 每次只调用 execution engine 执行一轮模型。
  - 每轮 iteration 后，scheduler 可以：
    - 检查请求是否完成
    - 立即返回 finished requests
    - 将 newly arrived requests 纳入下一轮调度
    - 动态调整 batch 中的请求集合
  - 该机制解决：
    - **Early-finished requests 无法及时返回**
    - **Late-joining requests 等待时间过长**
    - **Batch 固定导致资源浪费**

On the other hand, request x<sub>3</sub> only contains input tokens $( x _ { 3 1 } , x _ { 3 2 } )$ because it has not run any iterations yet.*

- 提出 **selective batching**。
  - 关键思想：
    - 不是对 Transformer 中所有 operations 都强制 batching
    - 只对适合 batching 的 operations 进行 batching
    - 对不适合 batching 的 **Attention** 单独处理
  - 对非 Attention operations 使用 token-wise batching：
    - **Linear**
    - **LayerNorm**
    - **Add**
    - **GeLU**
    - **MLP**
  - 对 **Attention operation**：
    - 按 request 拆分执行
    - 每个请求独立访问自己的 Attention K/V cache
    - 避免不同历史长度导致 tensor shape 不一致的问题
  - 设计依据：
    - Attention operation 不包含模型参数
    - 不 batching Attention 不会损失参数复用收益
    - 大模型推理瓶颈主要来自模型参数读取，非 Attention operations 的 batching 更关键

![](ad0b0963b5ec1aad7ea60ce20ebc70b0a2d0741ed61c64f672c493bec1ab8f6f.jpg) *Figure 5: An illustration of ORCA execution engine running a Transformer layer on a batch of requests with selective batching. We only depict the QKV Linear, Attention, and Attention Out Linear operations for simplicity.*

- 构建分布式推理服务系统 **ORCA**。
  - ORCA 将 scheduler 与 execution engine 紧密集成。
  - 系统组件包括：
    - **Endpoint**
    - **Request pool**
    - **Scheduler**
    - **Execution engine**
    - **Attention K/V manager**
  - 支持大规模 Transformer-based generative models 的分布式服务。
  - 支持模型并行：
    - **Intra-layer parallelism**：切分单层中的矩阵计算和参数
    - **Inter-layer parallelism**：按 Transformer layers 切分模型
  - 支持流水线执行：
    - Scheduler 可同时向多个 workers 注入不同 batches
    - 避免 FasterTransformer 依赖 microbatch pipeline 带来的 batching 与 pipelining trade-off

![](e26cdf4e4361d4662eebb26fffdbb4b80c7a96cb3d8be2a0302a733054b7f7b4.jpg) *Figure 7: An illustration of the distributed architecture of ORCA’s execution engine using the parallelization configuration shown in Figure 6. For example, the first inter-layer partition (Layer1 and Layer2) in Figure 6 is assigned to Worker1, while the second partition is assigned to Worker2.*

- 设计面向 iteration-level scheduling 的调度算法。
  - 保持 **iteration-level FCFS**：
    - 早到请求执行的 iteration 数不少于晚到请求
  - 支持 **max batch size** 控制延迟与吞吐权衡。
  - 引入 Attention K/V cache 内存预留机制：
    - 根据请求的 **max_tokens** 预留 K/V slots
    - 避免执行过程中因 K/V cache 空间不足产生 deadlock
  - 让 scheduler 感知 GPU memory constraint。

- 优化分布式执行通信路径。
  - ORCA 区分：
    - **Control plane**
    - **Data plane**
  - Control messages 使用 **gRPC** 等 CPU 通信通道。
  - Intermediate tensor data 使用 **NCCL** 进行 GPU 通信。
  - 避免将 CPU 需要解析的控制信息通过 NCCL 传递，从而减少 CPU-GPU synchronization overhead。

**关键实验结论**

| 对比项 | ORCA 结果 | 基线系统 |
|---|---:|---|
| 代表模型 | **GPT-3 175B** | **FasterTransformer** |
| 相同 latency 下 throughput 提升 | **36.9×** | 1× |
| 最大测试模型规模 | **341B parameters** | FasterTransformer |
| 调度粒度 | **Iteration-level** | Request-level |
| Batching 策略 | **Selective batching** | Full request-level batching |
| 分布式能力 | **Intra-layer + Inter-layer + Pipeline** | Intra-layer + Inter-layer + Microbatch pipeline |

- Microbenchmark 结果显示：
  - ORCA engine 与 FasterTransformer 在单 worker 或 intra-layer parallelism 场景下性能接近。
  - 在 175B 模型、跨 inter-layer partitions 场景中，ORCA 因 control/data plane separation 可比 FasterTransformer 快最高 **47%**。

- End-to-end workload 结果显示：
  - ORCA 在高负载下能显著提升 throughput，并保持较低 latency。
  - FasterTransformer 在请求长度和生成长度异质时表现下降明显。
  - ORCA 对真实服务场景更友好，因为实际请求通常具有：
    - 不同 arrival time
    - 不同 input length
    - 不同 output length
    - 不同 completion time

**核心意义**

- ORCA 的核心价值在于重新定义了生成式 Transformer 推理服务的系统边界。
  - 传统系统将一个请求视为最小调度单位。
  - ORCA 将一个 token generation iteration 视为最小调度单位。
  - 这一变化直接匹配了 autoregressive generation 的计算结构。

- ORCA 的两个关键机制互相依赖。
  - **Iteration-level scheduling** 提供调度灵活性。
  - **Selective batching** 保证灵活调度下仍能高效利用 GPU。
  - 二者结合，使系统同时获得：
    - **低 latency**
    - **高 throughput**
    - **高 GPU utilization**
    - **对异质请求的适应能力**
    - **对超大模型的扩展能力**

## 3. 核心技术和实现细节

### 0. 技术架构概览

**整体定位**

- **ORCA**是一个面向**Transformer-based Generative Models**的分布式推理服务系统，核心目标是在自回归生成场景下同时提升**低延迟**与**高吞吐**。
- 系统针对 GPT 类模型的推理特征进行专门设计：
  - 每个请求不是一次前向计算完成，而是需要执行多个**iteration**。
  - 每个**iteration**生成一个新的**token**。
  - 不同请求的输入长度、生成长度、当前 token index 可能不同。
  - 传统 serving 系统以**request-level scheduling**为粒度，导致早完成请求无法及时返回，新请求也无法及时加入。
- ORCA 的整体架构由两项核心机制支撑：
  - **Iteration-level Scheduling**
    - 调度粒度从整个 request 降到单个 generation iteration。
    - 每轮只执行一个 iteration，允许请求在 iteration 边界动态加入或离开 batch。
  - **Selective Batching**
    - 对非 Attention 操作进行 batching。
    - 对 Attention 操作按 request 拆分执行。
    - 解决不同请求 token 长度、状态长度不一致导致的 batch 形状不兼容问题。

---

**系统总览**

![](22f25004781927f2deef3e118526ef78014c1e7db2c2ce55763d163698e991ee.jpg) *Figure 4: System overview of ORCA. Interactions between components represented as dotted lines indicate that the interaction takes place at every iteration of the execution engine. $x _ { i j }$ is the j-th token of the i-th request. Shaded tokens represent input tokens received from the clients, while unshaded tokens are generated by ORCA. For example, request $x _ { 1 }$ initially arrived with two input tokens $( x _ { 1 1 } , x _ { 1 2 } )$ and have run two iterations so far, where the first and second iterations generated $x _ { 1 3 }$ and $x _ { 1 4 } .$ respectively. On the other hand, request x<sub>3</sub> only contains input tokens $( x _ { 3 1 } , x _ { 3 2 } )$ because it has not run any iterations yet.*

- ORCA 的整体系统由以下核心组件组成：
  - **Endpoint**
    - 对外暴露服务接口，例如 **HTTPS**或**gRPC**。
    - 接收客户端的 generation request。
    - 将新请求放入**Request Pool**。
    - 在请求完成后向客户端返回生成结果。
  - **Request Pool**
    - 管理系统内所有活跃请求的生命周期。
    - 记录每个请求的状态、输入 token、已生成 token、当前 generation 进度等。
    - 支持请求动态加入、完成后移除。
  - **Scheduler**
    - ORCA 的核心控制组件。
    - 每个 iteration 都会从 Request Pool 中选择一批请求。
    - 将选中的请求发送给 Execution Engine 执行一个 iteration。
    - 接收每个请求生成的新 token。
    - 更新 Request Pool 中的请求状态。
    - 发现请求完成后立即触发返回。
  - **Execution Engine**
    - 执行 Transformer 模型的实际 tensor computation。
    - 支持单 GPU、多 GPU、多机器分布式执行。
    - 内部实现**Selective Batching**。
    - 管理 Attention K/V cache。
  - **Attention K/V Manager**
    - 为每个请求维护 Attention 的历史 **Key/Value states**。
    - 支持自回归增量解码。
    - 请求完成后释放对应的 K/V memory slots。

---

**核心执行流程**

- 客户端提交请求：
  - 请求包含输入 tokens。
  - 请求进入 ORCA 的**Endpoint**。
  - Endpoint 将请求加入**Request Pool**。
- Scheduler 周期性调度：
  - Scheduler 检查 Request Pool。
  - 根据调度策略选择最多**max batch size**个请求。
  - 选中的请求可以处于不同状态：
    - **Initiation phase**
      - 请求第一次被调度。
      - 输入是完整 prompt tokens。
    - **Increment phase**
      - 请求已经生成过 token。
      - 输入通常是上一个 iteration 生成的单个 token。
- Execution Engine 执行一个 iteration：
  - 对 batch 中每个请求生成一个新 token。
  - 使用 Attention K/V Manager 读取历史 Key/Value。
  - 生成新的 Key/Value 并追加保存。
- Scheduler 接收结果：
  - 将新 token 追加到对应请求。
  - 检查是否达到终止条件：
    - 生成了**EOS token**。
    - 达到请求的**max tokens**或**max generation tokens**。
  - 完成请求立即返回客户端。
  - 未完成请求留在 Request Pool，等待后续 iteration。

---

**架构核心思想：Iteration-level Scheduling**

- ORCA 将传统 serving 系统中的调度粒度从**request-level**改为**iteration-level**。
- 传统架构的问题：
  - 一个 batch 被送入 engine 后，必须等 batch 内所有请求完成。
  - 早完成请求仍然被迫等待。
  - 新到达请求必须等当前 batch 全部结束。
  - 对生成长度差异大的 workload 极不友好。
- ORCA 的改进：
  - 每次只调度一个 iteration。
  - 每个 iteration 结束后 scheduler 都能重新决定 batch 组成。
  - 新请求最多等待当前 iteration 完成即可加入。
  - 已完成请求可以立即离开 batch 并返回。
- 带来的效果：
  - 降低**queueing delay**。
  - 降低早完成请求的**tail latency**。
  - 减少 inactive request 的无效计算。
  - 提高 GPU 利用率和 batch 灵活性。

---

**架构核心思想：Selective Batching**

![](ad0b0963b5ec1aad7ea60ce20ebc70b0a2d0741ed61c64f672c493bec1ab8f6f.jpg) *Figure 5: An illustration of ORCA execution engine running a Transformer layer on a batch of requests with selective batching. We only depict the QKV Linear, Attention, and Attention Out Linear operations for simplicity.*

- ORCA 需要在 iteration-level scheduling 下仍然保持 batching 效率。
- 难点在于：
  - 不同请求可能处于不同 phase。
  - 不同请求可能有不同 prompt length。
  - 不同请求可能处于不同 token index。
  - Attention 的 Key/Value state 长度随 token index 增长。
  - 因此 Attention 输入 tensor shape 不一致，无法直接组成传统 batch。
- ORCA 的解决方式：
  - 对**非 Attention 操作**进行 token-wise batching。
  - 对**Attention 操作**按 request 分开执行。
  - Attention 执行后再 merge 回统一 tensor。
- 适合 batching 的操作：
  - **LayerNorm**
  - **QKV Linear**
  - **Attention Out Linear**
  - **MLP**
  - **Add**
  - **GeLU**
- 不直接 batching 的操作：
  - **Attention**
    - 因为每个请求的历史 K/V 长度不同。
    - Attention 需要区分 request 边界。
    - Attention 本身没有 model parameters，不 batching 对参数复用收益影响较小。
- Selective Batching 的本质：
  - 保留大部分 Transformer 层中参数密集操作的 batching 收益。
  - 避免 Attention 的不规则 shape 限制整个 batch。
  - 让任意一组请求都可以组成 batch，而不要求 token index 或 prompt length 一致。

**Execution Engine 分布式架构**

![](e26cdf4e4361d4662eebb26fffdbb4b80c7a96cb3d8be2a0302a733054b7f7b4.jpg) *Figure 7: An illustration of the distributed architecture of ORCA’s execution engine using the parallelization configuration shown in Figure 6. For example, the first inter-layer partition (Layer1 and Layer2) in Figure 6 is assigned to Worker1, while the second partition is assigned to Worker2.*

- ORCA Execution Engine 支持大模型分布式推理，面向百亿到数千亿参数级别模型。
- 采用两类模型并行策略：
  - **Intra-layer Parallelism**
    - 在单个 Transformer layer 内部切分矩阵乘法和相关参数。
    - 多个 GPU 共同计算同一层中的 Linear、Attention 等操作。
    - 主要用于处理单层参数过大的问题。
  - **Inter-layer Parallelism**
    - 将 Transformer layers 按层划分给不同 worker。
    - 每个 worker 负责一组连续 layer。
    - 多个 worker 构成 pipeline。
- ORCA 中的 worker 架构：
  - 每个**Worker Process**负责一个 inter-layer partition。
  - 每个 worker 内部包含多个 CPU threads。
  - 每个 CPU thread 控制一个 GPU。
  - intra-layer partition 的多个 GPU 共同执行该 worker 负责的 layers。
- Engine Master 的职责：
  - 接收 Scheduler 发来的 batch execution request。
  - 将 batch 的 token 和 control message 发送给第一个 worker。
  - 接收最后一个 worker 返回的 output tokens。
- Worker Controller 的职责：
  - 接收 control message。
  - 将信息分发给 GPU-controlling threads。
  - 向下一个 worker 转发 control message。
  - 协调本 worker 内 GPU kernel launch。

**模型并行布局**

![](8ea2f728df36f05ba6d1b8c302f0f68cbbe7c0dfbaa91478de5582ea6b7b6771.jpg) *Figure 6: An example of intra- and inter- layer parallelism. A vertical dotted line indicates partitioning between layers and a horizontal line indicates partitioning within a layer.*

- ORCA 的模型切分方式可组合使用：
  - 横向切分 layer 内部计算，即**intra-layer parallelism**。
  - 纵向切分 layer stack，即**inter-layer parallelism**。
- 示例：
  - 一个 4-layer GPT 模型被分成 2 个 inter-layer partitions。
  - 每个 inter-layer partition 内部再被分成 3 个 intra-layer partitions。
  - 总共使用 6 个 GPU。
- 这种架构适合服务超大规模 GPT 类模型：
  - 参数无法放入单 GPU 时，可通过 intra-layer 切分。
  - layer 数量较多时，可通过 inter-layer pipeline 提升吞吐。
  - 多机多 GPU 场景下可同时扩展模型容量和并发处理能力。

---

**Control Plane 与 Data Plane 分离**

- ORCA 在分布式执行中区分两类通信：
  - **Control Plane**
    - 传输 request id、token index、input length、batch metadata 等控制信息。
    - 主要由 CPU 使用。
    - 使用 **gRPC**等普通通信机制。
  - **Data Plane**
    - 传输 GPU tensor intermediate results。
    - 主要由 GPU 生产和消费。
    - 使用 **NCCL**进行高带宽 GPU-to-GPU 通信。
- 设计动机：
  - 传统系统常用 NCCL 同时传输控制信息和 tensor 数据。
  - 控制信息会引入 CPU-GPU synchronization。
  - 每个 iteration 都发生同步，会造成明显开销。
- ORCA 的改进：
  - 控制信息不经过 NCCL。
  - CPU 可以直接处理 control message。
  - NCCL 专注于 tensor 数据传输。
  - 减少 CPU-GPU synchronization。
  - 提高多 worker pipeline 效率。

---

**Pipeline Parallelism 架构**

![](d6fabf0757f910f5740f07d6a24617d223c4ee028a6fe3f79eaa579d2a4fbd50.jpg) *Figure 2: Overall workflow of serving a generative language model with existing systems.*

- ORCA 的 pipeline 不是通过将单个 request batch 切成 microbatch 实现，而是通过**iteration-level scheduling**自然形成。
- Scheduler 可以在前一个 batch 尚未完全返回时继续注入后续 batch。
- 当 inter-layer workers 数量为**n_workers**时：
  - Scheduler 最多保持 n_workers 个 batch 同时在 engine 中流动。
  - 每个 worker 尽量保持忙碌。
  - 减少 pipeline bubbles。
- 与 FasterTransformer 的区别：
  - FasterTransformer 通常需要将 batch 拆成 microbatches 来填充 pipeline。
  - microbatch 太小会降低 batching 效率。
  - microbatch 太大又容易产生 pipeline bubbles。
  - ORCA 不需要在 batching efficiency 和 pipelining efficiency 之间做同等程度的权衡。
- ORCA 的优势：
  - batch 不必拆小。
  - pipeline 可以跨 iteration batch 自然展开。
  - 更适合持续到达的在线 serving workload。

---

**Scheduler 架构与调度策略**

- ORCA Scheduler 使用**iteration-level FCFS**策略。
- iteration-level FCFS 的含义：
  - 如果请求 A 比请求 B 更早到达，则 A 已执行的 iteration 数量必须不少于 B。
  - 后到达请求可能因为生成 token 更少而更早完成并返回，但不能在 iteration 进度上超过早到达请求。
- Scheduler 每轮选择请求时考虑：
  - **Arrival time**
    - 按到达时间排序。
  - **max batch size**
    - 限制单个 iteration batch 的最大请求数。
  - **K/V cache memory constraint**
    - 对第一次调度的请求预留 K/V slots。
    - 防止运行中因 K/V cache 空间不足而 deadlock。
- 请求状态包括：
  - **INITIATION**
    - 请求尚未执行过。
    - 需要为其预留 Attention K/V memory。
  - **RUNNING**
    - 请求已经被调度但对应 batch 尚未返回。
  - **INCREMENT**
    - 请求已经完成 initiation，后续按单 token iteration 执行。
- 关键参数：
  - **max_bs**
    - 最大 batch size。
    - 影响 latency-throughput trade-off。
  - **n_slots**
    - Attention K/V Manager 可用 slots 数。
    - 由 GPU memory budget 和模型规格决定。
  - **n_workers**
    - inter-layer pipeline worker 数量。
    - 决定可同时注入的 batch 数。

---

**Attention K/V Manager 架构**

- ORCA 为每个请求维护独立的 Attention Key/Value states。
- K/V cache 的特点：
  - 大小随生成 token 数增长。
  - 请求之间长度不同。
  - 不能像普通 intermediate activation 一样立即复用。
- K/V Manager 的职责：
  - 为新请求分配 K/V memory slots。
  - 在每个 iteration 保存当前 token 对应的 Key/Value。
  - 在 Attention 计算时提供历史 Key/Value。
  - 请求完成后释放该请求占用的 slots。
- Scheduler 与 K/V Manager 协同：
  - 请求第一次被调度前，Scheduler 根据请求的**max_tokens**预留足够 slots。
  - 若剩余 slots 不足，暂不调度该请求。
  - 保证请求一旦启动，就不会因 K/V cache 空间不足中途阻塞。
- 该设计避免了：
  - 运行时 memory allocation failure。
  - K/V cache deadlock。
  - 为所有请求按最大序列长度静态分配造成的显存浪费。

---

**与传统 Serving 架构的对比**

| 维度 | 传统 Serving 系统，例如 Triton + FasterTransformer | ORCA |
|---|---|---|
| 调度粒度 | **Request-level** | **Iteration-level** |
| Batch 生命周期 | 固定到整个 batch 完成 | 每个 iteration 可重组 |
| 新请求加入 | 等当前 batch 全部完成 | 等当前 iteration 完成 |
| 早完成请求返回 | 等 batch 内所有请求完成 | 完成后立即返回 |
| Attention batching | 全操作统一 batching | **Selective Batching** |
| 不同 token index 请求 | 难以高效 batch | 可组成同一 batch |
| Pipeline 实现 | 依赖 microbatch | 跨 iteration batch 自然 pipeline |
| K/V cache 管理 | 常按最大序列长度预分配 | 按请求 max_tokens 预留 |
| 分布式通信 | 控制与数据可能混合 | **Control/Data Plane 分离** |

### 3. Attention K/V State Manager

**Attention K/V State Manager 的核心定位**

- **Attention K/V State Manager** 是 ORCA execution engine 中负责维护每个请求历史 **Attention keys** 和 **Attention values** 的状态管理组件。
- 它服务于 Transformer-based generative model 的 **autoregressive generation**：
  - 每个请求需要逐 token 生成输出。
  - 每次生成新 token 时，当前 token 的 **query** 需要与该请求此前所有 token 的 **keys/values** 做 Attention。
  - 如果不缓存历史 K/V，每一轮都要重新计算此前所有 token 的 K/V，计算量会随序列长度显著膨胀。
- ORCA 采用类似 **incremental decoding** 的机制：
  - **initiation phase** 处理 client 提供的输入 tokens，并生成第一批 K/V 状态。
  - **increment phase** 每次只处理一个新 token，并复用此前缓存的 K/V 状态。
- **Attention K/V State Manager** 的关键价值：
  - 避免重复计算历史 token 的 K/V。
  - 支持不同请求拥有不同长度的历史状态。
  - 支持 **iteration-level scheduling** 下请求动态加入、完成、释放。
  - 让 ORCA 能在 **selective batching** 中对 Attention 进行 per-request execution，同时对非 Attention ops 继续做 token-wise batching。

![](ad0b0963b5ec1aad7ea60ce20ebc70b0a2d0741ed61c64f672c493bec1ab8f6f.jpg) *Figure 5: An illustration of ORCA execution engine running a Transformer layer on a batch of requests with selective batching. We only depict the QKV Linear, Attention, and Attention Out Linear operations for simplicity.*

---

**为什么需要单独的 K/V State Manager**

- Transformer 的 Attention 与 LSTM/RNN 的状态模式不同：
  - LSTM 的 hidden state / cell state 通常是固定大小。
  - Transformer 的 Attention K/V state 会随已处理 token 数线性增长。
- 对于第 t 个 token，Attention 需要访问：
  - 当前 token 的 **query**。
  - 当前 token 生成的 **key/value**。
  - 同一请求中此前 token 的所有 **keys/values**。
- 状态访问可抽象为：
  - 当前层第 l 层处理 token t 时，需要：
    - 历史 keys：**k_l,1:t-1**
    - 历史 values：**v_l,1:t-1**
    - 当前 key：**k_l,t**
    - 当前 value：**v_l,t**
- 这导致 K/V 状态具有两个重要特征：
  - **请求隔离**：不同请求的 K/V 不能混用。
  - **长度可变**：不同请求已生成 token 数不同，K/V tensor shape 不同。
- ORCA 的 **iteration-level scheduling** 会让一个 batch 中包含处于不同阶段、不同 token index 的请求：
  - 某些请求还在 initiation phase。
  - 某些请求已进入 increment phase。
  - 某些请求历史长度很短。
  - 某些请求历史长度很长。
- 传统 batch Attention 要求 batch 内 tensor shape 对齐，这在 ORCA 的动态调度下很难满足。
- ORCA 因此将 Attention 从全局 batch 中拆出来：
  - 非 Attention operations 使用 flattened token-wise batching。
  - Attention operation 按请求单独执行。
  - **Attention K/V State Manager** 为每个单独 Attention kernel 提供该请求对应的历史 K/V 地址。

**在 ORCA 整体架构中的位置**

- **Attention K/V State Manager** 位于 ORCA execution engine 内部。
- 它与以下组件协同：
  - **Scheduler**
    - 决定每一轮 iteration 调度哪些请求。
    - 在请求首次被调度时，为其 K/V state 预留 slots。
    - 在请求完成时，通知释放该请求对应缓存。
  - **Request Pool**
    - 保存请求生命周期状态。
    - 记录请求是否处于 **INITIATION**、**INCREMENT**、**RUNNING** 等状态。
  - **Execution Engine / Worker**
    - 执行 Transformer layer。
    - 在 Attention kernel 中根据 request id 和 token index 访问 K/V state。
  - **GPU kernels**
    - QKV Linear 生成当前 token 的 query/key/value。
    - Attention kernel 从 K/V Manager 读取历史 K/V，并写入当前 K/V。
- 在 distributed execution 中：
  - 每个 worker 负责部分 Transformer layers。
  - 每个 worker 内部维护其负责 layers 对应的 K/V state。
  - intra-layer parallelism 下，K/V 也按 partition 维度分布在不同 GPU 上。
  - inter-layer parallelism 下，不同 worker 维护不同 layer partition 的 K/V。

**输入输出关系**

| 阶段 | 输入 | K/V Manager 行为 | 输出 |
|---|---|---|---|
| **initiation phase** | client input tokens，request id，max_tokens | 为请求分配或绑定预留 K/V slots；保存输入 tokens 产生的 K/V | 当前请求的历史 K/V 状态被初始化；返回第一个 generated token |
| **increment phase** | 当前 generated token，request id，current token index | 读取该请求历史 K/V；追加当前 token 的 K/V | 更新后的 K/V 状态；返回下一个 generated token |
| **request finish** | request id，finish signal | 释放该请求占用的 K/V slots | K/V memory 可被后续请求复用 |

- Attention operation 的输入关系：
  - 来自 QKV Linear：
    - 当前 token 的 **query**
    - 当前 token 的 **key**
    - 当前 token 的 **value**
  - 来自 K/V Manager：
    - 同一 request id 下此前 tokens 的 **keys**
    - 同一 request id 下此前 tokens 的 **values**
  - 来自 scheduler/control message：
    - **request id**
    - **current token index**
    - **input length**
    - **phase information**
- Attention operation 的输出关系：
  - 对当前 token 计算出的 **context vector**。
  - 当前 token 的 **key/value** 被追加写入 K/V Manager。
  - 后续 Attn Out Linear、MLP 等非 Attention operations 继续在 flattened batch tensor 上执行。
- K/V Manager 的状态输出不是直接返回给 client：
  - 它是 engine 内部状态。
  - client 只接收生成的 output tokens。
  - K/V state 用于后续 iterations 的计算加速。

---

**核心数据结构抽象**

- K/V Manager 可理解为维护一个按请求索引的状态表：
  - key：**request id**
  - value：该请求在各 Transformer layer 上的 K/V buffers 元信息。
- 每个请求的 K/V 状态包含：
  - **request id**
  - **max_tokens**
  - **current length**
  - **per-layer key buffer address**
  - **per-layer value buffer address**
  - **slot range**
  - **phase/status**
- 每个 token 的 K/V 占用一个或多个逻辑 **slot**：
  - 论文中定义 **slot** 为存储一个 token 的 Attention key 和 value 所需的 GPU memory 单元。
  - 实际实现中，slot 大小取决于：
    - hidden size
    - number of layers
    - number of attention heads
    - fp16/bf16 precision
    - intra-layer partition degree
    - inter-layer partition degree
- K/V memory 可抽象为预分配区域：
  - 总容量为 **n_slots**。
  - scheduler 使用 **n_rsrv** 记录已预留 slots 数。
  - 请求首次调度时一次性预留 **req.max_tokens** 个 slots。
  - 请求结束后释放 **req.max_tokens** 个 slots。

---

**关键参数设置**

| 参数 | 含义 | 作用 | 设置原则 |
|---|---|---|---|
| **n_slots** | K/V Manager 可用 slot 总数 | 限制同时可服务请求的总 token 容量 | 在 GPU memory 允许范围内尽量设大 |
| **req.max_tokens** | 单个请求最大 token 数 | 请求首次调度时预留的 K/V slots 数 | 通常等于 input tokens + max_gen_tokens |
| **n_rsrv** | 当前已预留 slots 数 | scheduler 判断是否还能接纳新请求 | 动态更新 |
| **max_bs** | 每次 iteration 最大 batch size | 控制每轮最多处理多少请求 | 在 latency/throughput 之间调优 |
| **current token index** | 请求当前处理 token 位置 | Attention kernel 定位历史 K/V 范围 | 由 scheduler/control message 提供 |
| **request id** | 请求唯一标识 | K/V Manager 查找对应 buffer | 贯穿请求生命周期 |

- **n_slots** 是 K/V Manager 最关键的容量参数：
  - 它决定系统同时容纳多少历史 K/V。
  - 它不是 batch size，而是 token-level state capacity。
  - 对长输出请求更敏感。
- **req.max_tokens** 的预留策略保守但安全：
  - 请求首次被调度时，ORCA 直接预留该请求可能使用的最大 K/V 空间。
  - 即使实际生成提前结束，预留空间也在请求完成时才释放。
  - 好处是避免中途因 K/V 空间不足导致 deadlock。
- **n_rsrv** 的更新规则：
  - 新请求进入 initiation phase 并被选中：
    - n_rsrv += req.max_tokens
  - 请求完成：
    - n_rsrv -= req.max_tokens
- 这种策略牺牲一部分 memory utilization，换取调度安全性和实现简单性。

---

**内存管理流程**

- 请求到达：
  - endpoint 接收 client request。
  - request 被插入 **request_pool**。
  - 初始状态为 **INITIATION**。
  - 请求携带或推导出 **max_tokens**。
- 请求首次被 scheduler 选中：
  - scheduler 检查：
    - n_rsrv + req.max_tokens <= n_slots
  - 若满足：
    - 为该请求预留 K/V slots。
    - 将请求加入当前 batch。
  - 若不满足：
    - 停止继续选入新 initiation requests。
    - 等待已有请求完成释放 K/V slots。
- initiation phase 执行：
  - QKV Linear 为输入 tokens 生成 K/V。
  - K/V Manager 写入这些 input tokens 的 K/V。
  - Attention 计算得到第一个 output token。
  - 请求状态转入 **INCREMENT**。
- increment phase 执行：
  - 每次 iteration 只处理一个当前 token。
  - Attention kernel 根据 request id 读取该请求此前所有 K/V。
  - 当前 token 生成的新 K/V 被追加写入对应 slot。
  - current length 增加。
- 请求完成：
  - scheduler 检测到 finished(req)。
  - K/V Manager 释放该请求预留的 slots。
  - request_pool 删除该请求。
  - endpoint 返回结果给 client。

---

**算法流程细化**

- Scheduler 的 Select 逻辑与 K/V Manager 紧密绑定：
  - 从 request_pool 中过滤掉正在运行的请求。
  - 按 arrival time 排序，保证 **iteration-level FCFS**。
  - 最多选择 **max_bs** 个请求。
  - 对于处于 **INITIATION** 的请求：
    - 尝试预留 req.max_tokens 个 K/V slots。
    - 如果超出 n_slots，则不再选择该请求。
  - 对于处于 **INCREMENT** 的请求：
    - 不需要再次预留。
    - 直接加入 batch。
- 调度伪逻辑可概括为：
  - 选择候选请求。
  - 对新请求做 K/V capacity admission control。
  - 发起一轮 model iteration。
  - engine 返回 output token。
  - 更新 request state。
  - 若请求完成，释放 K/V reservation。

| 操作 | 是否访问 K/V Manager | 说明 |
|---|---:|---|
| **LayerNorm** | 否 | token-wise operation，可直接处理 flattened tensor |
| **QKV Linear** | 间接相关 | 生成当前 token 的 key/value，随后写入 K/V Manager |
| **Attention** | 是 | 读取历史 K/V，追加当前 K/V |
| **Attn Out Linear** | 否 | 不需要区分请求历史 |
| **MLP** | 否 | 可批处理 flattened tensor |
| **Add / GeLU** | 否 | token-wise operation |

---

**与 selective batching 的耦合关系**

- ORCA 的 selective batching 将 Transformer layer 分成两类：
  - **可 token-wise batching 的非 Attention operations**
    - Linear
    - LayerNorm
    - Add
    - GeLU
    - MLP
  - **需要 request-aware execution 的 Attention operation**
    - 必须知道每个 token 属于哪个请求。
    - 必须只对同一请求内部 tokens 做 attention。
    - 必须访问该请求自己的历史 K/V。
- K/V Manager 让 Attention 可以在 batch 被拆分后独立执行：
  - Split operation 将 flattened tensor 按请求拆开。
  - Attention kernel 对每个请求分别访问对应 K/V state。
  - Merge operation 将 Attention 输出重新合并为 flattened tensor。
- 这种设计避免了要求 batch 内请求拥有相同 token index：
  - 请求 x1 可能已有 4 个 tokens。
  - 请求 x2 可能已有 2 个 tokens。
  - 请求 x3 可能刚进入 initiation。
  - 请求 x4 可能 input length 更长。
- K/V Manager 提供 per-request state lookup，使这些请求可以在同一个 iteration-level batch 中共存。

---

**为什么 Attention 不强制 batching 损失较小**

- Attention operation 与 Linear / MLP 的核心差异：
  - Linear / MLP 包含大量 model parameters。
  - Attention 的 dot-product、Softmax、weighted sum 本身不包含 model parameters。
- 对 Linear / MLP 做 batching 的收益很大：
  - 可以复用从 GPU global memory 读取的 model parameters。
  - 更好利用 GPU matrix multiplication。
- 对 Attention 做 request-wise batching 的收益相对有限：
  - 不存在大量参数复用。
  - 主要处理 activation 和 K/V state。
  - 不 batch Attention 带来的损失小于不 batch Linear/MLP。
- ORCA 因此选择：
  - 保留非 Attention operations 的 batching。
  - 放弃 Attention 的严格 batch shape 对齐要求。
  - 用 K/V Manager 支撑可变长度状态访问。
- 该取舍是 ORCA 能同时实现 **iteration-level scheduling** 和高 GPU utilization 的关键。

---

**分布式场景下的 K/V 状态分布**

- ORCA 支持两类 model parallelism：
  - **intra-layer parallelism**
    - 单层内部的矩阵计算被切分到多个 GPU。
    - 同一层的 K/V state 也会按 partition 存储在对应 GPU。
  - **inter-layer parallelism**
    - 不同 Transformer layers 分配到不同 worker。
    - 每个 worker 只保存自己负责 layers 的 K/V state。
- 在 distributed engine 中：
  - Engine master 将 batch control message 发给第一个 worker。
  - control message 包含 request ids、token index、input length 等。
  - worker controller 将信息传给 GPU-controlling threads。
  - Attention kernel 根据 request id 和 token index 定位本地 K/V memory address。
- 控制面与数据面分离：
  - K/V Manager 的寻址依赖 CPU 可读的 control message。
  - ORCA 使用 gRPC 传递 control message。
  - NCCL 只用于 GPU tensor data transfer。
- 这样避免了现有系统中用 NCCL 传控制信息导致的 CPU-GPU synchronization overhead。

**生命周期示例**

- 假设请求 R 到达：
  - input tokens = 32
  - max_gen_tokens = 128
  - max_tokens = 160
- 请求首次被选中：
  - scheduler 检查 n_rsrv + 160 <= n_slots。
  - 若通过，K/V Manager 为 R 预留 160 个 token slots。
- initiation phase：
  - 一次处理 32 个 input tokens。
  - 每层生成并保存 32 组 K/V。
  - 输出第 1 个 generated token。
- 第 1 次 increment：
  - 输入上一轮 generated token。
  - Attention 读取 R 的 32 组历史 K/V。
  - 追加第 33 个 token 的 K/V。
  - 输出第 2 个 generated token。
- 第 k 次 increment：
  - Attention 读取 R 的前 32+k-1 个 tokens 的 K/V。
  - 追加当前 token 的 K/V。
- 请求达到 max_gen_tokens 或生成 EOS：
  - scheduler 标记 finished(R)。
  - K/V Manager 释放 R 的 160 个 slots。
  - 释放后的 slots 可供新请求使用。

---

**K/V Manager 对 latency 和 throughput 的影响**

- 对 latency 的影响：
  - 通过复用历史 K/V，避免重复处理完整 prefix。
  - 每轮 increment 只需处理一个新 token。
  - 已完成请求可立即释放并返回，不必等待 batch 内其他请求。
- 对 throughput 的影响：
  - 支持 late-joining requests 加入下一轮 iteration。
  - 避免 early-finished requests 继续占用 batch 计算。
  - 让 batch 可以由任意历史长度的请求组成。
  - 提高高负载下 GPU 资源利用率。
- 对 memory 的影响：
  - K/V cache 是长序列生成中主要动态内存占用之一。
  - n_slots 直接决定系统可承载的并发 token 状态规模。
  - 预留 max_tokens 能避免中途分配失败，但可能造成未使用空间。

---

**与 FasterTransformer 类系统的差异**

| 维度 | ORCA K/V Manager | FasterTransformer 典型方式 |
|---|---|---|
| 调度粒度 | **iteration-level** | **request-level** |
| batch 生命周期 | 每个 iteration 可变 | batch 固定直到全部请求完成 |
| K/V 分配 | 按请求 max_tokens 预留 | 常见为按最大序列长度预分配 |
| 请求完成释放 | 完成后由 scheduler 通知释放 | batch 完成后统一返回 |
| 可变长度请求 | 通过 selective batching + per-request K/V 支持 | batch 内处理效率受限 |
| late-joining | 可在下一轮加入 | 需等待当前 batch 结束 |
| early-finished | 可立即返回并释放 | 通常需等待 batch 内最长请求 |

- ORCA 的优势来自调度层和 K/V 管理层协同：
  - 不是单纯优化 Attention kernel。
  - 而是让请求生命周期、K/V memory、iteration scheduling 统一管理。
- FasterTransformer 更适合固定 batch、相似长度请求：
  - 对 heterogeneous generation workloads 效率较低。
  - 容易出现 early-finished request 的无效计算。
  - 新请求等待时间更长。

**潜在实现细节推断**

- K/V Manager 很可能采用预分配 GPU memory pool：
  - 避免每个 iteration 动态 cudaMalloc/cudaFree。
  - 降低 allocator overhead。
  - 减少 memory fragmentation。
- 每个请求维护 slot offset：
  - request_id -> base_slot
  - current token index -> base_slot + token_index
- Attention kernel 通过 metadata 定位：
  - key_ptr = key_pool + offset(request_id, layer_id, token_index, partition_id)
  - value_ptr = value_pool + offset(request_id, layer_id, token_index, partition_id)
- initiation phase 的 input tokens 可连续写入：
  - token index 0 到 input_len-1。
- increment phase 每轮追加一个 token：
  - token index = current_length。
- 释放策略可能是 free-list 或 bitmap：
  - 请求结束后回收连续 slot range。
  - 后续请求可复用空闲 range。
- 若采用固定 max_tokens reservation：
  - 更容易使用连续内存区间。
  - Attention kernel 地址计算更简单。
  - 缺点是短输出请求可能浪费部分预留空间。

**设计权衡**

| 设计选择 | 好处 | 代价 |
|---|---|---|
| **按请求维护 K/V** | 支持任意请求组合；请求隔离清晰 | metadata 管理复杂 |
| **首次调度时预留 max_tokens** | 避免运行中 K/V 空间不足；无 deadlock | 可能造成内存浪费 |
| **Attention 不做严格 batching** | 支持不同 token index；调度灵活 | Attention kernel batching 收益减少 |
| **非 Attention ops 继续 batching** | 保留参数复用和 GPU 利用率 | 需要 Split/Merge |
| **请求完成后释放 K/V** | 降低长期内存占用 | 依赖 scheduler 准确检测 finished |
| **control/data plane 分离** | 减少 CPU-GPU synchronization | 系统实现更复杂 |

**在整体系统中的作用总结**

- **Attention K/V State Manager** 是 ORCA 支撑 autoregressive Transformer serving 的状态核心。
- 它解决的不是单个 Attention kernel 的计算问题，而是以下系统级问题：
  - **历史状态复用**
  - **可变长度请求管理**
  - **iteration-level scheduling 下的动态请求集合**
  - **K/V memory admission control**
  - **请求完成后的及时释放**
  - **distributed model parallelism 下的状态定位**
- 它与 **selective batching** 构成 ORCA 的关键组合：
  - selective batching 允许 batch 中请求形态不一致。
  - K/V Manager 保证每个请求的 Attention 仍然能访问正确历史上下文。
- 它与 **scheduler** 构成内存安全闭环：
  - scheduler 负责预留和释放。
  - K/V Manager 负责存储和寻址。
  - n_slots / n_rsrv / req.max_tokens 共同避免 K/V cache exhaustion。
- 该机制使 ORCA 能在大模型推理中同时获得：
  - **低延迟**
  - **高吞吐**
  - **动态 batch 组合能力**
  - **对 heterogeneous generation workloads 的适应性**

### 4. Distributed Model Parallel Execution

**Distributed Model Parallel Execution 核心定位**

- **Distributed Model Parallel Execution** 是 ORCA 用于支撑 **hundreds of billions of parameters** 级 Transformer-based generative models 的底层执行机制。
- ORCA 面对的核心问题：
  - **模型参数过大**，单张 GPU 无法容纳完整模型。
  - **单次推理需要多轮 autoregressive iterations**，每轮都要经过所有 Transformer layers。
  - **Serving 场景要求低 latency 与高 throughput**，不能简单地将大模型串行放在多 GPU 上执行。
- ORCA 的解决方案是组合两类 Model Parallelism：
  - **intra-layer parallelism**
    - 在单个 Transformer layer 内部切分矩阵计算和参数。
    - 主要作用是让单层中的大规模 Linear、Attention 相关矩阵计算分布到多个 GPU 上。
  - **inter-layer parallelism**
    - 在 Transformer layers 之间切分模型。
    - 每个 worker 负责一段连续的 layers。
    - 主要作用是将完整模型的层堆栈分布到多个 GPU 或多台机器上。
- 两者组合后，ORCA 可以构建二维并行结构：
  - **横向切层内计算**：多个 GPU 协同执行同一层。
  - **纵向切层间堆栈**：不同 worker 负责不同层段。
  - 形成适合 GPT-3 级模型 serving 的分布式执行拓扑。

---

**模型并行结构**

![](8ea2f728df36f05ba6d1b8c302f0f68cbbe7c0dfbaa91478de5582ea6b7b6771.jpg) *Figure 6: An example of intra- and inter- layer parallelism. A vertical dotted line indicates partitioning between layers and a horizontal line indicates partitioning within a layer.*

- 图中展示的是 ORCA 使用的两级并行方式：
  - **horizontal partitioning**
    - 对应 **intra-layer parallelism**。
    - 将单个 layer 内部的大矩阵计算拆分到多个 GPU。
  - **vertical partitioning**
    - 对应 **inter-layer parallelism**。
    - 将多个 Transformer layers 按连续层段切分到不同 worker。
- 示例配置：
  - 模型有 **4 个 Transformer layers**。
  - 被划分为 **2 个 inter-layer partitions**。
  - 每个 inter-layer partition 内部又被划分为 **3 个 intra-layer partitions**。
  - 总 GPU 数为：
    - **2 × 3 = 6 GPUs**。
- 执行含义：
  - Worker1 负责前两个 layers。
  - Worker2 负责后两个 layers。
  - 每个 worker 内部有 3 个 GPU，共同执行该 worker 所持有 layers 的层内计算。

---

**intra-layer parallelism 的实现原理**

- **intra-layer parallelism** 作用于单个 Transformer layer 内部。
- 主要切分对象：
  - **Linear operations**
    - 例如 QKV Linear、Attention Out Linear、MLP 中的全连接矩阵。
  - **Attention-related matrix multiplications**
    - Attention 中的 query、key、value 相关计算。
  - **associated parameters**
    - 与上述矩阵计算对应的模型参数也被切分到多个 GPU。
- 核心目标：
  - 降低单 GPU 的参数存储压力。
  - 将大型矩阵乘法拆成多个子矩阵计算并行执行。
  - 提升单层计算吞吐。
- ORCA 采用的思想与 Megatron-LM、Mesh-TensorFlow 等训练系统类似：
  - 对大矩阵进行按维度切分。
  - 每个 GPU 保存参数的一部分。
  - 每个 GPU 执行局部矩阵乘法。
  - 必要时通过 **NCCL** 做跨 GPU collective communication，例如 all-reduce、all-gather 或 reduce-scatter 类型通信。
- 对 Transformer layer 的影响：
  - 从外部看，一个 layer 仍然接收完整 hidden states，输出完整 hidden states。
  - 从内部看，矩阵计算和参数存储已经分布在多个 GPU 上。
- 对 ORCA serving 的意义：
  - 支撑 **101B、175B、341B** 这类单 GPU 无法容纳的模型。
  - 让每个 layer 的计算能够利用一组 GPU 的合计算力和显存。

---

**inter-layer parallelism 的实现原理**

- **inter-layer parallelism** 作用于 Transformer layer stack。
- 切分方式：
  - 将完整模型的 layers 按顺序划分为多个连续区间。
  - 每个区间称为一个 **inter-layer partition**。
  - 每个 partition 分配给一个 **worker process**。
- ORCA 的设计：
  - 每个 worker 负责一段连续 Transformer layers。
  - 每个 worker 可以位于不同机器。
  - 每个 worker 内部控制一个或多个 GPU。
  - worker 内部 GPU 数量由 **intra-layer parallelism degree** 决定。
- 执行方式：
  - 输入 tokens 先进入第一个 worker。
  - 第一个 worker 执行自己负责的 layers。
  - 中间 hidden activations 通过 GPU-to-GPU data plane 传给下一个 worker。
  - 最后一个 worker 产生 logits 并解码出 output token。
- 对外表现：
  - 一个 iteration 仍然是“完整跑过所有 layers 并生成一个 token”。
  - 内部执行被拆成多个 worker 的流水式分布式计算。
- 作用：
  - 分摊模型参数。
  - 支撑超大层数模型。
  - 通过 pipeline execution 减少 worker idle time。

**ORCA 分布式执行架构**

![](e26cdf4e4361d4662eebb26fffdbb4b80c7a96cb3d8be2a0302a733054b7f7b4.jpg) *Figure 7: An illustration of the distributed architecture of ORCA’s execution engine using the parallelization configuration shown in Figure 6. For example, the first inter-layer partition (Layer1 and Layer2) in Figure 6 is assigned to Worker1, while the second partition is assigned to Worker2.*

- ORCA execution engine 的主要组件：
  - **Engine Master**
    - 接收 scheduler 发来的 batch execution request。
    - 将当前 iteration 的 tokens 和 control message 发给第一个 worker。
    - 从最后一个 worker 接收 output tokens。
  - **Worker Controller**
    - 每个 worker process 内部的控制逻辑。
    - 解析 request ids、token index、input length 等 control metadata。
    - 向本 worker 内的 GPU-controlling threads 下发执行指令。
    - 将 control message 转发给下一个 worker。
  - **GPU-controlling Threads**
    - 每个线程通常绑定一个 GPU。
    - 负责发起 CUDA kernels。
    - 处理对应 intra-layer partition 的计算。
  - **Attention K/V Manager**
    - 管理每个 request 的 Attention keys 和 values。
    - 负责为 increment phase 的 Attention 提供历史 K/V states。
  - **NCCL Data Plane**
    - 用于传输 GPU 产生和消费的 tensor data。
    - 包括 intra-layer GPU 间通信与 inter-layer worker 间 intermediate activations 传输。
  - **gRPC Control Plane**
    - 用于传输 CPU 需要解析的 control messages。
    - 不经过 GPU，避免不必要的 CPU-GPU synchronization。

---

**输入输出关系**

- ORCA engine 每次被 scheduler 调用时，处理的是一个 **iteration-level batch**。
- 输入包括两类信息：
  - **token inputs**
    - 对于 initiation phase request：
      - 输入是 client 提供的完整 input tokens。
      - 例如请求首次进入模型时，可能输入多个 tokens。
    - 对于 increment phase request：
      - 输入是上一个 iteration 生成的单个 token。
  - **control message**
    - 包含每个 request 的元数据：
      - **request id**
      - **current token index**
      - **number of input tokens**
      - request 当前处于 **initiation phase** 或 **increment phase**
      - batch 内 request 的排列信息
- 输出：
  - 每个 scheduled request 生成一个 output token。
  - 最后一个 worker 将 output tokens 返回给 Engine Master。
  - Engine Master 再返回给 scheduler。
- 输出被用于：
  - 更新 request pool 中对应 request 的 token sequence。
  - 判断 request 是否完成。
  - 若未完成，则该 token 会作为下一轮 increment phase 的输入。
  - 若完成，则释放其 K/V cache 资源，并向 client 返回结果。

---

**单次 iteration 的分布式执行流程**

- Scheduler 选择一个 batch。
  - batch 中可以包含不同状态的 requests。
  - 可能同时包含 initiation phase 和 increment phase requests。
  - 由于 **selective batching**，这些 request 可以在同一个 iteration 内被处理。
- Engine Master 接收 batch execution request。
  - 接收当前 tokens。
  - 接收 control message。
  - 将信息发给第一个 worker。
- Worker1 controller 接收信息。
  - 将 control message 转交给 GPU-controlling threads。
  - GPU threads 解析 metadata。
  - GPU threads 发起对应 CUDA kernels。
- Worker1 执行自己负责的 inter-layer partition。
  - 层内矩阵计算由 intra-layer GPUs 并行执行。
  - Attention 操作根据 request id 和 token index 访问 Attention K/V Manager。
  - 生成本 partition 的 output activations。
- Worker1 将 intermediate tensor data 发送给 Worker2。
  - tensor data 通过 **NCCL** 发送。
  - 该数据由 GPU 产生，并由下一个 worker 的 GPU 消费。
- Worker1 controller 同时转发 control message。
  - control message 通过 **gRPC** 或类似 CPU channel 转发。
  - 不等待 GPU kernels 完全结束即可转发 control metadata。
- 后续 worker 重复该流程。
  - 每个 worker 执行自己负责的 layers。
  - 每个 worker 内部继续使用 intra-layer parallelism。
- 最后一个 worker 完成最后一段 layers。
  - 计算最终 logits。
  - 生成 output token。
  - 同步 GPU kernels。
  - 将 output token 返回给 Engine Master。
- Engine Master 将 tokens 返回给 scheduler。
  - scheduler 更新 request pool。
  - 完成请求被移除。
  - 未完成请求进入下一轮调度。

---

**控制平面与数据平面分离**

- ORCA 的重要设计是 **control-data plane separation**。
- 数据平面：
  - 传输对象：
    - hidden states
    - intermediate activations
    - intra-layer partition 之间的 tensor results
  - 通信工具：
    - **NCCL**
  - 原因：
    - tensor data 由 GPU 产生，也由 GPU 消费。
    - NCCL 适合 GPU-to-GPU 高带宽通信。
- 控制平面：
  - 传输对象：
    - request ids
    - current token index
    - input length
    - batch layout
    - scheduling metadata
  - 通信工具：
    - **gRPC**
    - 或其他不涉及 GPU 的 CPU-side communication channel。
  - 原因：
    - control message 由 CPU 解析，用于发起 GPU kernels。
    - 如果通过 NCCL 传 control message，会引入 GPU-to-CPU synchronization。
- 与 FasterTransformer 等系统的差异：
  - FasterTransformer、Megatron-LM 类系统常通过 NCCL 交换 control messages。
  - CPU 需要使用这些 metadata 时会触发 CPU-GPU synchronization。
  - ORCA 避免让 CPU 需要的数据走 GPU channel。
- 性能收益：
  - 减少每个 iteration 中的同步开销。
  - 对 autoregressive serving 尤其关键，因为每个 request 需要多次 iterations。
  - 在 175B 模型 microbenchmark 中，ORCA engine 在禁用 pipeline 后仍比 FasterTransformer 快，论文将其主要归因于该设计。

---

**Pipeline execution across workers**

![](e26cdf4e4361d4662eebb26fffdbb4b80c7a96cb3d8be2a0302a733054b7f7b4.jpg) *Figure 7: An illustration of the distributed architecture of ORCA’s execution engine using the parallelization configuration shown in Figure 6. For example, the first inter-layer partition (Layer1 and Layer2) in Figure 6 is assigned to Worker1, while the second partition is assigned to Worker2.*

- ORCA 不只是将模型拆到多个 worker，还让不同 batch 在不同 worker 上形成 pipeline。
- Pipeline 的基本思想：
  - Worker1 处理 batch A 时，Worker2 可能处理前一个 batch。
  - Worker3 可能处理更早的 batch。
  - 多个 inter-layer partitions 同时工作，减少空闲。
- ORCA 的 scheduler 支持在前一个 batch 尚未完全返回时继续注入新 batch。
- Scheduler 维护：
  - **n_workers**
    - inter-layer workers 的数量。
  - **n_scheduled**
    - 当前已经注入但尚未完全返回的 batch 数。
- 调度逻辑：
  - 当 **n_scheduled < n_workers** 时，scheduler 可以继续向 engine 注入 batch。
  - 当 **n_scheduled = n_workers** 时，scheduler 等待一个 batch 返回。
  - 这样保证 pipeline 中最多保持 **n_workers** 个 in-flight batches。
- 好处：
  - 每个 worker 尽量都有 batch 可处理。
  - pipeline bubbles 减少。
  - 不需要像 FasterTransformer 那样将一个 request-level batch 拆成 microbatches。
- 与 FasterTransformer 的差异：
  - FasterTransformer 在 request-level scheduling 下，通常只能等当前 batch 完成后再注入下一批。
  - 为了利用 pipeline，需要把一个 batch 切成 microbatches。
  - microbatch 太小会降低 batching efficiency。
  - microbatch 太大会产生 pipeline bubbles。
  - ORCA 通过 iteration-level scheduling 直接在 batch 之间做 pipeline，避免该 trade-off。

---

**ORCA 与 FasterTransformer 的 pipeline 差异**

![](42ca3b07156dec83a381e598fcdb19c367cf67f49ca539836ca86266a34e8d76.jpg)

- ORCA 的 pipeline 特征：
  - pipeline 单位是 **iteration-level batch**。
  - scheduler 可以连续注入多个 batches。
  - 不需要将 batch 拆成 microbatch。
  - 每个 batch 仍保留较大的 batch size，维持 batching efficiency。
- FasterTransformer 的 pipeline 特征：
  - pipeline 单位通常是 **microbatch**。
  - 一个 request-level batch 被拆成多个 microbatches。
  - pipeline utilization 依赖 microbatch size。
  - 存在 batching efficiency 与 pipeline efficiency 的权衡。
- ORCA 更适合 generative serving 的原因：
  - 每个 request 有多次 iterations。
  - batch 成员会随 iteration 改变。
  - late-joining request 可以在下一轮 iteration 进入 pipeline。
  - early-finished request 可以及时退出。

**参数设置与实验配置**

- ORCA 的分布式执行参数主要包括：
  - **Inter-layer partitions**
    - 表示 Transformer layers 被切成多少段。
    - 也基本对应 worker 数。
  - **Intra-layer partitions**
    - 表示每个 layer 内部计算被切成多少份。
    - 对应每个 worker 内参与同一层计算的 GPU 数。
  - **Total GPUs**
    - 计算方式通常为：
      - **Inter-layer partitions × # Intra-layer partitions**
  - **max batch size**
    - 由 scheduler 使用。
    - 控制每次 iteration 最多处理多少 requests。
  - **n_slots**
    - Attention K/V Manager 可用的 K/V cache slots 数。
    - 约束同一时间可保留的 request token states。
- 论文实验中的模型配置如下：

|---:|---:|---:|---:|---:|---:|
| **13B** | 40 | 5120 | 1 | 1 | 1 |
| **101B** | 80 | 10240 | 1 | 8 | 8 |
| **175B** | 96 | 12288 | 2 | 8 | 16 |
| **341B** | 120 | 15360 | 4 | 8 | 32 |

- 配置解释：
  - **13B**
    - 单 GPU 可容纳。
    - 不需要模型分布式并行。
  - **101B**
    - 使用 8-way intra-layer parallelism。
    - 没有 inter-layer split。
    - 所有 layers 都在一个 inter-layer partition 中，但每层内部跨 8 GPUs。
  - **175B**
    - 使用 2 个 inter-layer partitions。
    - 每个 partition 内部使用 8-way intra-layer parallelism。
    - 总共 16 GPUs。
  - **341B**
    - 使用 4 个 inter-layer partitions。
    - 每个 partition 内部使用 8-way intra-layer parallelism。
    - 总共 32 GPUs。

---

**Worker 与 GPU 映射关系**

- 以 **175B** 配置为例：
  - Inter-layer partitions = **2**
  - Intra-layer partitions = **8**
  - 总 GPU 数 = **16**
- 映射方式：
  - Worker1：
    - 持有前半部分 Transformer layers。
    - 内部使用 8 GPUs 进行 intra-layer parallelism。
  - Worker2：
    - 持有后半部分 Transformer layers。
    - 内部使用 8 GPUs 进行 intra-layer parallelism。
- 在 Azure ND96asr A100 v4 VM 环境中：
  - 每台 VM 有 8 张 A100 GPUs。
  - 175B 模型可自然映射为：
    - 一台 VM 对应一个 inter-layer partition。
    - 每台 VM 内 8 GPUs 做 intra-layer parallelism。
- 对 **341B**：
  - 4 个 inter-layer partitions。
  - 每个 partition 使用 8 GPUs。
  - 通常需要 4 台 VM。
- 这种映射减少跨机器通信：
  - intra-layer communication 主要发生在单 VM 内部，通过 NVLink。
  - inter-layer communication 发生在 worker 间，通过高速 Infiniband 和 NCCL。

**与 iteration-level scheduling 的关系**

- Distributed Model Parallel Execution 是 ORCA engine 层能力。
- iteration-level scheduling 是 ORCA scheduler 层能力。
- 二者协同方式：
  - scheduler 每次选择一个 batch。
  - engine 只执行该 batch 的一个 iteration。
  - 该 iteration 在分布式模型并行拓扑上完整经过所有 layers。
- 输入输出闭环：
  - scheduler 输入 batch tokens 到 engine。
  - engine 分布式执行完整模型。
  - engine 输出每个 request 的 next token。
  - scheduler 更新 request pool，并决定下一轮 batch。
- 分布式执行必须支持频繁 iteration 调用：
  - 每个 request 可能需要数十到数百 iterations。
  - 每个 iteration 都涉及 worker 间通信和 GPU kernel launching。
  - 因此控制平面低开销、pipeline 保持满载非常关键。

---

**与 selective batching 的关系**

- selective batching 使 scheduler 能够构造任意 request 组合的 batch。
- Distributed Model Parallel Execution 必须能够执行这种 irregular batch。
- 在每个 worker 内部：
  - 非 Attention operations 使用 flattened token-wise batching。
  - Attention operation 按 request 拆分执行。
  - split 后的 Attention outputs 再 merge 回统一 tensor。
- 在分布式模型并行中：
  - 每个 inter-layer partition 都按相同 batch layout 执行。
  - control message 保证每个 worker 知道 batch 中每个 request 的 token index 和状态。
  - Attention K/V Manager 在每个相关 GPU 上维护本 partition 对应的 K/V states。
- 作用：
  - 分布式执行不仅支持大模型，还支持 ORCA 的动态 batch 语义。
  - 不要求 batch 内 requests 具有相同 input length 或相同 generated token index。

---

**Attention K/V Manager 在分布式执行中的作用**

- Transformer autoregressive inference 需要保存历史 **Attention keys/values**。
- 在分布式模型并行下，K/V states 也随模型切分分布在 GPU 上。
- 每个 worker 或 GPU 只维护自己负责部分所需的 K/V cache。
- K/V Manager 的职责：
  - 根据 request id 查找对应 K/V cache。
  - 根据 current token index 定位历史 token states。
  - 为 Attention kernel 提供 previous keys 和 previous values。
  - 在 request 完成时释放对应 K/V slots。
- 与 scheduler 参数的关系：
  - scheduler 使用 **n_slots** 控制可用 K/V cache 容量。
  - 对首次调度的 request，scheduler 根据 **max_tokens** 预留足够 slots。
  - 防止运行到中途 K/V cache 不足导致 deadlock。
- 分布式执行中的关键点：
  - K/V cache 不需要跨 worker 统一集中存储。
  - 每个 worker 保存自己 layers 对应的 K/V。
  - request id 和 token index 通过 control plane 分发，确保所有 worker 一致访问对应 state。

---

**算法流程中的分布式执行关键变量**

| 参数或变量 | 所属层级 | 含义 | 对 Distributed Execution 的影响 |
|---|---|---|---|
| **n_workers** | Scheduler / Engine | inter-layer workers 数量 | 决定 pipeline 中最多 in-flight batches 数 |
| **n_scheduled** | Scheduler | 已注入但未返回的 batches 数 | 控制是否继续注入 batch 或等待返回 |
| **max_bs** | Scheduler | 每个 iteration batch 的最大 request 数 | 影响 GPU utilization、latency、throughput |
| **n_slots** | Scheduler / K/V Manager | 可用于 K/V cache 的 token slots 数 | 限制并发 request 和最大 token state 存储 |
| **request id** | Control message | request 唯一标识 | 用于 K/V cache 查找与 request 状态更新 |
| **current token index** | Control message | 当前处理 token 的位置 | 用于 Attention 访问历史 K/V |
| **input length** | Control message | initiation phase 的输入长度 | 用于处理不同长度输入与 selective batching |

---

**调度与 pipeline 的算法关系**

- ORCA scheduler 的核心行为：
  - 从 request pool 中选择最多 **max_bs** 个 requests。
  - 将 batch 注入 engine。
  - 不立即等待返回，除非 pipeline 已满。
- pipeline 控制逻辑：
  - 如果 **n_scheduled < n_workers**：
    - 继续选择新 batch。
    - 继续注入 engine。
  - 如果 **n_scheduled = n_workers**：
    - 等待最早完成的 batch 返回。
    - 更新 request states。
    - 释放完成 request 的 K/V reservation。
- 对 inter-layer parallelism 的意义：
  - worker 数越多，pipeline 深度越大。
  - scheduler 保持最多 n_workers 个 batch 在 engine 中流动。
  - 每个 worker 同时处理不同 batch 的不同 layer segment。
- 对 latency 的影响：
  - pipeline 不改变单个 iteration 必须经过所有 layers 的依赖。
  - 但减少整体系统空闲，提高吞吐。
  - 在负载较高时，吞吐提升明显。

---

**性能结果中的分布式执行影响**

- engine microbenchmark 中：
  - 13B 和 101B 场景下，ORCA engine 与 FasterTransformer 性能接近。
  - 175B 场景下，ORCA engine 在禁用 pipeline 后仍最多快 **47%**。
- 论文解释：
  - 175B 使用 inter-layer partitions。
  - ORCA 的 **control-data plane separation** 减少了跨 worker 控制消息引发的同步开销。
- end-to-end serving 中：
  - ORCA 在 175B 和 341B 上优势更明显。
  - 原因包括：
    - iteration-level scheduling 支持 late-joining 和 early-leaving。
    - selective batching 提高动态 batch 的可执行性。
    - distributed pipeline 保持 workers 忙碌。
    - 避免 FasterTransformer microbatch pipeline 的效率权衡。
- 关键实验结果：
  - 在 175B 模型上，匹配约 **190ms median normalized latency** 时：
    - FasterTransformer throughput 为 **0.185 req/s**。
    - ORCA throughput 为 **6.81 req/s**。
    - ORCA 达到 **36.9× throughput improvement**。

| 模型 | 对比条件 | FasterTransformer | ORCA | 改善 |
|---|---:|---:|---:|---:|
| **175B** | 相近 median normalized latency ≈ 190ms | 0.185 req/s | 6.81 req/s | **36.9× throughput** |
| **175B engine microbenchmark** | 禁用 pipeline | baseline | up to 47% faster | **control-data plane separation 收益** |

---

**为什么 ORCA 的分布式执行更适合 Generative Models**

- Generative serving 的特殊性：
  - 每个 request 不是一次性执行完成。
  - 每个 output token 都需要一次 iteration。
  - 不同 request 的 input length 和 output length 差异很大。
  - batch 内 request 会不断完成或加入。
- 传统 request-level serving 的问题：
  - batch 固定到所有 request 完成。
  - early-finished request 不能立刻返回。
  - late-arriving request 需要等整个 batch 完成。
  - pipeline 依赖 microbatch，牺牲 batching efficiency。
- ORCA 的分布式执行与调度共同解决：
  - 每个 iteration 都可重新组 batch。
  - 任意 request 组合可通过 selective batching 执行。
  - 大模型通过 intra-layer 和 inter-layer parallelism 分布执行。
  - inter-layer workers 通过 pipeline 持续工作。
  - control messages 不走 GPU data channel，减少频繁 iteration 的同步成本。

**实现细节总结**

- ORCA 使用 **C++ + CUDA ecosystem** 实现。
- 通信组件：
  - **gRPC**
    - control plane。
    - 传 request metadata 和调度控制信息。
  - **NCCL**
    - data plane。
    - 传 GPU tensor data。
- GPU kernel 优化：
  - fused **LayerNorm** kernel。
  - fused **Attention** kernel。
  - fused **GeLU** kernel。
  - 对 split Attention operators 进一步融合：
    - 将不同 requests 的 Attention kernels 的 thread blocks 拼接成一个 CUDA kernel。
    - 降低 kernel launch overhead。
    - 提升 GPU utilization。
- 分布式拓扑：
  - worker process 对应 inter-layer partition。
  - worker 内多个 GPU 对应 intra-layer partitions。
  - controller 负责 CPU-side scheduling 和 kernel issuing。
  - GPU threads 负责具体 CUDA execution。
- 执行接口：
  - 输入一个 iteration-level batch。
  - 输出每个 request 的一个 generated token。
  - 与 scheduler 形成 token-by-token serving loop。

### 5. Control/Data Plane Separation

**Control/Data Plane Separation核心定位**

- **Control/Data Plane Separation**是ORCA分布式执行引擎中的关键系统设计，用于降低大模型推理中跨Worker通信带来的同步开销。
- ORCA将分布式推理通信拆成两类路径：
  - **Control Plane**
    - 传递CPU侧调度与执行控制信息。
    - 使用**gRPC**等不经过GPU的数据通道。
    - 典型内容包括**request ID**、**token index**、**input token数量**、请求状态、batch组成等。
  - **Data Plane**
    - 传递GPU侧计算产生和消费的中间张量。
    - 使用**NCCL**进行GPU-to-GPU通信。
    - 典型内容包括Transformer层之间、intra-layer partition之间、inter-layer partition之间的**intermediate activation tensor**。

![](e26cdf4e4361d4662eebb26fffdbb4b80c7a96cb3d8be2a0302a733054b7f7b4.jpg) *Figure 7: An illustration of the distributed architecture of ORCA’s execution engine using the parallelization configuration shown in Figure 6. For example, the first inter-layer partition (Layer1 and Layer2) in Figure 6 is assigned to Worker1, while the second partition is assigned to Worker2.*

---

**为什么需要分离Control Plane和Data Plane**

- 传统分布式Transformer推理系统的问题：
  - FasterTransformer、Megatron-LM等系统通常使用**NCCL**同时传输：
    - GPU中间张量。
    - CPU需要解析的控制消息。
  - 控制消息虽然体积很小，但如果通过GPU通信路径传递，会引入额外的**CPU-GPU synchronization**。
  - 每个iteration都需要交换控制消息，因此同步开销会在autoregressive generation中被不断放大。
- GPT类生成模型的推理特征使该问题更严重：
  - 每个请求需要执行多个iteration。
  - 每个iteration只生成一个token。
  - ORCA采用**iteration-level scheduling**后，scheduler和engine在每个iteration都有交互。
  - 控制消息频率极高，若每次都触发CPU-GPU同步，会显著影响吞吐和延迟。
- ORCA的核心判断：
  - **控制消息由CPU消费，不应走GPU通信路径**。
  - **中间张量由GPU消费，应继续走NCCL高速路径**。
  - 控制路径与数据路径解耦，可以避免“小控制消息拖慢大规模GPU流水线”。

---

**Control Plane传递什么**

| 控制信息 | 含义 | 消费方 | 作用 |
|---|---|---|---|
| **request ID** | 请求唯一标识 | Worker controller、GPU-controlling thread | 定位对应请求的K/V cache |
| **token index** | 当前处理到第几个token | Attention kernel、K/V manager | 获取历史Attention keys/values地址 |
| **input token数量** | initiation phase输入长度 | Worker controller、kernel launcher | 确定当前请求的输入tensor shape |
| **batch组成** | 当前iteration选择了哪些请求 | 所有Worker | 保证分布式Worker处理同一个iteration batch |
| **phase状态** | INITIATION或INCREMENT | Scheduler、Worker | 决定输入是完整prompt还是单个新token |
| **max_tokens或reserved slots信息** | 请求最大token预算 | Scheduler、K/V manager | 避免K/V cache内存分配死锁 |

- **request ID**是ORCA选择性批处理中的关键索引：
  - Attention K/V manager按请求维护历史key/value。
  - Attention kernel需要通过request ID找到对应请求的K/V cache区域。
- **token index**决定当前Attention需要访问多少历史tokens：
  - increment phase中，当前token需要attend到所有之前tokens。
  - 不同请求的token index可能不同，因此Attention无法简单做统一batch。
- **input token数量**用于处理initiation phase：
  - 新请求第一次进入系统时，可能有不同prompt长度。
  - Worker需要知道每个请求的输入长度，才能正确split和merge flattened token tensor。

---

**Data Plane传递什么**

| 数据类型 | 所在位置 | 通信方式 | 作用 |
|---|---|---|---|
| **intermediate tensor** | GPU memory | **NCCL** | 在不同Worker或GPU partition之间传递激活 |
| **intra-layer partial result** | GPU memory | **NCCL AllReduce/Collective** | 合并intra-layer parallelism中的矩阵计算结果 |
| **inter-layer activation** | GPU memory | **NCCL Send/Recv或等价通信** | 将上一组Transformer layers输出传给下一组layers |
| **模型参数** | GPU memory | 通常预加载，不频繁传输 | 执行Linear、MLP等算子 |
| **Attention K/V cache** | GPU memory | 本地访问为主 | 保存每个请求的历史key/value |

- Data Plane只处理GPU计算真正需要的张量。
- NCCL适合大规模GPU张量通信：
  - 利用NVLink、InfiniBand等高速互连。
  - 支持GPU直接通信。
  - 避免中间张量绕回CPU。
- ORCA保留NCCL用于Data Plane，是因为：
  - Tensor数据量大。
  - Tensor生产者和消费者都是GPU。
  - 走CPU路径会严重降低带宽并增加延迟。

---

**实现原理**

- ORCA执行引擎由一个**engine master**和多个**worker processes**组成。
- 每个Worker负责一个**inter-layer partition**：
  - 例如175B模型可分为2个inter-layer partitions。
  - 每个partition内部再通过**intra-layer parallelism**切到多个GPU。
- 每个Worker内部包含：
  - **controller**
    - CPU侧组件。
    - 接收gRPC控制消息。
    - 解析batch信息。
    - 将控制信息交给GPU-controlling threads。
  - **GPU-controlling threads**
    - 每个thread通常绑定一个GPU。
    - 根据控制消息launch CUDA kernels。
    - 为Attention kernel准备K/V cache地址。
  - **Attention K/V manager**
    - 维护每个请求的历史key/value。
    - 根据request ID和token index返回对应GPU memory地址。
  - **NCCL communication module**
    - 只负责GPU中间tensor通信。
    - 不承担CPU控制消息传递。

---

**算法流程：一次iteration的分布式执行**

- Scheduler选择batch：
  - 从request pool中选择最多**max_bs**个请求。
  - batch可以包含不同状态请求：
    - initiation phase请求。
    - increment phase请求。
    - 不同token index的请求。
    - 不同prompt长度的请求。
- Engine master接收batch：
  - 接收当前iteration要执行的请求集合。
  - 构造控制消息：
    - request IDs。
    - 每个请求当前token index。
    - 每个请求输入token数量。
    - 请求phase。
  - 将输入tokens和控制消息发送给第一个Worker。
- Worker1处理：
  - controller通过**gRPC**收到控制消息。
  - controller将控制信息传给GPU-controlling threads。
  - GPU-controlling threads解析控制信息并launch kernels。
  - 对非Attention算子执行selective batching。
  - 对Attention算子按请求split后分别执行。
  - 中间tensor通过**NCCL**传给下一个Worker。
  - control message通过**gRPC**提前转发给Worker2。
- Worker2及后续Worker处理：
  - controller无需等待Worker1 GPU kernels完全结束即可接收控制消息。
  - GPU侧等待NCCL数据到达后继续执行对应layers。
  - control message继续沿Control Plane传递。
- 最后一个Worker处理：
  - 执行最后一组Transformer layers。
  - 同步GPU kernel完成。
  - 取回每个请求生成的output token。
  - 将output tokens返回engine master。
- Scheduler更新request pool：
  - 将生成token追加到对应请求。
  - 若生成结束或达到max_gen_tokens，则请求完成。
  - 释放该请求占用的K/V slots。
  - 下一iteration重新选择batch。

---

**输入输出关系**

| 模块 | 输入 | 输出 | 说明 |
|---|---|---|---|
| **Scheduler** | request pool、max_bs、K/V slots状态 | 当前iteration batch | 决定哪些请求进入下一次模型执行 |
| **Engine master** | batch、tokens、请求元信息 | 发往Worker1的control message和tokens | 连接调度层与执行层 |
| **Worker controller** | gRPC控制消息 | kernel launch参数、转发给下一Worker的控制消息 | CPU侧解析和分发 |
| **GPU-controlling thread** | request ID、token index、tensor pointer | CUDA kernel执行 | 驱动GPU完成算子 |
| **Attention K/V manager** | request ID、token index | K/V cache地址 | 支持incremental decoding |
| **NCCL Data Plane** | GPU intermediate tensor | 下一partition输入tensor | 只传输GPU张量 |
| **最后Worker** | 最后一层hidden states | output token | 返回每个请求的新token |

---

**与整体ORCA架构的关系**

- **iteration-level scheduling**要求每个iteration都重新调度：
  - Scheduler每轮都可能改变batch成员。
  - 请求可以late-join。
  - 请求可以early-leave。
- **selective batching**要求执行引擎理解请求级元信息：
  - 非Attention算子可以flatten token后batch执行。
  - Attention算子需要按请求访问不同长度的K/V cache。
  - 因此每个Worker必须知道request ID、token index、input length等控制信息。
- **Control/Data Plane Separation**使上述两项机制可扩展：
  - 控制消息高频但小。
  - 中间tensor低频相对更大但必须高速。
  - 分离后避免高频控制消息污染NCCL数据路径。
- 在多Worker流水线中作用更明显：
  - 控制消息可以提前转发。
  - GPU无需为CPU读取控制消息而停顿。
  - Worker之间可以形成更平滑的pipeline。

---

**与FasterTransformer通信方式的关键差异**

| 维度 | ORCA | FasterTransformer等传统方式 |
|---|---|---|
| 控制消息通道 | **gRPC等CPU网络通道** | 常与GPU通信路径绑定 |
| Tensor数据通道 | **NCCL** | **NCCL** |
| NCCL用途 | 仅传输GPU中间张量 | 可能同时承载控制相关数据 |
| CPU-GPU同步 | 控制消息不触发额外GPU同步 | 控制消息可能引发CPU-GPU同步 |
| Scheduler粒度 | **iteration-level** | request-level |
| Batch变化频率 | 每个iteration可变化 | 一个batch执行完前固定 |
| 对pipeline支持 | 可跨batch自然pipeline | 依赖microbatch pipeline |
| 对大模型多Worker支持 | 控制与数据解耦，扩展性更好 | 控制同步开销更明显 |

---

**参数设置与工程含义**

- **n_workers**
  - 表示inter-layer partitions数量。
  - ORCA scheduler保持最多**n_workers**个batch在pipeline中并发运行。
  - Control Plane需要将每个batch的控制消息依次传递到对应Workers。
- **max_bs**
  - 每个iteration最多调度的请求数。
  - max_bs越大，非Attention算子的batch效率越高。
  - max_bs过大可能增加单iteration延迟。
  - Control Plane消息大小随batch size增长，但通常远小于tensor数据。
- **n_slots**
  - Attention K/V manager预留的K/V cache容量。
  - 以slot为单位，一个slot表示单个token的key/value存储空间。
  - Scheduler在请求首次调度时根据max_tokens预留slots。
  - 避免执行到中途因K/V cache不足而死锁。
- **token index**
  - Attention访问历史K/V cache的关键参数。
  - 不同请求token index不同是Transformer生成推理无法普通batch Attention的根源。
- **request ID**
  - K/V cache寻址的主键。
  - 也是Control Plane中最核心的字段之一。

---

**性能影响**

| 性能维度 | Control/Data Plane Separation带来的效果 |
|---|---|
| **CPU-GPU synchronization** | 减少控制消息导致的同步 |
| **GPU utilization** | GPU更少等待CPU解析控制信息 |
| **pipeline efficiency** | 控制消息可提前传递，Worker更容易保持忙碌 |
| **latency** | 降低每iteration固定开销 |
| **throughput** | 在多Worker大模型上提升明显 |
| **scalability** | 更适合175B、341B等跨多GPU/多机器模型 |

- 论文中175B模型microbenchmark显示：
  - ORCA engine在禁用pipeline的情况下仍可比FasterTransformer快最高约**47%**。
  - 作者将该提升主要归因于**control-data plane separation**。
- 原因并不是ORCA的Attention batching更强：
  - ORCA实际上不batch Attention。
  - FasterTransformer会batch Attention。
  - ORCA仍更快，说明通信和同步路径优化在大模型分布式推理中非常关键。

---

**为什么控制消息不能简单放进NCCL**

- NCCL面向GPU collective communication设计：
  - 最适合大tensor。
  - 数据生产者和消费者通常都是GPU。
- 控制消息的消费者是CPU：
  - CPU需要解析request ID、token index、batch metadata。
  - 如果控制消息经GPU路径传输，CPU最终仍要读取这些信息。
  - 这会引入GPU到CPU可见性同步、stream同步或类似等待。
- 控制消息体积很小：
  - 使用NCCL传递小消息并不划算。
  - 固定开销和同步成本可能超过消息传输本身。
- Autoregressive inference放大固定开销：
  - 每个token一次iteration。
  - 每个iteration一次控制交互。
  - 几十到上百个generated tokens会产生大量重复控制通信。

---

**在Selective Batching中的具体作用**

- Selective batching要求每个Worker准确知道每个请求的结构：
  - 哪些tokens属于哪个request。
  - 每个request当前处于initiation还是increment phase。
  - 每个request需要访问多长的历史K/V。
- Control Plane提供这些元信息：
  - 非Attention算子可将所有tokens flatten成形如**[ΣL,H]**的tensor。
  - Attention前通过Split按request拆开。
  - Attention后通过Merge重新合并。
- Data Plane只传递合并后的中间activation：
  - 不需要把request metadata混入activation tensor。
  - Tensor流保持纯GPU计算数据。
- 这种设计降低了执行引擎复杂度：
  - CPU处理调度语义。
  - GPU处理数值计算。
  - NCCL处理大张量搬运。

---

**在Pipeline Parallelism中的具体作用**

- ORCA的pipeline不是通过把一个batch切成microbatch实现。
- ORCA通过iteration-level scheduling连续注入多个batch：
  - Worker1处理batch AB。
  - Worker2处理batch AB时，Worker1可以处理batch CD。
  - Worker3处理batch AB时，Worker2处理batch CD，Worker1处理batch EF。
- Control Plane Separation的价值：
  - 下游Worker可以提前收到控制消息。
  - Worker controller可以提前准备kernel launch参数。
  - GPU侧只需等待Data Plane的activation tensor到达。
- 如果控制消息也依赖NCCL：
  - 下游Worker可能必须等待GPU通信完成后CPU才能解析控制信息。
  - pipeline bubble更容易出现。
  - 每个iteration的调度灵活性会被同步成本抵消。

---

**设计边界与限制**

- Control/Data Plane Separation并不减少GPU tensor通信本身：
  - 大模型跨GPU仍需要传输activation。
  - intra-layer parallelism仍需要collective communication。
- 它主要减少的是：
  - 高频控制消息导致的同步。
  - CPU等待GPU通信通道释放。
  - GPU等待CPU控制解析。
- 对单GPU模型收益有限：
  - 没有跨Worker控制转发问题。
  - 性能更多由kernel效率和batch size决定。
- 对多Worker大模型收益明显：
  - inter-layer partitions越多，控制消息传播链越长。
  - iteration次数越多，固定控制开销越容易累积。
- 对request-level scheduling系统不易直接复用：
  - 传统serving interface通常只在整个request batch开始和结束时交互。
  - ORCA需要scheduler和engine在每个iteration交互。
  - 因此Control Plane必须成为引擎接口的一等设计对象。

---

**关键结论**

- **Control/Data Plane Separation**的本质是让**CPU消费的控制信息走CPU通道**，让**GPU消费的张量数据走GPU通道**。
- 该设计避免了控制消息通过NCCL引发的额外**CPU-GPU synchronization**。
- 它是ORCA支持**iteration-level scheduling**、**selective batching**和跨Worker**pipeline parallelism**的底层通信基础。
- 在175B、341B这类分布式大模型推理中，该设计显著降低每iteration固定开销，提升吞吐并降低延迟。

### 6. Pipeline Parallelism across Iteration Batches

**核心定位**

- **Pipeline Parallelism across Iteration Batches** 是 ORCA 在 **inter-layer model parallelism** 场景下提升 GPU 利用率的关键机制。
- 核心思想：
  - ORCA 不把一个完整 request batch 固定执行到结束。
  - ORCA 将执行粒度切到 **iteration-level batch**。
  - Scheduler 在一个 batch 尚未完成所有 worker 处理前，继续向 execution engine 注入新的 iteration batch。
  - 不同 **worker** 同时处理不同 iteration batch，从而形成跨 batch 的 **inter-layer pipeline**。
- 该机制解决的问题：
  - 避免 inter-layer partition 之间的空闲。
  - 避免 FasterTransformer 依赖 **microbatch** 才能填充 pipeline 的限制。
  - 在保持较大 batch size 的同时获得较高 pipeline utilization。
  - 与 **iteration-level scheduling** 和 **selective batching** 配合，使 late-joining requests 能快速进入 pipeline。

---

**相关系统结构**

![](e26cdf4e4361d4662eebb26fffdbb4b80c7a96cb3d8be2a0302a733054b7f7b4.jpg) *Figure 7: An illustration of the distributed architecture of ORCA’s execution engine using the parallelization configuration shown in Figure 6. For example, the first inter-layer partition (Layer1 and Layer2) in Figure 6 is assigned to Worker1, while the second partition is assigned to Worker2.*

- ORCA 的 distributed execution engine 由多个 **worker** 组成。
- 每个 **worker** 负责一段连续的 Transformer layers，即一个 **inter-layer partition**。
- 每个 worker 内部还可以包含多个 GPU-controlling threads，对应 **intra-layer parallelism**。
- 数据流关系：
  - **Engine master** 接收 scheduler 选出的 iteration batch。
  - **Worker1** 处理前若干 Transformer layers。
  - 中间 activation tensors 通过 **NCCL** 传递给下一个 worker。
  - **Worker2 / Worker3 / ...** 继续处理后续 layers。
  - 最后一个 worker 生成 output token，并返回给 engine master。
- 控制流关系：
  - Request id、token index、input length 等 control message 通过 **gRPC** 等 CPU-side channel 传递。
  - Intermediate tensor data 通过 **NCCL** 走 GPU-side data plane。
  - 这种 **control-data plane separation** 减少 CPU-GPU synchronization。

---

**基本实现原理**

- ORCA 将一次模型执行拆成多个 **iteration batch**。
- 一个 **iteration batch** 的含义：
  - 包含若干 request。
  - 每个 request 在该 batch 中只执行 **一个 iteration**。
  - 每个 request 通常只生成 **一个 output token**。
  - 对于 initiation phase，输入可能是完整 prompt tokens。
  - 对于 increment phase，输入通常是上一个 iteration 生成的单个 token。
- Inter-layer pipeline 的形成方式：
  - Worker1 开始处理 batch A。
  - 当 batch A 的 intermediate activation 被传给 Worker2 后，Worker1 不等待 batch A 完全结束。
  - Scheduler 继续注入 batch B。
  - Worker1 处理 batch B，同时 Worker2 处理 batch A。
  - 如果有 3 个 workers，则 Worker3 可处理 batch A，Worker2 处理 batch B，Worker1 处理 batch C。
- 关键点：
  - Pipeline 的基本单位不是 request，也不是 microbatch，而是 **iteration-level batch**。
  - 每个 pipeline stage 对应一个 **inter-layer partition**。
  - 每个 pipeline slot 中流动的是一个 **batch of current-iteration tokens**。

---

**算法流程**

- Scheduler 持续循环执行：
  - 从 request pool 中选择一批 request。
  - 构造一个 **iteration batch**。
  - 调用 execution engine 执行该 batch 的一个 iteration。
  - 在未达到 pipeline 深度前，不等待 batch 返回。
  - 当已注入 batch 数达到 worker 数量后，等待最早注入的 batch 返回。
  - 根据返回的 output token 更新 request state。
  - 如果 request 完成，立即返回给 client，并释放对应 Attention K/V slots。
- 论文 Algorithm 1 中的关键变量：
  - **n_workers**
    - inter-layer pipeline 的 worker 数量。
    - 也可以理解为 pipeline depth。
  - **n_scheduled**
    - 当前已经注入但尚未返回的 iteration batches 数量。
  - **max_bs**
    - 每个 iteration batch 中最多包含的 request 数量。
  - **n_slots**
    - Attention K/V manager 可用的 K/V cache slot 数。
  - **n_rsrv**
    - 当前已经预留的 K/V cache slots 数。
- Pipeline 控制逻辑：
  - Scheduler 每调度一个 batch：
    - `n_scheduled += 1`
  - 当：
    - `n_scheduled = n_workers`
  - Scheduler 才等待一个已调度 batch 返回。
  - Batch 返回后：
    - `n_scheduled -= 1`
    - pipeline 中腾出一个 slot。
    - Scheduler 可继续注入新的 iteration batch。

---

**关键流程示意**

- 假设：
  - 有 3 个 workers：**Worker1、Worker2、Worker3**。
  - `max_bs = 2`。
  - Requests 到达顺序为 A、B、C、D、E、F。
- ORCA 的调度行为：
  - 注入 batch AB 的第 1 个 iteration：**A1B1**。
  - 不等待 A1B1 完全返回，继续注入 batch CD：**C1D1**。
  - 再继续注入 batch EF：**E1F1**。
  - 此时 3 个 workers 均被填满：
    - Worker1 处理 E1F1。
    - Worker2 处理 C1D1。
    - Worker3 处理 A1B1。
  - A1B1 返回后，A 和 B 若未完成，会重新进入 request pool 的可调度状态。
  - Scheduler 再选择 A、B 的下一轮 iteration：**A2B2**。
- 该方式的本质：
  - 每个 request 的多个 iterations 可以分散在多个 pipeline waves 中。
  - 每个 worker 在不同时间处理不同 batch 的不同 layer partition。
  - Pipeline 不依赖把一个 request batch 拆成 microbatches。

---

**输入输出关系**

| 层级 | 输入 | 输出 | 说明 |
|---|---|---|---|
| Scheduler | Request pool、request state、arrival time、K/V reservation state | Iteration batch | 决定下一轮哪些 requests 被执行 |
| Engine master | Iteration batch、tokens、control message | 分发给 Worker1 的执行任务 | 连接 scheduler 与 distributed engine |
| Worker1 | 当前 iteration tokens、request ids、token index、input length | Intermediate activations | 处理前若干 Transformer layers |
| Middle workers | 上一 worker 的 activations、control message | 新的 intermediate activations | 继续处理中间 layer partitions |
| Last worker | 最后一段 layers 的输入 activations | Output tokens | 为每个 request 生成一个 token |
| Request pool | Output tokens、finished flag | 更新后的 request state | 决定继续 increment 或返回 client |

- 对单个 iteration batch：
  - 输入：
    - 一组 request ids。
    - 每个 request 当前 iteration 的 input token 或 prompt tokens。
    - 每个 request 的 phase：
      - **INITIATION**
      - **INCREMENT**
    - 每个 request 的 token index。
    - 对应的 Attention K/V cache pointers。
  - 输出：
    - 每个 request 的一个 generated token。
    - Request 是否 finished 的状态。
    - 更新后的 K/V cache。
- 对整个 serving system：
  - 输入：
    - 连续到达的 client requests。
  - 输出：
    - 每个 request 的完整 generated sequence。
  - Pipeline parallelism 的作用：
    - 缩短 worker 空闲时间。
    - 提升系统吞吐。
    - 降低 late-joining request 的排队延迟。

---

**与 FasterTransformer 的差异**

| 维度 | ORCA | FasterTransformer |
|---|---|---|
| 调度粒度 | **Iteration-level** | **Request-level** |
| Pipeline 单位 | **Iteration batch** | **Microbatch** |
| 是否可在当前 batch 未结束前注入新 batch | **可以** | **不可以** |
| Batch 组成是否可动态变化 | **可以** | **基本固定** |
| Early-finished request 是否可立即返回 | **可以** | **通常不可以** |
| Late-joining request 等待时间 | 通常只等待一个 iteration | 需等待当前 request batch 完成 |
| Pipeline 与 batching 的关系 | 可同时保持较大 batch size 和 pipeline utilization | microbatch size 与 pipeline bubble 存在 trade-off |
| 对 heterogeneous requests 的适应性 | 强 | 弱 |

- FasterTransformer 的典型限制：
  - Serving system 向 engine 提交一个 request batch。
  - Engine 必须处理完整 batch，直到所有 requests 完成。
  - 为了让 inter-layer partitions 并行，只能把 batch 切成 **microbatches**。
- Microbatch 机制的问题：
  - Microbatch 太小：
    - Pipeline bubble 少。
    - 但 batch computation efficiency 下降。
  - Microbatch 太大：
    - Batch efficiency 较好。
    - 但 microbatch 数可能小于 pipeline stages，产生 pipeline bubbles。
- ORCA 避免该 trade-off：
  - 不需要把同一个 batch 切碎。
  - 不同 iteration batches 自然填充 pipeline。
  - Scheduler 可持续向 pipeline 注入新 work。

---

**参数设置与含义**

| 参数 | 含义 | 对 pipeline 的影响 | 设置原则 |
|---|---|---|---|
| **n_workers** | inter-layer workers 数量 | 决定 pipeline depth | 通常由模型规模和 inter-layer partition 决定 |
| **max_bs** | 单个 iteration batch 最大 request 数 | 影响单个 stage 的计算强度 | 根据 latency budget 与 throughput 需求调节 |
| **n_scheduled** | 已注入未返回 batch 数 | 控制 pipeline 中 in-flight batches 数 | 运行时动态维护 |
| **n_slots** | K/V cache 总 slot 数 | 限制可同时服务的 token 容量 | 在 GPU memory 允许下尽量取大 |
| **n_rsrv** | 已预留 K/V slots | 防止 K/V cache 分配死锁 | Scheduler 在 request 首次调度时更新 |
| **max_tokens** | 单个 request 最大 token 数 | 决定该 request 需预留的 K/V slots | 由 input tokens + max_gen_tokens 给出 |

- **n_workers**
  - Pipeline 并发度上限。
  - 若有 4 个 inter-layer workers，scheduler 最多保持 4 个 in-flight iteration batches。
  - 这样每个 worker 理论上都能同时处于 busy 状态。
- **max_bs**
  - 控制每个 iteration batch 的 request 数量。
  - 较大 `max_bs`：
    - 提升非 Attention operations 的 batching efficiency。
    - 增加每个 stage 的执行时间。
    - 可能提高单 request latency。
  - 较小 `max_bs`：
    - 降低排队和单轮执行时间。
    - 可能导致 GPU utilization 不足。
- **n_slots**
  - 用于 Attention K/V cache。
  - ORCA 在 request 首次进入系统时根据 `max_tokens` 预留 slots。
  - 保证 request 后续 iterations 不会因 K/V cache 不足而中途阻塞。

---

**为什么 ORCA 可以跨 iteration batch 做 pipeline**

- 依赖于 **iteration-level scheduling**：
  - Scheduler 每次只要求 engine 执行一个 iteration。
  - Engine 每次返回每个 request 的一个 token。
  - Scheduler 可在每个 iteration 边界重新决定 batch 组成。
- 依赖于 **selective batching**：
  - 即使 requests 的 token index 不同，也能被放进同一个 iteration batch。
  - Non-Attention operations 使用 token-wise batching。
  - Attention operation 对每个 request 单独处理，再 merge。
- 依赖于 **stateful K/V cache management**：
  - 每个 request 的 Attention keys 和 values 独立维护。
  - 不要求 batch 内 requests 拥有相同 sequence length。
  - Worker 只需通过 request id 和 token index 找到对应 K/V cache。
- 依赖于 **asynchronous scheduling behavior**：
  - Scheduler 不同步等待每个 batch 完全穿过所有 workers。
  - 只在 in-flight batches 达到 `n_workers` 后等待返回。
  - 形成稳定 pipeline。

---

**在整体系统中的作用**

- 提升 **inter-layer pipeline utilization**：
  - 多个 workers 不再串行等待同一个 batch。
  - 每个 worker 可持续处理不同 iteration batch。
- 提升 **throughput**：
  - Pipeline 中同时存在多个 batches。
  - 单位时间完成更多 iterations。
  - 对大模型尤其明显，因为大模型通常必须跨多个 GPUs / machines 做 inter-layer parallelism。
- 降低 **latency**：
  - Late-arriving request 不必等当前 request batch 完全结束。
  - Early-finished request 可在 iteration 返回后立即完成。
  - Scheduler 可快速把新 request 填入后续 iteration batch。
- 改善 heterogeneous workload 表现：
  - 请求的 input length、generation length、current token index 可以不同。
  - Pipeline 仍能持续运行。
  - 避免被最长 request 拖累整个 batch。
- 解耦 batching 与 pipelining：
  - FasterTransformer 中 microbatch size 同时影响 batching efficiency 和 pipeline efficiency。
  - ORCA 中 batch size 主要服务于 batching efficiency，pipeline 由 iteration batches 自然填充。

---

**性能含义**

| 场景 | ORCA 的优势来源 |
|---|---|
| 多 inter-layer partitions | 跨 iteration batches 填满 pipeline |
| 高并发请求 | Scheduler 持续注入新 iteration batches |
| 请求长度差异大 | Early-finished request 可及时离开，late-joining request 可快速加入 |
| 大 batch size | Selective batching 支持灵活 batch 组成 |
| 大模型 serving | Worker 空闲时间减少，GPU 利用率提升 |

- 论文中 175B GPT-3 配置：
  - 使用 **2 个 inter-layer partitions**。
  - 每个 inter-layer partition 内使用 **8-way intra-layer parallelism**。
  - 总计使用 **16 GPUs**。
- 在 end-to-end evaluation 中：
  - ORCA 在相近 latency 下相比 FasterTransformer 获得显著 throughput 提升。
  - 论文报告在 175B 模型上，相同 latency 水平下 ORCA 达到 **36.9× throughput improvement**。
- 关键原因不是单个 CUDA kernel 必然更快，而是：
  - Scheduling granularity 更细。
  - Pipeline bubble 更少。
  - Batch composition 更灵活。
  - K/V cache 管理更适合 autoregressive serving。

---

**执行时序抽象**

- 对 3 个 workers 的稳定状态，可抽象为：

| 时间片 | Worker1 | Worker2 | Worker3 |
|---|---|---|---|
| t1 | Batch A iteration 1 | idle | idle |
| t2 | Batch B iteration 1 | Batch A iteration 1 | idle |
| t3 | Batch C iteration 1 | Batch B iteration 1 | Batch A iteration 1 |
| t4 | Batch A iteration 2 | Batch C iteration 1 | Batch B iteration 1 |
| t5 | Batch B iteration 2 | Batch A iteration 2 | Batch C iteration 1 |

- 该时序表达的重点：
  - Worker1 不等待 Batch A 完成所有 workers。
  - Batch A 返回后，若 request 未完成，可再次进入后续 iteration batch。
  - Pipeline 中流动的是不同 batch 的不同 iteration。
  - 每个 request 的 autoregressive dependency 仍被满足：
    - A 的 iteration 2 必须等待 A 的 iteration 1 output token 返回。
    - 但 B、C 等其他 batch 的 iteration 1 可在此期间推进。

---

**正确性约束**

- Autoregressive dependency 必须严格满足：
  - 同一 request 的 iteration `t+1` 依赖 iteration `t` 生成的 token。
  - Scheduler 只能在 request 前一轮 iteration 返回后，再调度该 request 的下一轮 iteration。
- Inter-layer dependency 必须严格满足：
  - 同一 iteration batch 必须按 layer partition 顺序经过 Worker1、Worker2、...、WorkerN。
  - 下游 worker 依赖上游 worker 的 intermediate activations。
- K/V cache consistency 必须保证：
  - 每个 request 的 K/V cache 只能追加当前生成 token 对应的 key/value。
  - Finished request 的 K/V cache slots 必须释放。
  - 未 finished request 的 K/V cache 必须保留到后续 iterations。
- FCFS 语义：
  - ORCA 使用 **iteration-level FCFS**。
  - 较早到达的 request 至少执行了与较晚到达 request 相同数量的 iterations。
  - Late request 可能因生成 token 少而更早返回，但不会破坏 iteration-level fairness。

---

**与 selective batching 的配合关系**

- Pipeline parallelism 负责跨 workers 保持并行。
- Selective batching 负责让每个 iteration batch 内部可高效执行。
- 二者结合后的执行路径：
  - Scheduler 选择任意一组可运行 requests。
  - Engine 将这些 requests 的当前 tokens 合并为 flattened tensor。
  - Non-Attention operations 以 batching 方式执行。
  - Attention 前执行 Split。
  - 每个 request 单独执行 Attention，并访问自己的 K/V cache。
  - Attention 输出 Merge 回 batched tensor。
  - Batched tensor 继续经过后续 Linear、MLP、LayerNorm 等 operations。
  - Inter-layer boundary 处将 activation tensor 传给下一个 worker。
- 没有 selective batching 时：
  - Batch 内 request 必须拥有相同 phase 和相同 token index。
  - Scheduler 很难构造足够大的 iteration batch。
  - Pipeline 即使能注入多个 batches，也可能因 batch 太小导致 GPU utilization 低。

---

**实现细节要点**

- Scheduler 与 engine 的接口必须支持：
  - 每次只执行一个 iteration。
  - 每次传入可变 batch composition。
  - 每次返回每个 request 的 generated token。
- Worker controller 需要解析：
  - Request ids。
  - Token positions。
  - Input token counts。
  - Phase information。
  - K/V cache addresses。
- Worker 间传输需要区分：
  - **Control message**
    - CPU 使用。
    - 用于 kernel launch 和 K/V addressing。
    - 通过 gRPC 等控制通道传输。
  - **Intermediate tensors**
    - GPU 使用。
    - 通过 NCCL 传输。
- Last worker 需要同步 GPU execution：
  - 因为它必须取回 output tokens。
  - Output tokens 返回 engine master。
  - Engine master 再返回 scheduler。
- 前面 worker 可减少同步：
  - 发出 GPU kernels 后，可转发 control message。
  - 不必等待完整 batch 完成再让 pipeline 前进。

---

**技术价值总结**

- **Pipeline Parallelism across Iteration Batches** 的本质是：
  - 用多个 **iteration-level batches** 填充 inter-layer pipeline。
  - 替代传统 request-level serving 中的 microbatch pipeline。
- 它带来的关键收益：
  - **更高 worker utilization**。
  - **更少 pipeline bubbles**。
  - **更强 batching flexibility**。
  - **更低 queueing delay**。
  - **更适合 autoregressive Transformer serving**。
- 它成立的关键前提：
  - **Iteration-level scheduling** 提供细粒度调度边界。
  - **Selective batching** 支持任意 request 组合。
  - **K/V cache manager** 支持跨 iteration 状态维护。
  - **Control-data plane separation** 降低分布式执行同步开销。
