# Orca: A Distributed Serving System for Transformer-Based Generative Models 通俗讲解

### 0. 整体创新点通俗解读

**一句话抓住这篇论文**

- **ORCA**解决的不是“怎么让单次 Transformer inference 更快”，而是一个更系统的问题：
  - **现有 serving 系统把生成式模型当成普通模型来服务，调度粒度太粗，导致 GPU 忙得很假、用户等得很冤。**
- 它的核心贡献可以概括为：
  - 把调度粒度从**一个完整 request**切成**一个 generation iteration**。
  - 再用**selective batching**让这些进度不一致的 request 仍然能一起跑。
  - 最后把这套机制做成支持**大模型分布式 serving**的系统。

---

**痛点直击：之前的做法到底哪里难受**

- 普通 inference serving 系统的默认思路是：
  - 来一批 request。
  - 拼成一个 batch。
  - 扔给 execution engine。
  - 等整个 batch 全部跑完，再返回结果。

- 这个逻辑对 **ResNet**、**BERT** 这类“一次 forward 就结束”的模型很合理。
  - 一个 request 基本就是一次模型执行。
  - batch 进去，batch 出来。
  - 谁也不拖谁太久。

- 但对 **GPT-style autoregressive generation**，这个逻辑就很别扭。
  - 一个 request 不是跑一次模型，而是要跑很多次。
  - 每次只生成一个 **Token**。
  - 有的 request 生成 5 个 Token 就结束。
  - 有的 request 要生成 100 个 Token。
  - 它们被绑在同一个 batch 里，就会出现两个典型问题：

- **早结束的 request 被迫陪跑**
  - 某个 request 已经生成了 **EOS** 或达到长度限制。
  - 但 batch 里还有别的 request 没结束。
  - 传统 engine 不会中途把它放出来。
  - 结果是：
    - 用户明明已经可以拿到结果，却还在等。
    - GPU 还可能对“已经结束的 request”做无意义计算。

- **新来的 request 被迫排队**
  - 一个新 request 到达时，GPU 正在处理一个长 batch。
  - 传统系统不能把它插入正在进行的 batch。
  - 它只能等当前 batch 全部完成。
  - 如果 batch 里有长生成 request，新 request 的 queueing latency 会很难看。

- 这就是这篇论文的核心观察：
  - **生成式模型的服务瓶颈，不只是单个 kernel 慢，而是 request-level scheduling 不适合 multi-iteration workload。**

---

**通俗比方：传统系统像“整桌上菜”，ORCA 像“流水线自助餐”**

- 传统 serving 的 batch 很像餐厅里“整桌一起上菜”：
  - 一桌人一起点餐。
  - 厨房按这一桌统一处理。
  - 有人只点一碗汤，很快做好。
  - 有人点满汉全席，要等很久。
  - 但服务员规定：**必须等整桌菜都做完，才能一起端出去。**

- 这对短任务的人非常不公平。
  - 汤早就好了，但不能上。
  - 后面新来的顾客也不能插进厨房队列。
  - 厨房看似一直忙，但服务体验很差。

- **ORCA**的思路像把餐厅改成“每轮只做一道工序”的流水线：
  - 每一轮，厨房只推进每位顾客的一小步。
  - 谁吃完了，马上离席。
  - 新来的顾客，下一轮就能加入。
  - 不再把一桌人强行绑定到最后。

- 换到模型 serving 里：
  - “一桌菜”就是一个 **request-level batch**。
  - “一道工序”就是一次 **generation iteration**。
  - “汤做好却不能端”就是 **early-finished request** 被拖住。
  - “新顾客不能进厨房”就是 **late-joining request** 排队太久。

- 这个比方的顿悟点在于：
  - **ORCA 不是让每道菜做得神奇地更快，而是改变了厨房接单和出菜的节奏。**
  - 它把“整单完成才调度”改成了“每做一步就重新调度”。

---

**关键一招：把 request-level scheduling 扭成 iteration-level scheduling**

- 传统系统的基本单位是：
  - **一个 request**
  - 或者更准确地说：**一个 request 从开始生成到结束生成的完整生命周期**

- **ORCA**把这个单位换掉：
  - 不再让 engine 一口气把整个 batch 跑到结束。
  - scheduler 每次只让 engine 跑**一个 iteration**。
  - 每个 iteration 结束后，scheduler 重新检查：
    - 哪些 request 已经完成，可以返回。
    - 哪些新 request 到了，可以加入。
    - 下一轮 batch 应该由哪些 request 组成。

- 这个替换非常关键：
  - 原流程是：
    - **组 batch → 跑完整生成 → 返回**
  - ORCA 的流程是：
    - **组 batch → 跑一个 Token → 更新状态 → 重新组 batch → 再跑一个 Token**

- 这带来的变化是质变：
  - batch 不再是一个“绑死到结束”的队伍。
  - batch 变成了每一轮动态变化的“临时车厢”。
  - 早结束的 request 可以下车。
  - 新来的 request 可以上车。
  - GPU 的 batch size 也更容易维持在较高水平。

Interactions between components represented as dotted lines indicate that the interaction takes place at every iteration of the execution engine. $x _ { i j }$ is the j-th token of the i-th request. Shaded tokens represent input tokens received from the clients, while unshaded tokens are generated by ORCA. On the other hand, request x<sub>3</sub> only contains input tokens $( x _ { 3 1 } , x _ { 3 2 } )$ because it has not run any iterations yet.*

---

**真正难点：进度不同的 request 怎么还能 batch？**

- 如果只提出 **iteration-level scheduling**，其实还不够。
- 因为它马上带来一个麻烦：
  - 每个 request 的生成进度可能不同。
  - 有的还在处理 prompt。
  - 有的已经生成到第 20 个 Token。
  - 有的生成到第 100 个 Token。
  - 它们的 **Attention K/V cache** 长度不同。
  - tensor shape 不一致。

- 传统 batching 要求很强：
  - 每个 request 的计算图类似。
  - 输入 shape 类似。
  - 才能拼成一个规整的大 tensor。

- 但在 ORCA 里，scheduler 每轮挑出来的 request 很可能形态各异。
  - 这时如果强行要求“所有操作都 batch”，就做不起来。
  - 如果完全不 batch，又会丢掉 GPU throughput。

- 论文最巧的地方是：
  - **作者没有执着于“所有操作都必须 batch”。**
  - 而是问了一个更细的问题：
    - 哪些操作真的需要规整 batch？
    - 哪些操作其实只要把 Token 摊平成一堆就能一起做？

---

**Selective Batching：不是全都 batch，而是该 batch 的 batch**

- **Selective batching**的直觉非常简单：
  - **非 Attention 操作**可以继续 batch。
  - **Attention 操作**单独按 request 处理。

- 为什么这样可行？
  - **Linear**、**LayerNorm**、**MLP**、**GeLU**这些操作，本质上更像对每个 Token 做类似变换。
  - 它们不太关心这些 Token 来自哪个 request。
  - 所以可以把不同 request 的 Token 摊平成一个大矩阵一起算。

- **Attention**不一样。
  - Attention 必须知道：
    - 当前 Token 属于哪个 request。
    - 它能 attend 到哪些历史 Token。
    - 对应的 **K/V cache** 在哪里。
  - 不同 request 的历史长度不同。
  - 所以 Attention 很难用传统方式一起 batch。

- ORCA 的处理方式是：
  - 在进入 Attention 前，把大 batch **split** 成每个 request。
  - 每个 request 单独做 Attention。
  - Attention 后再 **merge** 回一个大 tensor。
  - 后面的 Linear、MLP 等继续 batch。

![](ad0b0963b5ec1aad7ea60ce20ebc70b0a2d0741ed61c64f672c493bec1ab8f6f.jpg) *Figure 5: An illustration of ORCA execution engine running a Transformer layer on a batch of requests with selective batching. We only depict the QKV Linear, Attention, and Attention Out Linear operations for simplicity.*

- 这一步的关键直觉是：
  - **不是所有算子都同等值得 batch。**
  - 对大模型来说，很多开销来自读模型参数。
  - **Attention 本身没有大规模模型参数**，不像 Linear/MLP 那样需要大量权重读取。
  - 所以不 batch Attention，损失相对可控。
  - 但保住 Linear/MLP 的 batching，就保住了大头收益。

---

**这篇论文的整体贡献可以这样理解**

- **贡献一：重新定义生成式模型 serving 的调度单位**
  - 从 **request-level** 改为 **iteration-level**。
  - 让 request 可以在每个 Token 生成后动态进出 batch。
  - 直接解决：
    - **early-finished request**
    - **late-joining request**
    - batch 内 request 长度差异导致的浪费

- **贡献二：提出 selective batching，让动态 batch 真能跑起来**
  - 如果没有 selective batching，iteration-level scheduling 很可能只停留在想法层面。
  - 因为动态选出来的 request shape 不一致。
  - ORCA 用“Attention 单独算，其他操作合起来算”的方式绕过这个障碍。

- **贡献三：把这个思路扩展到大模型分布式 serving**
  - 支持 **intra-layer parallelism**。
  - 支持 **inter-layer parallelism**。
  - 支持 pipeline execution。
  - 控制消息和 tensor 数据传输分离，减少不必要的 CPU-GPU 同步。

- **贡献四：证明这不是小优化，而是 serving 架构级收益**
  - 在 **GPT-3 175B** 规模上，相同 latency 下达到 **36.9× throughput improvement**。
  - 这个数字说明：
    - ORCA 的收益主要不是来自某个 kernel 写得更好。
    - 而是来自调度模型与生成式 workload 的结构更匹配。

| 维度 | 传统 FasterTransformer/Triton 式 serving | ORCA |
|---|---|---|
| 调度粒度 | **Request-level** | **Iteration-level** |
| Batch 生命周期 | 固定到整个生成结束 | 每个 iteration 可重组 |
| 早结束 request | 可能被拖住 | 可立即返回 |
| 新到 request | 等当前 batch 完整结束 | 下一轮 iteration 可加入 |
| Shape 不一致问题 | 很难 batch | 通过 **selective batching** 处理 |
| Attention 处理 | 一般尝试整体 batch | 按 request 单独处理 |
| 非 Attention 处理 | batch | 继续 batch |
| 大模型支持 | 支持但调度僵硬 | 分布式调度与执行协同设计 |

---

**最值得记住的直觉**

- **ORCA 的本质不是“更快的 Transformer kernel”。**
- 它真正做的是：
  - 看清楚 autoregressive generation 是一个**多轮交互式任务**。
  - 然后把 serving 系统从“批处理一整单”改成“每轮动态调度”。
  - 再用 selective batching 保住 GPU 的吞吐优势。

- 如果用一句更工程化的话说：
  - **ORCA 把 LLM serving 从静态 batch execution，推进到了动态 token-level batching 的方向。**

- 这也是为什么这篇论文影响很大：
  - 后来很多 LLM serving 系统，比如连续 batching、dynamic batching、paged KV cache 这类方向，本质上都在沿着类似思想继续走：
    - **不要把 request 绑死。**
    - **让 batch 随 Token 生成过程动态变化。**
    - **围绕 KV cache 和调度重新设计 serving 系统。**

### 1. Iteration-level Scheduling

**痛点直击：Request-level Scheduling卡在“整桌人吃完才能结账”**

![](b3265c6d41183072bb80fc0b68bca2d365929f9140ea282d5e57c2e0b51679fc.jpg) *Figure 3: An illustration for a case where the requests have the same input length but some requests finish earlier than others. Shaded tokens represent input tokens. “-” denotes inputs and outputs of extra computation imposed by the scheduling.*

- 传统 serving system，比如 **Triton + FasterTransformer**，调度粒度是**完整请求**：
  - Scheduler 把一批 request 组成一个 batch。
  - Execution engine 接过 batch 后，一口气跑到这一批所有 request 都生成结束。
  - 中途 scheduler 基本插不上手。

- 这在普通模型里问题不大：
  - 比如 **ResNet** 或 **BERT**，一个 request 通常跑一次 forward 就结束。
  - Batch 固定一小段时间，大家一起进、一起出，没什么浪费。

- 但对 **Transformer-based generative model**，问题突然变得很难受：
  - GPT 这类模型是 **autoregressive generation**。
  - 一个 request 不是跑一次模型，而是每生成一个 **token** 就要跑一次模型。
  - 生成 100 个 token，就要跑大约 100 次 iteration。

- 于是传统 request-level batching 会出现两个典型痛点：

  - **Early-finished request被困住**
    - 有的 request 很快生成 `<EOS>` 或达到长度上限。
    - 但 batch 里还有别的 request 没生成完。
    - 这个已经完成的 request 不能立刻返回 client。
    - 更糟的是，engine 可能还要为它做“空转”式计算或占着 batch 位置。

  - **Late-joining request进不来**
    - 新 request 在当前 batch 执行中途到达。
    - 它不能加入正在跑的 batch。
    - 它只能等整个 batch 全部结束。
    - 如果 batch 里有一个长输出 request，新 request 的排队时间会被严重拉长。

- 本质问题不是 Transformer 算得慢，而是：
  - **调度器的视野太粗**
  - 它只在“一个完整 batch 全部结束”时才重新决策。
  - 但 generative inference 的自然节奏其实是：
    - **每生成一个 token，系统状态就发生一次变化**
    - 有 request 完成了
    - 有 request 新来了
    - 有 request 进入下一轮 decoding
    - Batch 的最佳组成也变了

---

**通俗比方：不是包场吃完一桌，而是回转寿司每轮换座**

- 传统 **Request-level Scheduling** 像是餐厅安排一桌人吃饭：
  - 服务员把 8 个人凑成一桌。
  - 厨房开始服务这一桌。
  - 即使有人 5 分钟吃完，也不能先走结账。
  - 门口来了新客人，也不能坐进来。
  - 必须等这一桌所有人都吃完，服务员才重新安排下一桌。

- 这对“每个人饭量差不多”的场景还可以。
  - 如果大家都吃一份套餐，差别不大。
  - 一桌人一起开始、一起结束，batch 很自然。

- 但 GPT serving 更像是：
  - 每个人不是点一份套餐。
  - 每个人是不断点小碟寿司。
  - 有人吃 3 碟就饱。
  - 有人要吃 100 碟。
  - 还有人中途刚进店。

- **Iteration-level Scheduling** 的直觉是：
  - 不要按“整顿饭”调度。
  - 改成按“每一轮上菜”调度。
  - 每上一轮菜，也就是每生成一个 token，就重新看一眼餐厅：
    - 谁吃饱了？立刻结账。
    - 谁刚进来？下一轮可以安排。
    - 谁还没吃完？继续给他上下一碟。
    - 桌子还空不空？能不能塞更多人提高利用率？

- 这个比方的关键顿悟是：
  - **生成式模型的最小自然进度单位不是request，而是token iteration**
  - 传统系统把“一个完整生成请求”当成不可打断的任务。
  - ORCA 把它拆成一串可调度的小步：
    - 第 1 个 token
    - 第 2 个 token
    - 第 3 个 token
    - …

---

**关键一招：把“跑完整个请求”替换成“只跑一轮生成”**

![](22f25004781927f2deef3e118526ef78014c1e7db2c2ce55763d163698e991ee.jpg) *Figure 4: System overview of ORCA. Interactions between components represented as dotted lines indicate that the interaction takes place at every iteration of the execution engine. $x _ { i j }$ is the j-th token of the i-th request. Shaded tokens represent input tokens received from the clients, while unshaded tokens are generated by ORCA. For example, request $x _ { 1 }$ initially arrived with two input tokens $( x _ { 1 1 } , x _ { 1 2 } )$ and have run two iterations so far, where the first and second iterations generated $x _ { 1 3 }$ and $x _ { 1 4 } .$ respectively. On the other hand, request x<sub>3</sub> only contains input tokens $( x _ { 3 1 } , x _ { 3 2 } )$ because it has not run any iterations yet.*

- ORCA 的核心改动非常直接：
  - 原来 scheduler 调用 engine 的语义是：
    - **“请把这个batch里的所有request都生成完。”**
  - ORCA 改成：
    - **“请只给这个batch里的每个request生成一个token。”**

- 这个小改动带来的系统行为变化很大：

| 调度方式 | Engine一次调用做什么 | Batch能否中途变化 | 已完成request能否立刻返回 | 新request等待多久 |
|---|---|---|---|---|
| **Request-level Scheduling** | 跑完整个生成过程 | 不能 | 不能，等整个batch结束 | 等当前batch全部结束 |
| **Iteration-level Scheduling** | 只跑一次model iteration，生成一个token | 能，每轮都可重组 | 能，每生成一轮后检查 | 最多等当前iteration结束 |

- ORCA 每一轮的逻辑是：
  - Scheduler 从 **request pool** 里选一组 request。
  - Engine 对这组 request 跑一次 Transformer。
  - 每个 request 产出一个新 token。
  - Scheduler 拿回结果后更新 request 状态：
    - 如果 request 结束，就从 pool 移除并返回 client。
    - 如果没结束，就保留在 pool，等待下一轮。
    - 如果有新 request 到达，也放入 pool，下一轮就有机会被选中。

- 作者没有重新设计 Transformer，也没有改变 autoregressive generation 的数学逻辑。
  - 巧妙之处在于：
    - **把调度边界从request边界前移到iteration边界**
    - 让 scheduler 在每个 token 生成后重新获得控制权

- 这相当于把原来的黑盒执行：
  - **batch → engine → 完整文本**
- 改成细粒度闭环：
  - **batch → engine → 一个token → scheduler重新决策 → 下一轮batch**

- 这个“重新决策”的能力就是 ORCA 的核心价值：
  - **早完成的request不再陪跑**
  - **新到达的request不再长时间干等**
  - **batch组成可以动态变化**
  - **GPU更容易保持高利用率**
  - **latency和throughput不再被长尾request强行绑架**

---

**一句话抓住本质**

- **Iteration-level Scheduling** 不是让模型每个 token 算得更快。
- 它是让系统在**每生成一个token后重新洗牌batch**。
- 传统方法的问题是“这一桌人必须一起吃完”。
- ORCA 的办法是“每上一轮菜就重新安排座位”。
- 对 autoregressive generation 来说，这正好卡在最自然、最有效的调度粒度上。

### 2. Selective Batching

**痛点直击：为什么需要Selective Batching**

- **ORCA的Iteration-level Scheduling**解决了一个大问题：
  - 每一轮生成一个Token后，Scheduler都能重新组Batch。
  - 已完成的请求可以立刻退出。
  - 新来的请求可以很快加入。
  - 不再像传统Request-level Scheduling那样，一批请求必须“同生共死”。

- 但这马上带来一个新麻烦：**Batch里的人不齐整了**。
  - 有的请求刚开始，处在**initiation phase**，一次要处理一整段Prompt。
  - 有的请求已经生成了几十个Token，处在**increment phase**，每次只处理一个新Token。
  - 有的请求历史长度是20，有的是200，有的是500。
  - 这些请求的Tensor shape不一样，尤其是**Attention K/V cache长度不一样**。

- 传统Batching的前提是：
  - Batch里的请求最好长得一样。
  - 操作图一样。
  - Tensor shape一样。
  - 才能拼成一个大Tensor一起跑。

- 但在生成式Transformer Serving里，这个前提经常不成立：
  - 如果强行等“长度相同、阶段相同”的请求凑成Batch，GPU会等人，吞吐低。
  - 如果不Batch，逐个请求跑，GPU利用率又很差。
  - 如果像FasterTransformer那样固定一个Batch跑到底，短请求会被长请求拖住，新请求也进不来。

- **Selective Batching的痛点不是“能不能Batch”，而是“能不能在请求状态很乱的时候，仍然尽量Batch”。**

![](ad0b0963b5ec1aad7ea60ce20ebc70b0a2d0741ed61c64f672c493bec1ab8f6f.jpg) *Figure 5: An illustration of ORCA execution engine running a Transformer layer on a batch of requests with selective batching. We only depict the QKV Linear, Attention, and Attention Out Linear operations for simplicity.*

---

**通俗比方：不是所有工序都需要按订单分开做**

- 可以把Transformer推理想成一家餐厅后厨在处理很多外卖订单。

- 每个请求是一张订单。
  - 有的订单刚来，要处理一整份套餐。
  - 有的订单已经做到一半，只差最后一道菜。
  - 有的订单很复杂，有的很简单。
  - 每张订单当前进度不同。

- 后厨里有两类工序：

  - **通用流水线工序**
    - 切菜、洗菜、加热、装盒。
    - 不太关心这片菜属于哪张订单。
    - 只要把所有食材摊开，一起处理就行。
    - 对应Transformer里的**Linear、LayerNorm、MLP、GeLU、Add**等非Attention操作。

  - **按订单定制工序**
    - 调味、搭配、检查这道菜要和这张订单前面做过的东西是否一致。
    - 必须知道“这是哪张订单”“之前已经做了什么”。
    - 不能把不同订单混在一起算。
    - 对应Transformer里的**Attention**，因为它必须访问该请求自己的历史**K/V cache**。

- 传统Batching像是：
  - 要求所有订单完全一样、进度一样，才能一起进厨房。
  - 这在现实中很僵硬。

- **Selective Batching像是更聪明的后厨管理**：
  - 能混着做的工序就混着做。
  - 必须按订单单独处理的工序就拆开做。
  - 做完再合并回流水线。

- 顿悟点在这里：
  - **Batching不是非黑即白的。**
  - 不必要求整个Transformer Layer都Batch。
  - 只要把最耗参数读取、最适合矩阵并行的部分Batch起来，就已经赚到了大头。
  - Attention虽然被拆开执行，但它没有大量模型参数，不存在“Batch后复用参数读取”的巨大收益，所以拆开损失没想象中大。

---

**关键一招：把“整个Layer一起Batch”改成“只Batch能Batch的部分”**

- 作者没有试图强行让所有请求对齐。
  - 没有要求相同Prompt长度。
  - 没有要求相同生成步数。
  - 没有要求都处在同一个phase。
  - 没有要求Attention K/V cache长度一致。

- 作者做了一个很关键的逻辑转换：
  - 传统做法问的是：**这批请求能不能整体Batch？**
  - ORCA问的是：**这个Layer里的哪些操作可以Batch，哪些操作不能Batch？**

- 这个转换非常重要。
  - 原来Batching的单位是**request-level Tensor shape**。
  - 现在Batching的单位变成了**operation-level compatibility**。
  - 能兼容的操作合并。
  - 不能兼容的操作拆开。

- 具体流程可以理解成：

  - 把不同请求当前要处理的Token全部摊平。
    - 不再强行拼成传统的`[B, L, H]`。
    - 而是拼成类似`[total_tokens, H]`。
    - 这里的**total_tokens**可以来自不同请求、不同长度、不同阶段。

  - 对非Attention操作统一Batch执行。
    - **QKV Linear**可以一起跑。
    - **LayerNorm**可以一起跑。
    - **MLP**可以一起跑。
    - **Add**可以一起跑。
    - 这些操作本质上多是Token-wise的，不太关心请求边界。

  - 到了Attention时，把Batch拆开。
    - 每个请求单独执行自己的Attention。
    - 每个请求只看自己的历史**K/V cache**。
    - 不同请求的Attention长度可以不同。

  - Attention结束后再Merge回来。
    - 输出重新拼成一个大Tensor。
    - 后续非Attention操作继续Batch。

- 这个设计最巧妙的地方是：
  - **它没有消灭不规则性，而是把不规则性隔离在Attention里面。**
  - 其他大部分计算仍然保持Batch效率。
  - Scheduler因此可以大胆地把任意请求放进同一个Batch。

---

**为什么Attention可以“牺牲”Batching**

- 直觉上会担心：
  - Attention不Batch，会不会很亏？

- ORCA的判断是：
  - **亏得不多。**

- 原因很直接：
  - Transformer里大量耗时来自带模型参数的矩阵乘法。
    - 比如**Linear**、**MLP**。
    - Batch能复用从GPU memory读出来的模型权重。
    - Batch越大，参数读取摊薄得越好。

  - **Attention本身没有大规模模型参数**。
    - 它主要是在当前Query和历史Key/Value之间做计算。
    - Batch Attention并不能像Batch Linear那样显著复用模型权重。
    - 所以Attention不Batch，损失相对可控。

- 换句话说：
  - **ORCA把Batching资源用在最值钱的地方。**
  - 非Attention操作Batch，拿到主要收益。
  - Attention拆开，换来调度自由度。
  - 这是一个非常工程化、也非常聪明的取舍。

---

**和传统Batching的核心差别**

| 方案 | Batch要求 | 对不同生成阶段请求的支持 | Attention处理方式 | 主要问题 |
|---|---:|---:|---:|---|
| **传统Batching** | 请求形状尽量一致 | 弱 | 整体Batch | 不灵活，短请求和新请求容易被拖住 |
| **不Batch** | 无要求 | 强 | 单请求执行 | GPU利用率低，吞吐差 |
| **Selective Batching** | 只要求非Attention可摊平 | 强 | 按请求拆分 | Attention部分少量损失，换来整体高吞吐 |

---

**一句话抓住本质**

- **Selective Batching不是“把一批请求一起跑”，而是“把一批请求中能共享流水线的部分一起跑，不能共享历史上下文的Attention部分单独跑”。**

- 它的核心智慧是：
  - **不要为了Attention的形状不一致，放弃整个Transformer Layer的Batching。**
  - 把不规则的地方切出来。
  - 把规则的地方继续合并。
  - 这样ORCA才能同时拥有**灵活调度**和**高GPU利用率**。

### 3. Attention K/V State Manager

**痛点直击：为什么需要 Attention K/V State Manager**

- **Transformer 自回归生成**最麻烦的地方，不是算一个 Token，而是每生成一个新 Token，都要回头看前面所有 Token。
  - 对 GPT 这类模型来说，生成第 t 个 Token 时，Attention 需要用到前面所有 Token 的 **Key/Value**。
  - 如果没有缓存，每一步都要把历史 Token 重新送进模型，重新算一遍历史 **K/V**。
  - 这会造成大量重复计算，尤其是长文本生成时，成本会越来越高。

- 传统系统里通常也会做 **K/V cache**，但 ORCA 的难点更特殊：
  - ORCA 采用 **iteration-level scheduling**，每一轮调度的 batch 都可能变化。
  - 有的请求刚进入 **initiation phase**，有的请求已经生成了几十个 Token。
  - 有的请求下一轮还要继续，有的请求刚刚结束，需要立刻释放资源。
  - 所以 K/V 不能简单绑定到一个固定 batch 上，而必须绑定到**每个 request**。

- 换句话说，ORCA 面临的不是“要不要缓存 K/V”，而是：
  - **如何在 batch 每轮动态变化的情况下，仍然准确找到每个请求自己的历史 K/V？**
  - **如何避免已经结束的请求继续占用显存？**
  - **如何保证新请求加入时，有足够的 K/V 空间，不会中途爆显存？**

- 这个问题如果处理不好，会直接导致两个后果：
  - **性能差**：重复计算历史 Token，吞吐下降。
  - **显存乱**：请求生命周期不同，K/V cache 容易碎片化、泄漏，甚至导致调度死锁。

![](29af86d2cac3229be2028a4c5e39953ebc1273f54f3a92b385f30916c5abab2c.jpg) *Figure 1: Illustrations for GPT’s inference procedure, Transformer layer, and internal state usage.*

---

**通俗比方：K/V State Manager 像“每桌客人的独立账本”**

- 可以把 ORCA 的推理服务想象成一家很忙的餐厅。
  - 每个 **request** 是一桌客人。
  - 每生成一个 **Token**，就像这桌客人又点了一道菜。
  - Attention 的历史 **K/V**，就像这桌客人之前点过什么、口味偏好是什么、账单目前记到哪里。

- 如果没有 **Attention K/V State Manager**：
  - 服务员每上一道新菜，都要重新问一遍这桌客人之前点过什么。
  - 桌子越久，问得越多，效率越来越低。
  - 有些客人吃完走了，账本还放在桌上，占着空间。
  - 新客人来了，却可能因为账本堆满了而没地方坐。

- 有了 **Attention K/V State Manager**：
  - 每桌客人都有一本独立账本。
  - 服务员每次只需要看这桌自己的账本，不会混到别桌。
  - 客人继续点菜，就在原账本后面追加记录。
  - 客人离开，调度器通知系统把账本销毁，腾出空间。

- 这个比方最关键的地方在于：
  - ORCA 的 batch 不是固定一桌一桌服务，而是每一轮都可能重新组合。
  - 今天这一轮服务 A、B、C，下一轮可能服务 A、D、E。
  - 所以账本不能跟“当前 batch”绑定，只能跟**每个 request 的身份**绑定。
  - **Attention K/V State Manager**就是那个负责保管、查找、追加、释放这些账本的后台管家。

---

**关键一招：把 K/V 从 batch 里“解耦”出来，变成 request 级状态**

- 作者最巧妙的逻辑转换是：
  - 传统 batched inference 隐含假设：**K/V cache 跟 batch 结构一起走**。
  - ORCA 改成：**K/V cache 跟 request 生命周期一起走**。

- 这一步非常关键，因为 ORCA 的调度方式已经从 **request-level scheduling** 变成了 **iteration-level scheduling**。
  - 以前一个 batch 一旦发给 engine，就一直跑到整个 batch 完成。
  - 所以 K/V 可以比较粗暴地按 batch 组织。
  - ORCA 每一轮 iteration 后都可能换人：
    - 已完成的 request 离开。
    - 新到的 request 加入。
    - 未完成的 request 继续生成。
  - 因此 K/V 必须变成一种**长期存在、按 request 管理的状态**。

- **Attention K/V State Manager**做的事情可以概括为四步：
  - **创建**
    - 当一个 request 第一次被调度时，系统为它预留 K/V 存储空间。
    - 预留大小通常根据该 request 的 **max_tokens** 决定。
  - **追加**
    - 每生成一个新 Token，对应层的 Attention 会产生新的 **Key/Value**。
    - Manager 把这些 K/V 追加到该 request 自己的缓存区域。
  - **读取**
    - 下一次该 request 进入 increment phase 时，Attention 不再重算历史 Token。
    - 它直接从 Manager 中取出该 request 之前所有 Token 的 K/V。
  - **释放**
    - request 结束后，scheduler 通知 Manager 删除对应 K/V。
    - 显存槽位回收，供后续新请求使用。

| 管理对象 | 传统固定 batch 思路 | ORCA 的 Attention K/V State Manager |
|---|---|---|
| K/V 归属 | 跟随 batch | 跟随 request |
| batch 变化 | 不方便变化 | 每个 iteration 都可变化 |
| 历史 K/V 复用 | 可以复用，但结构较死 | request 级精准复用 |
| 请求结束 | 往往等 batch 整体结束 | request 完成即可释放 |
| 显存管理 | 容易预分配过大 | 按 max_tokens 预留，更细粒度 |

---

**为什么它是 ORCA 的关键支撑，而不是普通缓存**

- **Attention K/V State Manager**不是一个简单的性能优化小组件，而是 ORCA 能跑起来的基础设施。
  - 没有它，**selective batching**很难成立。
  - 没有它，**iteration-level scheduling**会丢失每个 request 的历史上下文。
  - 没有它，动态加入、提前离开的 request 会让 K/V 管理变得混乱。

- 它和 **selective batching**之间的关系很紧：
  - 非 Attention 操作可以把不同 request 的 Token flatten 到一起做批处理。
  - Attention 操作不能简单合并，因为每个 request 的历史长度不同。
  - 所以 ORCA 在 Attention 前把 batch 拆开。
  - 每个 request 单独做 Attention 时，就需要从 Manager 中取出自己的历史 K/V。
  - Attention 完成后再 merge 回去，继续做后面的 batched non-Attention ops。

![](ad0b0963b5ec1aad7ea60ce20ebc70b0a2d0741ed61c64f672c493bec1ab8f6f.jpg) *Figure 5: An illustration of ORCA execution engine running a Transformer layer on a batch of requests with selective batching. We only depict the QKV Linear, Attention, and Attention Out Linear operations for simplicity.*

---

**一针见血地说**

- **Attention K/V State Manager**的本质是：
  - 把 Transformer 生成过程中不断增长的历史上下文，做成一个**request 级、可追加、可查询、可释放的状态表**。

- 它解决的核心矛盾是：
  - ORCA 想让 batch 每轮都能动态变化。
  - 但 Attention 又要求每个 request 必须记住自己的完整历史。
  - 于是作者没有强行让所有 request 对齐，而是把历史 K/V 独立托管起来。

- 最直观的理解：
  - **调度器负责决定“这一轮谁上车”。**
  - **K/V State Manager 负责保证“每个人上车时都能带上自己的历史行李”。**
  - **请求结束后，它还负责把行李从车上清掉，别占显存。**

- 这就是 ORCA 能同时做到 **动态调度**、**历史复用**和**显存可控**的关键一招。

### 4. Distributed Model Parallel Execution

**痛点直击：为什么需要Distributed Model Parallel Execution**

- **核心痛点不是“跑得更快”这么简单，而是模型大到单张GPU根本放不下。**
  - GPT-3 175B、341B这类模型的参数量已经远超单卡显存容量。
  - 即使使用fp16，**175B参数本身就约350GB**，还没算中间激活、Attention K/V cache、通信缓冲区。
  - 单卡40GB A100面对这种模型，问题不是慢，而是**无法启动**。

- 传统推理服务系统面对大模型会有两个“很难受”的地方：
  - **层内矩阵太大**
    - Transformer里的Linear、QKV Linear、MLP矩阵乘法规模巨大。
    - 单张GPU做一整个矩阵乘法，显存和算力都会被压爆。
  - **层数太多**
    - GPT-3 175B有96层，341B有120层。
    - 即使每层能拆开算，所有层都塞到同一组GPU上，也会让显存压力极大。

- 更麻烦的是，ORCA服务的是**autoregressive generation**。
  - 每生成一个Token都要跑一遍模型。
  - 模型并行如果设计不好，每个Token都会触发大量跨GPU、跨机器同步。
  - 结果就是：
    - GPU在等通信。
    - CPU在等GPU。
    - Pipeline里有bubble。
    - 服务端吞吐上不去，延迟还高。

- 所以这里的Distributed Model Parallel Execution要解决的是：
  - **放得下模型**。
  - **跑得动每个Token**。
  - **多GPU不要互相干等**。
  - **跨机器通信不要把推理节奏拖死**。

![](8ea2f728df36f05ba6d1b8c302f0f68cbbe7c0dfbaa91478de5582ea6b7b6771.jpg) *Figure 6: An example of intra- and inter- layer parallelism. A vertical dotted line indicates partitioning between layers and a horizontal line indicates partitioning within a layer.*

---

**通俗比方：这像是在建一条巨型汽车装配线**

- 可以把一个大Transformer模型想成一辆巨型汽车的生产流程。
  - 每一层Transformer layer是一道工序。
  - 每层里面的Linear、Attention、MLP是这道工序里的大型机器。
  - 一个Token通过模型，就像一辆车从生产线头走到生产线尾。

- **inter-layer parallelism**像是把整条生产线切成几段。
  - 第1组工人负责前30层。
  - 第2组工人负责中间30层。
  - 第3组工人负责后30层。
  - 每组工人只保存自己负责的那部分模型参数。
  - 好处是：
    - 不需要每组人都掌握整辆车的全部工序。
    - 模型参数被分摊到不同GPU/机器上。
    - 每段生产线可以形成Pipeline。

- **intra-layer parallelism**像是某一道工序太重，必须几个人一起抬。
  - 比如一个超大的矩阵乘法，单个GPU算不了或太慢。
  - 那就把这个矩阵切开，让8张GPU各算一块。
  - 算完之后通过通信把结果拼起来。
  - 好处是：
    - 单层内部的大矩阵不再压垮单卡。
    - 每个GPU只承担一部分参数和计算。

- ORCA的组合策略就是：
  - **横着切层内计算**：用**intra-layer parallelism**拆大矩阵。
  - **竖着切层间结构**：用**inter-layer parallelism**拆Transformer层堆栈。
  - 合起来就像：
    - 一条生产线被切成多个车间。
    - 每个车间里的重活又由多个工人协作完成。

- 这个Mental Model很重要：
  - **inter-layer parallelism解决“层太多，整栋楼太高”的问题。**
  - **intra-layer parallelism解决“单层太宽，一张卡搬不动”的问题。**
  - ORCA不是只选一种切法，而是把两种切法叠起来，形成一个二维切分。

| 并行方式 | 类比 | 解决的问题 | 代价 |
|---|---|---|---|
| **intra-layer parallelism** | 一道重工序多人协作 | 单层矩阵太大、单卡算不动 | 层内GPU通信 |
| **inter-layer parallelism** | 生产线分成多个车间 | 层数太多、参数放不下 | 层间Pipeline通信 |
| **ORCA组合使用** | 多车间、多工人协同装配 | 百亿到千亿级模型分布式推理 | 调度和通信更复杂 |

---

**关键一招：作者把“大模型执行”变成二维切分后的流水线协作**

- ORCA最巧妙的地方不是发明了全新的model parallelism。
  - **intra-layer parallelism**和**inter-layer parallelism**本身在Megatron-LM、Mesh-TensorFlow等训练系统里已经存在。
  - ORCA真正关键的是：
    - 把这些训练里常见的模型并行方式，改造成适合**在线推理服务**的执行架构。
    - 再和ORCA自己的**iteration-level scheduling**配合起来。

- 原来的流程更像：
  - Serving system把一个batch交给engine。
  - Engine内部跑完整个生成过程。
  - 跑完所有请求后再返回。
  - 对大模型来说，这会导致：
    - batch固定。
    - Pipeline不灵活。
    - 新请求进不来。
    - 已完成请求出不去。

- ORCA把这一步扭转了：
  - **不是让engine一次处理完整请求。**
  - **而是让engine一次只跑一个iteration。**
  - 每个iteration内部，再用分布式模型并行跑完整个Transformer。
  - 换句话说：
    - 调度粒度变成**Token generation step**。
    - 执行粒度仍然是完整模型的一次前向。
    - 大模型本身通过二维model parallelism分摊到多GPU上。

![](e26cdf4e4361d4662eebb26fffdbb4b80c7a96cb3d8be2a0302a733054b7f7b4.jpg) *Figure 7: An illustration of the distributed architecture of ORCA’s execution engine using the parallelization configuration shown in Figure 6. For example, the first inter-layer partition (Layer1 and Layer2) in Figure 6 is assigned to Worker1, while the second partition is assigned to Worker2.*

- 具体替换掉的关键环节是：
  - 传统系统：
    - **一个worker/engine实例试图管理完整模型执行逻辑**。
    - 即使底层有model parallelism，调度层也看不到每个iteration的边界。
  - ORCA：
    - 引入**engine master**和多个**worker**。
    - 每个worker负责一个**inter-layer partition**。
    - 每个worker内部再用多张GPU做**intra-layer partition**。
    - master每次只下发当前iteration的请求信息。
    - worker之间传递中间tensor，形成Pipeline。

- 这里有一个很关键的工程判断：
  - ORCA把通信分成两类：
    - **control plane**：请求ID、Token位置、输入长度等控制信息。
    - **data plane**：GPU之间传递的中间tensor。
  - 它没有把所有东西都塞进NCCL。
  - 而是：
    - **NCCL**只负责GPU tensor数据传输。
    - **gRPC**等CPU侧通道负责控制消息。
  - 这个设计避免了每个iteration都因为控制信息触发不必要的CPU-GPU同步。

- 这一步的直觉是：
  - **GPU该搬tensor就搬tensor。**
  - **CPU该传调度信息就传调度信息。**
  - 不要让“通知工人下一辆车是谁”这件小事，也非得通过吊车来传。

- ORCA的分布式执行不是孤立存在的，它服务于更大的调度目标：
  - iteration-level scheduling不断产生一个个batch。
  - inter-layer partitions像生产线不同段一样接力处理这些batch。
  - intra-layer partitions在每一段内部并行完成大矩阵计算。
  - Pipeline持续填满，GPU空转减少。

- 关键结论：
  - **Distributed Model Parallel Execution让ORCA具备“服务超大模型”的物理能力。**
  - **iteration-level scheduling让ORCA具备“高效服务动态请求”的调度能力。**
  - 两者结合，才是ORCA能在175B/341B模型上取得高吞吐、低延迟的原因。
