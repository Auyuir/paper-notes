# SGLang: Efficient Execution of Structured Language Model Programs 通俗讲解

### 0. 整体创新点通俗解读

**痛点直击**

现在的 LLM 应用早就不是简单的“一问一答”了。像 Agent 控制流、Tree of Thought 这种复杂任务，本质上是一段**LM Program**：里面套着大量的 LLM 调用、分支循环、还要强制输出 JSON 格式。
你跑这些程序时，系统其实极其难受：
- **重复劳动太慢太贵**：同一段 System Prompt 或 Few-shot 例子，在多轮调用里被反复计算。现有的推理引擎（比如 vLLM）处理完一个请求就把 **KV Cache** 扔了，下一个请求来了又得重算一遍 Prefill，白白烧卡。
- **结构化输出像挤牙膏**：你要限制 LLM 输出特定 JSON 格式时，现有系统是**逐个 Token** 去查有限状态机（**FSM**）的。哪怕遇到 `{"summary": "` 这种完全确定的字符串，它也要一个 Token 一个 Token 地解码，每次都跑一次完整的 Forward Pass，慢得令人发指。

---

**通俗比方**

你可以把跑 LM Program 想象成**处理一批公文**：
- **传统做法（无 KV Cache 复用）**：每处理一份公文，哪怕前 10 页的“公司模板”都一样，办事员也要把这 10 页重新看一遍、重新理解一遍。这不仅慢，还占脑容量。
- **SGLang 的 RadixAttention**：就像给办事员发了一个**前缀字典树**。只要公文开头一样，直接把之前的“理解记忆”拿过来用。如果内存满了，就用 **LRU** 策略把最不常用的记忆删掉。
- **传统受限解码**：就像办事员过安检，哪怕前面是一条空无一人的直道，他也得走一步、停一步、问一句“下一步能走吗？”。
- **SGLang 的 Compressed FSM**：相当于给安检员配了望远镜，一眼看过去只要前面是一条没有分叉的直道，直接一脚油门冲过去（**多 Token 一次性解码**）。

---

**关键一招**

SGLang 没有去重新训练模型，也没有去魔改 Transformer 架构，而是**在前后端之间巧妙地插了一个协同优化的 Runtime**。它把原来割裂的“代码执行”和“模型推理”打通了：

- **针对 Cache 浪费**：作者并没有在请求结束后丢弃 **KV Cache**，而是将其挂载到一个 **Radix Tree** 上。
  - 前端解释器在遇到 `fork` 等并行原语时，会先给 Runtime 发一个“Hint”，告诉它接下来的前缀是什么。
  - Runtime 拿到 Hint 后，在 Radix Tree 里做前缀匹配，直接复用历史 **KV Cache**。
  - 调度器也不再是先来后到，而是**按最长共享前缀优先**的策略来调度请求，最大化 Cache 命中率。

- **针对解码太慢**：作者并没有去优化 Attention 计算，而是**扭转了 FSM 的遍历逻辑**。
  - 原本的 FSM 是基于字符/单 Token 转移的。
  - SGLang 在构建 FSM 时，把那些只有唯一出度的“单链路径”直接**压缩成一条边**。
  - 模型在解码时，只要踩到这条压缩边，就直接吐出多个 Token，把多次 Forward Pass 压缩成一次。

- **针对黑盒 API 贵**：对于只能调 API 的模型，作者在解释器里加了**投机执行**。既然多调一次 API 就要多付一次 Input Token 的钱，那就在第一次调用时故意忽略 `stop` 符号，让它多生成一点，后面的 `gen` 原语直接去匹配这段“白嫖”出来的输出。

---

**核心收益**

这套组合拳打下来，效果极其显著：

| 优化场景 | 核心机制 | 收益 |
| :--- | :--- | :--- |
| **多轮/共享前缀** | RadixAttention + Cache-aware Scheduling | 命中率最高达 99%，吞吐量提升最高 **6.4x** |
| **JSON 结构化输出** | Compressed FSM | 吞吐量提升 **1.6x** |
| **API 多次调用** | Speculative Execution | 输入 Token 成本降低约 **3 倍** |

总结一句话：SGLang 认清了 LLM 应用从“单次推理”变成了“程序化调度”的现实，用**操作系统的缓存调度思维**（Radix Tree + LRU + 调度器）重构了推理引擎，把以前引擎看不见的“冗余计算”全给榨干了。

### 1. RadixAttention

**痛点直击**

在复杂的 LLM Programs（如 ReAct agent、Tree-of-thought、多轮对话）中，大量请求其实共享相同的 Prompt 前缀（比如系统指令、few-shot 示例、历史对话记录）。但传统的推理引擎（如早期的 vLLM）把每个请求都当成独立个体，**用完即弃**。
- **算力浪费**：哪怕两个请求只有最后几个 Token 不同，引擎也会把前面几千个 Token 的 KV cache 从头算一遍。
- **显存爆炸**：重复存储相同的 KV cache，瞬间撑爆 GPU 显存，导致 batch size 上不去，吞吐量极低。
- **延迟高企**：Prefill 阶段的冗余计算直接拖慢了首字响应时间（TTFT）。
这就导致系统在处理多轮、多分支调用时，又慢又贵，根本无法规模化部署。

---

**通俗比方**

你可以把它理解为 **LLM 推理系统的 Git 版本控制**，或者一个 **高维度的 Trie 树文件系统**。
- 假设你在写代码，如果每次新建一个分支，都要把 `main` 分支的所有历史代码重新拷贝并重新编译一遍，这显然极其愚蠢。
- 正确的做法是：大家共享 `main` 分支的编译产物（KV cache），每个新分支只需要计算自己新增的那几行代码（新 Token）。
- RadixAttention 就是干这个的。它把所有历史请求的 KV cache 挂在一棵 Radix Tree 上。新请求来了，先在树上“寻址”，找到最长公共前缀，直接复用现成的“编译产物”，只对差异部分进行计算。

---

**关键一招**

作者并没有去重写 Transformer 的底层 CUDA Kernel，也没有去搞复杂的模型结构改造，而是巧妙地在**内存管理层**插了一个基于 Radix Tree 的 LRU Cache 机制，把原本“用完即毁”的无状态推理，扭转成了“有记忆”的缓存推理。

具体的逻辑转换如下：
- **结构转换**：将原本扁平的、独立的 KV cache 存储池，改造成一棵 **Radix Tree**。树的节点代表 Token 序列的公共前缀，边保存对应的 KV cache 张量。
- **复用机制**：当新请求到达时，系统不再直接分配显存，而是先在 Radix Tree 上进行**前缀匹配**。匹配命中的部分直接复用，只对未命中的后缀部分进行 Prefill 计算。
- **驱逐策略**：引入 **LRU (Least Recently Used)** 策略。当 GPU 显存不足时，优先驱逐那些最久没被使用的叶子节点，保留公共前缀，从而最大化缓存命中率。
- **调度协同**：配合 **Cache-aware scheduling**，不再用先来先服务（FCFS），而是优先调度那些共享前缀最长的请求，让它们打批处理，进一步榨干缓存的价值。

| 特性 | 传统推理引擎 | RadixAttention |
| :--- | :--- | :--- |
| **KV cache 生命周期** | 请求结束即销毁 | 作为 LRU Cache 长期保留 |
| **前缀复用** | 需手动配置或无法复用 | 基于 Radix Tree 自动匹配复用 |
| **多级共享支持** | 仅支持单级（如系统提示词） | 支持动态树状多级共享 |
| **显存管理** | 静态分配 | 动态分配与驱逐 |

通过这一招，系统在多轮对话和复杂 Agent 任务中，把缓存命中率拉到了 50%~99%，直接把吞吐量干到了 **6.4倍** 的提升。

### 2. Compressed Finite State Machine

**痛点直击**

当你需要 LLM 输出结构化数据（比如严格的 JSON 格式）时，系统会用正则表达式构建一个 FSM 来约束解码过程，防止模型“胡说八道”。
- 之前的做法极其死板：FSM 每次只允许模型看一步，生成一个 Token。
- 痛点在于：当遇到像 `{"summary": "` 这种毫无歧义的固定前缀时，模型明明知道接下来只能输出这几个字符，却还得像挤牙膏一样，一个 Token 一个 Token 地跑前向传播。
- 这就像在高速公路上开碰碰车，明明可以一脚油门踩到底，却非要一寸一寸挪，极其浪费算力和时间，导致解码速度慢得令人发指。

---

**通俗比方**

这其实就是一个“折叠单行道”的逻辑。
- 你可以把传统 FSM 想象成一个迷宫地图。在迷宫里，遇到岔路口你当然得停下来看看 FSM 允许往哪走，这很合理。
- 但是，如果迷宫里有一段路是“单行道”，没有任何分叉，直通通连着下一个路口，传统 FSM 还是要求你一步一停，每走一步都要停下来确认一次“前面还是单行道吗？”。
- 压缩 FSM 的做法就是直接把这段单行道在地图上“折叠”成一条线，告诉你“前面 100 米都是直道，别停了，一口气冲过去”。

---

**关键一招**

作者并没有重头训练模型，也没有修改 Attention 机制，而是巧妙地在 FSM 和模型推理之间插了一个**图压缩预处理**步骤。
- **识别单一路径**：系统分析 FSM，找出所有“只有一个后继节点，且只有一个合法字符”的边。
- **合并压缩**：把这些首尾相连的确定性路径，直接压缩成一条“超级边”。
- **跳跃式解码**：在运行时，一旦模型走到这条“超级边”上，系统直接把这条边代表的多个 Token 一次性塞给模型，跳过中间那些毫无意义的逐 Token 前向传播。
- **结果**：通过这种“多 Token 一步解码”的逻辑转换，原本需要多次前向传播的固定格式输出，现在一次就能搞定，大幅提升了结构化输出的解码速度。

### 3. API Speculative Execution

**痛点直击**

- 在使用黑盒 API 模型（如 GPT-4）编写复杂 LM Program 时，程序往往需要链式调用多次 `gen`。
- 例如：先让模型生成名字，再生成职业。代码逻辑是 `context + "name:" + gen("name") + "job:" + gen("job")`。
- **痛点在于**：每次 `gen` 都是一次独立的 API 请求。你不仅要为相同的 `context` 重复支付 **Input Token** 费用，还要忍受多次网络请求带来的 **Latency**。
- 这就像你每次只点一道菜，吃完再去前台点下一道，结账和上菜的时间全浪费了。

**通俗比方**

- 想象你在快餐店点套餐。原本的流程是：点汉堡 -> 等待 -> 付钱 -> 吃完 -> 再去点薯条 -> 等待 -> 付钱。
- **API Speculative Execution** 的逻辑是：你直接对服务员说“给我来个汉堡，顺便把后面的薯条和可乐也猜着一起拿过来”。
- 模型本身具有很强的续写能力，当你让它生成 `name` 时，它大概率会顺着格式自己把 `job` 也写出来。
- 我们干脆让第一次 API 调用**不要停**，一口气把后面的内容也生成出来。

**关键一招**

- 作者并没有修改 API 接口，而是巧妙地在 **Interpreter（解释器）** 层做了一个“缓存与匹配”的动作。
- 具体流程如下：
  - **忽略停止信号**：在第一次调用 `gen` 时，解释器故意忽略 `stop` 条件，让模型继续往下生成几个 Token。
  - **本地缓存**：解释器把这些多生成的文本截留下来，放在本地。
  - **模式匹配**：当程序执行到下一个 `gen` 原语时，解释器不再发起新的 API 请求，而是去本地缓存里找，看模型刚才“猜”出来的内容能不能对上。
  - **直接复用**：如果对上了，直接复用这部分输出；如果没对上，再发起真实的 API 请求兜底。
- 通过这一招，把多次串行的 API 调用，压缩成了**一次调用 + 本地匹配**，既省了钱又省了时间。

| 对比维度 | 传统串行调用 | API Speculative Execution |
| :--- | :--- | :--- |
| **API 请求次数** | N 次 | 1 次（理想情况） |
| **Input Token 成本** | 重复支付 Context 费用 | 仅支付 1 次 |
| **网络 Latency** | 累加的往返延迟 | 单次往返延迟 |
| **执行逻辑** | 请求 -> 等待 -> 请求 | 请求 -> 缓存 -> 本地匹配 |
