# Fast Transformer Decoding: One Write-Head is All You Need 通俗讲解

### 0. 整体创新点通俗解读

**痛点直击**

Transformer在训练时并行度极高，但在**增量推理**（Incremental Decoding）时极其难受。因为生成文本是自回归的，每生成一个Token，都要把之前所有的Keys和Values重新加载一遍。

在标准的Multi-head Attention中，有$h$个头，意味着要存$h$份庞大的K和V张量。这导致**内存带宽**成为严重瓶颈：
- GPU/TPU的计算单元大部分时间都在干等数据从显存搬过来。
- 算力被严重浪费，解码速度被内存读写死死拖住。

---

**通俗比方**

想象一个公司有$h$个部门经理（Query头），他们每天都要查阅公司的历史档案（Keys和Values）来做决策。

- **以前的Multi-head做法**：每个经理都要求档案室给自己单独建一套档案库。每次有新档案进来，档案室要更新$h$个库，经理们也要各自跑一趟自己的库去翻找。这导致档案室（内存带宽）累死，经理（计算单元）等死。
- **Multi-query Attention的做法**：档案室只保留**一套公共档案库**。所有经理都来这一个库查资料，只是每个人带着自己的不同问题（Query）来查。这样档案室的更新和查阅压力瞬间降到了原来的$1/h$。

---

**关键一招**

作者并没有去动Query的多头结构，而是巧妙地把Keys和Values的投影矩阵$P_k$和$P_v$的“头”维度直接砍掉。

- 原来输入经过投影会生成$h$组K和V。
- 现在只生成**1组**K和V。
- 所有的Query头都去和这**同一组**K和V计算Attention。

这一个简单的张量维度裁剪，直接把增量推理时K和V的内存读写量减少了$h$倍，让解码速度飙升，而模型质量几乎不掉。

---

**性能对比**

| Attention Type | Inference (enc. + dec.) | Beam-4 Search (enc. + dec.) |
| :--- | :---: | :---: |
| multi-head | 1.7 + 46 | 2.0 + 203 |
| **multi-query** | **1.5 + 3.8** | **1.6 + 32** |

*注：数值为 TPUv2 上每个Token的微秒数。可以看到Decoder部分的速度提升了10倍以上。*

### 1. Multi-Query Attention

**痛点直击**

在自回归模型的**增量解码**阶段，系统面临一个极其尴尬的硬件瓶颈：**内存带宽**远比**算力**捉襟见肘。
- 每生成一个新 Token，模型都必须把之前所有历史 Token 的 **Keys** 和 **Values** 张量从显存重新加载一遍。
- 在传统的 **Multi-head Attention** 中，每个 Head 都维护着各自独立的一套 **Keys** 和 **Values**。
- 这导致张量体积庞大（包含 batch、heads、sequence、dimension 四个维度）。
- 硬件大部分时间都在“搬砖”（读取数据），而不是“干活”（矩阵乘法），导致解码速度慢得令人发指。

---

**通俗比方**

把 Attention 机制想象成一家公司的档案查阅系统，有 $h$ 个不同视角的调研员（即 **Heads**）。
- **Multi-head Attention 的做法**：每个调研员都要求档案室给他们复印一份完整的公司历史档案（**Keys** 和 **Values**）。每次来了新任务（**Query**），8个调研员就要同时搬出8份沉甸甸的档案。搬运这些档案（内存读取）累死人，真正看档案的时间（算力）反而很短。
- **Multi-Query Attention 的做法**：8个调研员共用同一份历史档案。他们带着各自不同的问题（**Queries**）去查阅同一套档案。
- 结果：搬运档案的体力活直接减少到原来的 1/8，但大家依然能从不同视角得出结论。

---

**关键一招**

作者并没有去压缩模型的维度或者砍掉 Head 数量，而是巧妙地做了一个**降维共享**。
- **保留 Queries 的多头特性**：$P_q$ 依然是 `[h, d, k]`，每个 Head 依然可以从不同视角提出问题。
- **剥夺 Keys 和 Values 的多头特性**：将 $P_k$ 和 $P_v$ 的维度从 `[h, d, k]` 降维成 `[d, k]`。
- **逻辑扭转**：所有 Heads 共享同一组 **Keys** 和 **Values** 投影矩阵。在计算 Attention 时，多个 Queries 去和同一组 Keys 做点积，再去加权同一组 Values。

这一招直接把内存访问量与计算量的比例从 $\Theta(\frac{n}{d} + \frac{1}{b})$ 暴跌至 $\Theta(\frac{1}{d} + \frac{n}{dh} + \frac{1}{b})$，把最头疼的 $\frac{n}{d}$ 项硬生生缩小了 $h$ 倍。

**性能与质量对比**

| Attention 类型 | K/V 张量维度 | 内存带宽瓶颈 | 解码速度 | 模型质量 (BLEU) |
| :--- | :--- | :--- | :--- | :--- |
| **Multi-head** | `[b, h, m, k]` | 极其严重 | 慢 (46 $\mu s$/token) | 基准 (28.4) |
| **Multi-query** | `[b, m, k]` | 大幅缓解 | 极快 (3.8 $\mu s$/token) | 几乎无损 (28.5) |

通过这种共享机制，模型在推理速度上获得了数量级的提升，而质量几乎没有损失，完美解决了增量解码的带宽噩梦。
