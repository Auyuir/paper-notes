# Beyond Prefill-Decode Disaggregation: Dissecting LLM Inference for Heterogeneous Platforms via Dynamic Operator Scheduling 通俗讲解

### 0. 整体创新点通俗解读

**痛点直击**

在异构硬件（比如 **NPU** 擅长算力，**PIM** 擅长带宽）上跑大模型推理时，传统的 **Prefill-Decode Disaggregation (PD)** 策略太“死板”。
- **调度僵化**：PD 策略简单粗暴地把 Prefill 阶段全塞给 NPU，Decode 阶段全塞给 PIM。但这忽略了运行时的真实情况——有时候 NPU 空着，有时候某个算子放在“局部最优”的设备上反而会导致另一个设备排队等待，拖慢整体端到端时延。
- **权重排布撕裂**：NPU 和 PIM 对同一个权重矩阵在物理内存中的排布偏好完全不同。NPU 喜欢 **NPU_OPT**（分形排布），PIM 喜欢 **PIM_OPT**（Bank 级并行排布）。如果只存一份通用的 **Linear** 布局，每次执行前都要做耗时的格式转换；如果两份都存，边缘设备的内存预算直接爆掉。

PD, AF, PD+Linear, PD+FFN, and PD+Attn are diferent policies. See Table 1 for details.*

如上图所示，根本不存在一种放之四海而皆准的静态调度策略。最优解会随着 Prefill 长度、Decode 长度和 Batch Size 剧烈漂移。

---

**通俗比方**

把异构系统想象成一个后厨：
- **NPU** 是“切菜主厨”（算力强，但拿食材慢）。
- **PIM** 是“备菜小哥”（就在冰箱旁边，拿食材极快，但切菜慢）。

传统的 PD 调度就像是死板的菜单分配：备菜全让小哥做，主炒全让主厨做。结果主厨可能切完了菜，闲得发慌等小哥拿调料；或者小哥为了给主厨备一种特殊切法的葱花，不得不把整筐葱重新翻一遍（格式转换）。

这篇论文提出的 **DOPS** 框架，引入了一个聪明的“统筹大堂经理”：
- **Bifocal Scheduler**：经理分配任务时不仅看“谁现在手速快”（Near-focus），还要看“把这道菜给主厨，会不会导致后面三道菜卡在出餐口”（Far-focus）。
- **Weight Layout Arbiter (WLA)**：经理决定食材在冷库（主存）里怎么摆放。既不全部按主厨的刀法切好（太占地方），也不全部原封不动放着（每次都要重切）。而是根据历史出餐记录，动态调整哪些食材按主厨偏好存，哪些按小哥偏好存。

---

**关键一招**

作者并没有去重新设计 NPU 或 PIM 的硬件架构，而是巧妙地在原有的编译/调度流水线中，插入了一个**闭环的联合优化引擎**，把“算子调度”和“权重排布”这两个原本解耦的问题死死绑在了一起。

- **扭转调度逻辑**：放弃了传统的 Roofline 模型（只看算力和带宽上限，太乐观），改用 **Bifocal Score**。这个分数由两部分组成：
  - **Near-focus**：估算当前算子如果放在某设备上，加上通信延迟和权重重载惩罚后的真实完成时间，并往后看 H 个后继算子做短程模拟。
  - **Far-focus**：引入跨阶段的权重复用惩罚和 Token 摊销 bias。在 Decode 阶段，哪怕当前 Token 把算子放到某个设备上代价稍高，只要能摊销后续几十个 Token 的总成本，这就是个好决策。
- **扭转排布逻辑**：WLA 并不做全局暴力搜索，而是采用**两阶段块坐标搜索**：
  - 先根据 Bifocal 跑出来的调度结果，看哪个权重块在哪个设备上被加载得多，直接把该块的格式定为那个设备的最优格式（粗调）。
  - 然后针对个别不匹配的块，在邻居空间内做局部翻转，只要总 Makespan 下降就接受（精调）。

![](images/f2626a5b17f6a1a83a1c63253d89be55853a794eedb64df457d58947d17d3554.jpg) *Figure 4: Overall workflow of DOPS for dissecting LLM inference on a heterogeneous NPU–PIM system. E2E: end-to-end.*

通过这种“调度决定排布，排布反作用于调度”的闭环，DOPS 在不翻倍内存的前提下，把异构硬件的协同效率榨干。最终在实验中，Bifocal 相比 PD 基线取得了 **1.20× 到 2.23×** 的加速，WLA 又额外带来了 **1.28× 到 1.33×** 的提升。

### 1. Bifocal 动态算子调度机制

---

**痛点直击**

之前的算子调度太“近视眼”。基于 Roofline 模型的静态分配，只盯着单个算子的理论峰值性能。
- 比如 NPU 算力高，就把一堆算子全塞给 NPU。结果 NPU 排队堵死，PIM 闲得发慌。
- 更致命的是，算子在 NPU 和 PIM 之间来回切，权重格式不匹配，每次都要重新转换，白白浪费带宽和时间。
- 这就是典型的“局部最优导致全局灾难”，只看单步快不快，不管后面堵不堵。

---

**通俗比方**

就像高速公路收费站调度。
- NPU 是大站人工通道（算力强），PIM 是 ETC 通道（带宽高）。
- 以前的调度员只看眼前：哪条道当前车少，就把车往哪赶。结果所有车挤到人工通道，后面排长龙，ETC 通道空着。而且车从 ETC 切到人工，还要停下来换卡（权重重排），费时费力。
- Bifocal 调度员则戴了副“双焦眼镜”：不仅看眼前哪条道快，还拿望远镜看看下游几公里堵不堵，顺便看看这辆车是不是经常跑这条线。

---

**关键一招**

作者没有重写算子，而是把“局部贪心评分”换成了“双焦评分”。
具体来说，把调度决策拆成了两部分：

- **Near-focus（算当前账）**：评估当前算子放哪个设备完成最快。这里不仅算执行时间，还把排队时间、权重重排开销都算进去了。
- **Far-focus（算未来账）**：包含三个偏向项：
  - **DAG-window lookahead**：往后看几个算子，看下游会不会堵车。
  - **Phase-reuse bias**：看权重能不能一直留在同一个设备上，避免搬来搬去。
  - **Token-amortization bias**：在 Decode 阶段，看能不能把一次性的搬运成本摊销到后续多个 Token 上。

这样一搞，调度器不再追求单步最快，而是追求全局时间线最优。哪怕当前某步在 PIM 上跑得慢点，只要能避免下游拥堵或者省下权重搬运的开销，整体反而是赚的。

### 2. 权重布局仲裁器 (WLA)

**痛点直击**

在 NPU 和 PIM 组成的异构系统里，这俩兄弟的“口味”完全不同：
- **NPU** 喜欢吃“切块摆盘好”的 **NPU_OPT** 格式，方便直接塞进矩阵计算引擎。
- **PIM** 喜欢吃“按通道排好”的 **PIM_OPT** 格式，方便直接在内存颗粒里并行计算。

之前的做法非常难受：如果主存里只存一份通用的 **Linear** 格式，每次计算前都要在运行时做格式转换，开销极大；如果为了省事，给 NPU 和 PIM 各存一份它们喜欢的专属格式，内存占用直接翻倍，边缘设备的内存预算根本扛不住。这就是典型的“顾头不顾尾”，省了内存就慢，快了就爆内存。

---

**通俗比方**

这就像你开了一家异国餐厅，厨房里有中厨（**NPU**）和西厨（**PIM**）。
- 中厨做菜喜欢用“切好块的”土豆（**NPU_OPT**）。
- 西厨做菜喜欢用“切好条的”土豆（**PIM_OPT**）。

如果供应商每天只送一车完整的土豆（**Linear**），两个厨师每次做菜前都得自己切，手忙脚乱，出餐极慢。如果你让供应商送两份预处理好的土豆（一份块、一份条），冰箱又塞不下。

**WLA (Weight Layout Arbiter)** 就是你请来的聪明采购经理。他不会盲目备货，而是先看这周的菜单（调度策略）：
- 如果某道菜中厨做得多，他就把这批土豆按“块”买回来。
- 如果某道菜西厨做得多，他就按“条”买回来。
- 如果两边都不常做，就直接买完整土豆（**Linear**）。

---

**关键一招**

作者并没有去搞复杂的运行时数据流重排，也没有暴力存两份权重，而是巧妙地在调度和执行之间插了一个**两阶段块坐标搜索**机制。

这个机制的核心逻辑是“看菜下饭”：
- **粗调阶段**：
  - 先默认所有权重都是 **Linear** 格式。
  - 跑一遍调度器，看看每个权重块到底是被 **NPU** 调用得多，还是 **PIM** 调用得多。
  - 谁用得多，就直接把这个块的存储格式“粗暴地”改成谁喜欢的格式（**NPU_OPT** 或 **PIM_OPT**）。
- **细调阶段**：
  - 拿着粗调的结果，开始挨个块“试错”。
  - 把某个块的格式翻转一下（比如从 **NPU_OPT** 换回 **Linear**），再跑一遍调度。
  - 如果发现总延迟变小了，就保留这个翻转；变大了就退回去。

通过这种“先看大局定基调，再抠细节做微调”的策略，**WLA** 在不翻倍内存的前提下，把运行时的格式转换开销降到了最低，完美平衡了内存预算和执行延迟。

### 3. 调度与布局联合优化的闭环框架 (DOPS)

**痛点直击**

在异构的 NPU-PIM 系统上跑 LLM 推理，以前的玩法是“各管一段，互不干涉”。Prefill 阶段算力密集，全扔给 NPU；Decode 阶段访存密集，全扔给 PIM。这种 Prefill-Decode Disaggregation (PD) 看着合理，但在真实场景下极其难受，原因有三：
- **静态规则水土不服**：LLM 的 workload 变化极大。Prefill 长一点、Decode 短一点、Batch size 变一下，最优的算子分配策略就完全不同。用一套死规则打天下，必然在某些场景下严重拖后腿。
- **Roofline 模型过度乐观**：以前根据算力峰值和带宽峰值来分配任务，但真实运行时存在设备争用、排队和通信开销。把一堆准备好的算子全塞给同一个设备，反而会在关键路径上造成拥堵。
- **权重布局的“精神分裂”**：NPU 喜欢分块打包的权重（NPU_OPT），PIM 喜欢按通道/ Bank 对齐的权重（PIM_OPT）。如果你在主存里只存一份通用格式，两边用的时候都要现场重排，慢得要死；如果你存两份，边缘设备的内存预算直接爆炸。

---

**通俗比方**

想象一个双人厨房：NPU 是个大力士主厨，擅长抡大铁锅做大锅饭（GEMM）；PIM 是个手脚麻利的小工，专门站在冰柜旁切配小菜（GEMV）。

以前的调度员是个死脑筋，规定“所有大锅饭都给主厨，所有小菜都给小工”。但有时候主厨忙不过来，小工闲得发慌；有时候小工切菜太多，主厨没活干。

更头疼的是“食材摆放”（权重布局）问题。主厨喜欢把肉一筐一筐地放（NPU_OPT），小工喜欢把肉一片一片挂在墙上（PIM_OPT）。
- 如果只买一筐肉：小工每次拿肉都得自己切片，累个半死。
- 如果买一筐肉再买一份挂墙的肉：冰柜塞不下（内存溢出）。

DOPS 就是一个聪明的厨房大总管。他不仅动态分配任务（看谁闲就给谁），还懂得“联合优化”食材的摆放方式。他发现：“明天主厨要请客，小工没活，那肉就全按筐买；后天小工要备宴席，主厨休息，那肉就全挂墙上。”如果两人都忙，就精打细算地买一部分筐装、一部分挂装，绝不浪费冰柜空间。

---

**关键一招**

作者并没有重头设计一个新的硬件架构，而是巧妙地在软件调度栈里插了一个**闭环反馈机制**，把“任务调度”和“权重布局”这两个原本独立的问题，死死地耦合在一个优化空间里解决。

核心逻辑转换在于：**用调度的结果指导布局，用布局的成本反哺调度**。

具体拆解为两个引擎的咬合运作：

- **Bifocal Scheduler（动态调度器）**：
  - 它不用死板的 Roofline，而是用一个 **Bifocal Score** 来评估任务该给谁。
  - 这个分数包含 **Near-focus**（近期：算上排队时间和通信延迟，这任务啥时候能干完）和 **Far-focus**（远期：这个决定会不会让下游拥堵？这块权重下一步谁还会用？）。
  - 它甚至能“忍辱负重”：在 Decode 阶段，它可能会故意选择一个当前耗时略高的设备，只为了把权重迁移成本摊销到后续更多的 Token 上。

- **Weight Layout Arbiter (WLA)（布局仲裁器）**：
  - 它不盲目复制权重，而是根据 Bifocal 跑出来的调度轨迹，看哪块权重被哪个设备调用得多。
  - 采用**两阶段块坐标搜索**：先粗略地按主导设备把权重格式定下来，再做局部微调，只要总延迟下降就接受新布局。

![](images/f2626a5b17f6a1a83a1c63253d89be55853a794eedb64df457d58947d17d3554.jpg) *Figure 4: Overall workflow of DOPS for dissecting LLM inference on a heterogeneous NPU–PIM system. E2E: end-to-end.*

**布局格式对比与权衡策略**

| 权重布局格式 | 物理特征 | 对 NPU 的影响 | 对 PIM 的影响 | WLA 选择条件 |
| :--- | :--- | :--- | :--- | :--- |
| **Linear** | 行/列主序，通用 | 需运行时转换 | 需运行时转换 | 负载均衡，两者调用频率相近 |
| **NPU_OPT** | 分形/分块打包 | 直接加载，零开销 | 访存效率低，需重排 | NPU 调用占绝对主导 |
| **PIM_OPT** | Bank/Channel 对齐 | 需重排，开销大 | 直接加载，高并行 | PIM 调用占绝对主导 |

这个闭环最妙的地方在于：WLA 每改一次权子的格式，Bifocal 就得重新算一遍调度时间；Bifocal 算出来的调度轨迹变了，WLA 就得重新评估该存哪种格式。两者互相博弈，直到找到一个总延迟最低的平衡点。这就彻底打破了以前“先定格式再跑调度”或“只管调度不管格式”的割裂状态。
